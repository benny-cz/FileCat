# Administrator helper startup controls

These are bounded Windows component controls for I154/V06/B04. Run only on an authorized disposable administrative test environment. They do not approve or execute an operation plan and do not validate UAC or the consent UI. The launcher calls the actual `ElevationBroker.Launch` route with a nonexistent synthetic plan, waits six seconds, and terminates only its verified returned helper process if it remains running.

The hook writes one owned JSON observation and exits 73 before the target's entry point. Two direct hook positives bracket self-contained and framework-dependent helper launches. A corrected helper must have no hook marker; record its actual exit/refusal or bounded termination rather than treating every no-marker result as a successful plan execution.

Build `hook/Hook.csproj` and publish `launcher/Launcher.csproj` for the test architecture with the pinned repository SDK. Publish the actual `FileCat.PrivilegedHost` with the production self-contained/framework-dependent and ReadyToRun settings. The owned bundle contains `hook/`, `launcher/`, `broker-sc/` and `broker-fdd/`. Its manifest contains `NativeRoot`, `SourceCommit` and a `Files` array with each relative `Path`, `Bytes` and `SHA256`; independently hash every input and the transport before staging it. Use a fresh `C:\FileCatReleaseValidation\broker-loader-<32 lowercase hex digits>` root.

`Run-OwnedControls.ps1 -Root <owned root> -PayloadHash <payload.zip SHA256> -ManifestHash <manifest.json SHA256>` verifies the inputs, grants the ordinary account write access only to the owned hook directory, copies broker inputs into a fresh protected Program Files fixture, runs the four controls, verifies process/input state, and removes the protected fixture. It changes no machine/user environment variables or security policy. It preserves outputs and inventories under the owned root. Independently verify the returned output hashes, marker PID/image/identity and launcher results before interpreting them.

For a controlled comparison, preserve every launcher/hook/helper binary and change only the helper runtime configuration's `System.StartupHookProvider.IsSupported` value. Separately validate the actual committed publish output for both architectures and deployment modes. Full native loader/profiler/runtime/dependency/UAC/consent/installed-candidate qualification remains required.

The `native-profiler` sources are harmless I155 loader controls. Compile the DLL for the helper architecture with the Windows C++/SDK tools (`/LD /MT`, `advapi32.lib`, and `/EXPORT:DllGetClassObject=OwnedProfilerClassFactory`); compile `LoadLibraryControl.cpp` for the same architecture. DLL attach writes only `FILECAT_OWNED_HOOK_MARKER`; its deliberately unavailable factory supplies no profiler callbacks. Direct LoadLibrary/FreeLibrary controls exit 73. A separate launcher variant saves/restores process-local CORECLR_ENABLE_PROFILING, CORECLR_PROFILER and CORECLR_PROFILER_PATH, then calls the same actual broker route. Retain that exact variant, compiler inputs, payload hashes and positive controls. Do not substitute a managed hook positive for a native DLL positive.

The `witness` project is an explicitly synthetic managed entry point. In a separate pinned component copy, replace only the managed entry DLL with its output while preserving the native bootstrap, runtime and configuration. Under the same profiling environment it records the same-process PID/image, exact argument handoff, runtime version, sanitized environment and system directory/PATH, then exits 41 on success (42 on a failed condition). It never approves or runs a real plan. Its separate `.witness.json` file distinguishes successful CLR handoff from a bootstrap that merely refuses to start. These controls do not qualify the production consent UI, limited caller or healthy operation plan.
