## 1. Executive recommendation

**Implement native NTFS compression first. Defer EFS mutation; the previously proposed share-only EFS protocol is rejected, not merely awaiting tests.** Compression is useful occasional file-manager work: apply an existing Windows facility to a captured selection, see job outcomes, and retry incomplete work without visiting Explorer. It needs little permanent UI. EFS serves a narrower advanced audience and needs substantially more explanation, identity protection, and integration work. Misunderstanding compression costs space or time; misunderstanding EFS can cause loss of access or unintended unencrypted output. These are qualitative product judgments, not usage measurements.

Compression guarantees that FileCat inspects, transforms and verifies the same held physical object, reached by a case-aware, handle-relative no-follow traversal. It does **not** freeze all names or metadata against concurrent equal-privilege writers. Sharing flags cannot provide that stronger guarantee. Reject observed aliases/reparse objects and report detected churn; do not describe an exclusive namespace snapshot. EFS additionally needs a supported path-binding and conflict protocol that prevents silent decompression. No such recipe has been established here. WP6 is a bounded feasibility decision before investing in the EFS integration packages.

Ship one **NTFS compression…** command for the C-only release, directly after Attributes in **File → Inspect**. Put its panel context entry in **More FileCat actions**, with the exact Find/palette placement in §4.4. Show only Compress and Remove compression. Keep ordinary Attributes/times and Properties unchanged. Reserved EFS actions remain unavailable at the backend and absent from this dialog; the product must not advertise an encryption workflow before its protocol and gates exist. One explicit action, one scope, one typed job; no automatic replay or generic Undo.

Initial supported objects are ordinary local NTFS files/folders accessed as the invoking user, including eligible references from Find/working sets and removable NTFS. Qualification is required for each released architecture. Network paths, detected cloud-managed/offline items, unqualified reparse objects, multiply linked files, and system/volume roots are excluded as specified below. Compression has its own deliverable and does not wait for EFS.

Required work is marked **C** (compression and shared infrastructure) or **E** (conditional EFS only). **O** means optional. Allocated-size columns, savings estimates, new themes, animations, compression levels, and an Attributes-dialog cross-link are optional and are not release prerequisites.

Native compression keeps files usable in place; it is not Pack/Unpack. ### 4.1 Dialog and preparation

**One compact C form:** title **NTFS compression…**; captured selection/hidden-mark summary; current main-data/folder-default compression counts; two-action selector with unset initial state; contextual help; folder-scope radios only when folders are present; eligibility message; collapsed **Selected items (N)** disclosure; Cancel and the action-specific primary button. EFS flag/conflict details are contextual, not a second permanent status dashboard. No new toolbar, key-bar, panel column or nested Attributes controls.

Use the existing `DialogCard` clamping, scrollable body and fixed action footer; do not build another modal shell. Long names/reasons wrap inside the body. The footer and current action/scope remain keyboard reachable at the existing **640 × 420 DIP** minimum MainWindow/Find size and the existing high-text-scale/native accessibility qualification. Escape cancels review; focus returns through the existing modal ownership behavior. All controls have explicit names, text explains errors, and the submit button cannot act while action/eligibility is unset or stale.

**Captured-target disclosure:** back the at-most-64 rows only with the immutable capture, including eligible roots. Each row has the captured name, original full display location and provider, hidden-mark indicator, basic observed state and current action eligibility/reason. Use original locations to distinguish identical Find/working-set names in visible and accessible text. Search/copy include those locations; escape control characters losslessly using existing report helpers. No live listing subscription, filesystem work or target resolution occurs when expanding/searching/copying this disclosure. Reuse `MarkedItemsReview`'s presentation ideas, not its live-selection ownership. Auto-expand on a selected-root refusal. Captured membership is edited only by Cancel and re-marking.

Show cached counts immediately, then **Checking selected items: 20 of 40…** during bounded root inspection. More than 64 roots gets **Select at most 64 items. A selected folder can include its existing contents.** Aggregate main-stream/folder-default states as enabled, disabled, unknown/unreadable and unsupported; mixed known values remain distinct from unknowns. Caption: **Current state of selected items. Folder contents have not been inspected.** Distinguish Windows limits, FileCat scope, permissions and transient inspection failure. Compression Details says **Changes the main file data. Alternate data streams keep their own compression settings.** C performs no stream/key scan.

**Owned preparation:** acquire the native transient allowance before queuing inspection, then use `Services.Io.RunOwned` whenever a delegate acquires/uses a native lease. Link preparation, caller and `Services.Io.StoppingToken` cancellation. Do not copy the ordinary attribute reader's `Run`: its task can cancel before its delegate returns. A queued delegate may cancel immediately; a started delegate keeps all ownership until actual return. It disposes local leases on throw; a successful result remains in `try/finally` until current revision/cancellation checks and adoption succeed. A stale/unadopted result is disposed exactly once. Never return capacity early or wait for capacity from a device worker.

Keep the queued transient-allowance lease in a caller-owned `try/finally` around enqueue and awaited `RunOwned`: enqueue failure, an already-stopped scheduler or cancellation before entry must release it even though the delegate never runs. Started work keeps it until actual return. Transfer successful pins/results explicitly into their distinct review owner before caller cleanup; do not release adopted roots with the transient allowance or from a cancellation callback. `DeviceIoScheduler.Enqueue`/`WorkItem<T>.Cancel` are the existing never-started cases to exercise.

**Resource wait escape:** distinguish waiting for a resource from inspecting a file. If its owner supplies a live typed job reference, show the blocking operation's title and **Cancel preparation and show operation**. This cancels/closes the new preparation before focusing the existing main Operations pane and selecting the blocker; standalone Find routes to that owner window. The user can then Resume, Review decision or Stop that job. If another preparation/current-object review owns the resource, say **Another storage check or review is using this resource** and retain Cancel; focus its owner window only when a known owner exists. Do not invent a job/Operations row for a pre-job owner. A waiting preparation must not trap the decision needed to release its resource behind another modal.

**Initial versus actionable ownership:** for the standard **listing-selection invocation**, initial checking belongs to the captured listing generation. On invalidation, close/cancel the checking form, publish no job or stale review, and dispose late results through the owned path. If its origin is still alive/current, announce once **The selected listing changed while checking. Nothing was changed.** Do not automatically recapture or restart. When root checking has reached a stable review result and all successfully inspected roots' pins are adopted, detach listing-generation/tab-closed subscriptions before showing the actionable review. The review may contain refused/unreadable roots with submission disabled; only eligible complete checks for every root permit submission. From this milestone, navigation does not retarget the review. Dialog closure/application shutdown still cancels it, and native owners outlive any still-running delegate that uses them.

**Optional detached one-item invocation:** the companion details window may outlive its originating listing. Enable its compression link only after a narrow explicit-subject adapter is implemented and qualified. Capture exactly one original `ItemRef`, an action-request revision, report lifetime and shutdown token; never obtain selection or a generation from `ActiveTab`. Initial preparation belongs to that report/request and cancels if it closes or is canceled/replaced. Inspection-tier refresh does not replace this independent action request. Apply the same fresh native pins, action/scope review, limits and submission protocol. At the actionable milestone detach report-lifetime cancellation and let the modal review own the request; a later report close cannot cancel an approved review/job. Its job has no listing/mark-cleanup origin. Direct Find/listing commands retain the settled-Find/generation rules; this already-captured detached subject does not require the old Find to remain open or settle. The owning main window hosts the dialog. Missing adapter/owner disables the optional link without blocking C or F3. Permissions/attributes require their own adapter; this C entry does not make those existing selection-based commands safe to reuse.

**Review revision:** the dialog owns one monotonically increasing revision. Changing action/scope or starting Retry synchronously invalidates prior approval and immediately updates presentation/availability. Derive C eligibility from retained observations synchronously when sufficient; action changes do not replace root pins. If native inspection is necessary, allow one in-flight request and one replaceable latest request, each carrying revision/action/scope. Old completions cannot replace current facts or enable submission and cannot dispose pins already owned by the review. Use the bounded latest-request pattern in `MainViewModel.Links.cs`, not another preview framework. Radio changes update a single selected-action value from the newly checked option; do not read the first checked control during radio transition.

Retry always uses the original immutable capture. Keep every successfully adopted root pin alive; reinspection remains bound to it. A replacement at that captured path is stale and requires closing the review/start of a new request. A root which never acquired a pin may acquire its first pin on Retry, and its fresh facts must be displayed before approval. Post-milestone checks belong to dialog revision/lifetime, not the origin's later listing generation. Submission atomically freezes the validated action, scope, revision and unconsumed owner before closing the form.

**Button presentation:** extend `DialogButton` with one optional observable presentation snapshot (text, accessible name/help, Changed), retaining static `Text` as fallback. `OverlayDialogService` subscribes only for that dialog lifetime. On Changed, update text/accessibility **and requery existing availability in the same UI callback**. Final Click/Enter uses existing validation and the same storage-dialog action state. Do not add dynamic result delegates or a separate action model in the host. Unset action displays **Choose action**; changing Compress → Remove followed immediately by Enter must show/submit removal with current eligibility.

**Standalone Find entry:** require that the window has finished publishing its current search/refinement/grouping results, using a cached Find-local availability state. Include pending final refresh/group publication; `SearchSession.Finished` alone is insufficient. Reason: **Stop the search or wait for results to finish updating before changing compression.** Recheck direct dispatch before capturing/inspecting. This v1 rule avoids changing Find's refresh pipeline or weakening the initial generation boundary. After actionable review, later Find refreshes do not retarget the capture.

Before submission show **Storage changes run separately from other tracked file operations. Later queued operations may wait while this change is queued, paused, or waiting for your decision.** §6.4 distinguishes safe unstarted-job reordering from bypassing an active reservation. This note concerns FileCat jobs, not external applications.

### 4.3 Visible results

Storage results use the single snapshot and presentation rules in §6.4.1. A successful no-op must visibly say **Already satisfied**; successful job summaries must not disappear through the ordinary transfer renderer. Pending recovery becomes visible in the current session through §6.4.2.

Keep C/E Attr letters and existing file-name colors in list/picture modes. Preserve selected/focused/high-contrast precedence. After success, partial failure, cancellation, or uncertain completion, invalidate affected metadata and refresh open parent/descendant panels, workspace result tabs, and standalone Find views referencing affected items. Coalesce refresh on the UI thread; do not re-enumerate every panel for every item. Generation checks apply to refresh publication. For listing-selection invocations, keep incomplete roots marked; automatic unmarking of a complete root is allowed only if its origin still has the captured **TabViewModel.NavigationGeneration**, original location and captured mark revision. Add a small monotonic mark revision at `ListingModel.MarksChanged`; automatic mark restoration during a same-location refresh does not increment it. A later navigation intent or mark edit makes completion conservative: leave marks alone. Ordinary mark-preserving metadata refresh must not by itself disable completion cleanup. Do not clear a newly made selection after navigation away/back merely because names match. A detached one-item job has no mark-cleanup origin and never automatically marks, unmarks or reselects anything; affected-location refresh still runs. These guards affect selection cleanup only; they never invalidate a submitted job. Refresh must preserve unrelated marks and must not navigate a panel.

## 5. Platform, capability, and transition tables

### 5.1 Required native contracts and repository qualification

The existing seams are `WindowsFileRecords`/`WindowsFileRecords.Efs` for inspection, `WindowsFileOperations.Native` and `Elevation/NtFile` for handle/open patterns, and `Native/NativeMethods` for volume queries. The repository does **not** yet implement this plan's GET/SET compression service, path-based EFS mutation or key/export workflow. The following are required contracts and conservative scope decisions for those proposed adapters. Their ABI/constants, native results and refusals must be captured by the named §9 fixtures; existing method names, historical citations and header availability do not close a gate.

| Required contract / chosen boundary | Implementation decision and repository evidence gate |
|---|---|
| Classic compression uses synchronous `DeviceIoControl(FSCTL_SET_COMPRESSION)`; directories receive a creation default. | Proposed adapter uses `COMPRESSION_FORMAT_DEFAULT`/`NONE`, then `FSCTL_GET_COMPRESSION` on the same handle. No byte callback/within-file percentage. N-C1 qualifies calls and directory behavior. |
| GET describes the opened stream; DEFAULT is a SET input, not the expected successful GET result. | Accept GET NONE or known LZNT1 as appropriate. V1 changes only unnamed data/folder default and preserves named-stream states. N-C1 qualifies main/named stream states and hashes separately. If that invariant fails, leave the affected action disabled; do not silently add an ADS scan or broaden its scope. |
| Initial **enable** ceiling is 30,000,000,000 bytes. | This is FileCat's conservative qualification boundary, not a claimed universal kernel cutoff. N-C2 tests below/at/above it and large-file removal; removal does not inherit the enable ceiling. Broadening requires an explicit repository design change and new native evidence. |
| Initial compression support requires allocation units no larger than 4096 bytes. | Inspect the actual containing volume/unit; Unknown is unavailable. N-C2 qualifies supported/refused cases. Keep this eligibility boundary separate from other NTFS capabilities. |
| Conditional EFS uses path-based `EncryptFileW` and `DecryptFileW(path, 0)`; call success alone cannot establish the intended effect or prevent silent decompression. | No adapter ships before replacement E-ID feasibility. Preflight conflicts and read postconditions even after failure/cancellation requested during a call. N-E1/N-E2 qualify exclusive-access, folder/read-only-child and compression-conflict cases. |
| Conditional `FileEncryptionStatusW` results retain exact native reason codes. | Map encryptable/encrypted/unknown/read-only/system/root/filesystem limitations distinctly. Status alone does not establish build/policy/key support; N-E1 must qualify enabled cases. |
| Volume evidence includes compression/encryption support and read-only state. | Extend the existing handle-based query seam to preserve flags including `FILE_FILE_COMPRESSION`, `FILE_SUPPORTS_ENCRYPTION`, `FILE_READ_ONLY_VOLUME`; qualify ABI/flags in N-C2/N-E1. Do not treat `VolumeInfo.Unknown` booleans as negative proof. |
| EFS's initial enabled-build policy excludes Home; ARM64 requires separate qualification. | An edition/architecture string is not capability evidence. Conditional EFS enables only qualified build/action combinations; unknown build/policy remains unavailable. Do not infer a universal ARM limitation or borrow x64 evidence. |
| Ordinary attribute editing stays separate from compression/EFS. | Keep existing attribute masks unchanged. Sparse EFS cases need N-E1; TxF, raw FSCTL and replacement-file workarounds are outside the admitted EFS protocol. |

Proposed interop values are GET `FILE_ANY_ACCESS`, SET read/write access bits, and NONE=0, DEFAULT=1, LZNT1=2. Verify them against the actual build ABI when adding the Windows adapter and record that version with N-C1 evidence. They are not declarations already present in this service. Directory access-bit names and the concrete handle recipe are specified in §6.3; header verification alone is not native acceptance.

### 5.3 File transitions

Apply physical/scope eligibility first, then compare the requested action with held observations; request mutation rights only when a change is needed. C inspection reads identity, type, size/link count, relevant flags/tag, actual-volume capabilities and main-stream GET. Its EFS conflict input is the held `FILE_ATTRIBUTE_ENCRYPTED` flag. It must not enumerate ADS, call `FileEncryptionStatusW`, query EFS users/recovery agents, acquire private keys, run setup/backup or require output receipts. Detailed EFS eligibility is a later E-only service.

Below, U = neither main-stream compression nor EFS enabled, C = classic main-stream compression, E = EFS. “Already” is an observed no-op preserving unrelated state, including named-stream compression. It requires neither a write-capable handle nor a redundant SET/EFS call; an E-only Remove compression no-op must not require the user's decryption key. If basic state is unreadable, do not infer a no-op. The E-only named-stream refusal in §5.2 overrides U→E. Already-E items need no new stream conversion/key setup. Physical exclusions such as reparse/multiple links remain exclusions even when the requested flag appears set; ReadOnly regular-file refusal and the enable-size limit apply only when a change is required.

| Observed file state | Compress | Remove compression | Encrypt with EFS | Decrypt |
|---|---|---|---|---|
| U | SET DEFAULT → verify C | Already U | EFS setup/recovery review, Encrypt → verify E | Already U; no key setup |
| C only | Already C | SET NONE → verify U | Conflict; separate remove required | Already C; preserve compression |
| E only | Conflict; separate decrypt required | Already E; do not decrypt | Already E; no call/rekey; do not require a new backup merely for this no-op | Reviewed Decrypt → verify U |
| Both flags, unrecognized compression format, or inconsistent observations | Refuse automatic mutation; report exact observed facts and request inspection | Same | Same | Same |
| Unknown/unreadable | Reinspect or refuse; never assume disabled | Same | Same | Same |
| Unsupported physical object/location | Refuse with exact reason | Same | Same | Same |
| Mixed roots | Evaluate each root and display population counts; any known refusal blocks submission; otherwise each follows its row | Same | Same | Same |

Idempotence is based on requested intent and observed state, never a UI comparison that discards the request. For C, a failed native return with the desired postcondition observed is Changed with an issue; a success with a readable wrong postcondition is Failed, never AlreadySatisfied. Unreadable postcondition after a call is Uncertain, even if the API reported success. PartiallyApplied describes the selected scope under §6.4.1, not another object count or a “partially compressed” native format. Conditional E records only effects its admitted protocol actually supports observing.

### 5.4 Folder/scope order

| Action | Selected items only | Recursive order and failure behavior |
|---|---|---|
| Compress | Set/verify selected folder default only | Preorder: set/verify each directory before walking it, then process files and subdirectories. Already-C directory still descends. |
| Remove compression | Clear/verify selected folder default only | Preorder: clear defaults before descendants so ordinary new creation does not keep reintroducing compression. Already-clear directory still descends. |
| Encrypt | Set/verify selected folder default only, after E gates/setup | Preorder: establish directory default before existing children. Already-E directory still descends. |
| Decrypt | Clear/verify selected folder default only | Preorder: clear default before descendants. Review explicitly covers future creations becoming unencrypted as well as processed existing content. |

If a directory's requested default fails, conflicts, or cannot be verified, skip its subtree and report why; continue independent roots/siblings. A successfully changed parent remains changed if a later child fails or Stop is requested. No postorder restoration. A C directory's ReadOnly marker alone does not cause this refusal. An AlreadySatisfied directory still needs listing access to traverse; failed enumeration is a distinct incomplete-subtree outcome.

A completed pass covers discovered, admitted objects, not all objects at an instant. Roots have continuity to their still-live review pins. A descendant becomes admitted when successfully opened and inspected through its held parent. Compare the enumeration record's available identity/kind with that handle; a mismatch or disappearance is churn and is not mutated. An enumeration record alone does not keep an object alive: before admission, live membership can change and not every replacement/recycled ID can be detected. After admission, inspection, mutation and postcondition use the same held object. New entries encountered before the cursor passes may be processed; later arrivals may be missed. Do not prescan/pin every descendant or repeatedly rescan for convergence. Report detected churn and ask for a fresh reviewed scope after writers stop when needed.

### 5.5 Sparse-file support work

Sparse state, logical contents, allocated storage and hole ranges are separate observations. A sparse attribute does not prove that holes currently exist, and allocated size below logical size does not by itself prove sparse holes: compression, shared extents and filesystem accounting can also explain it. The companion plan owns bounded read-only details. This plan owns interoperability with the four explicit storage actions; creating holes, punching ranges and clearing sparse state remain separate, unrequested mutations.

Microsoft's [File encryption](https://learn.microsoft.com/en-us/windows/win32/fileio/file-encryption) explicitly permits sparse files. Plan EFS support as a candidate that preserves sparse state and logical data, subject to all current EFS gates. The documented [compression control](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ni-winioctl-fsctl_set_compression) does not establish this application's sparse-preservation contract. Qualify compression and decompression independently instead of assuming either compatibility or a universal Windows prohibition. The current `sparse-entry` refusal is a FileCat qualification boundary, not an assertion that Windows cannot encrypt sparse files.

| Work | Required behavior and finite acceptance destination |
|---|---|
| S-DETAILS: sparse observations | Use the companion summary/full-report bounds and provenance. Distinguish main data from named streams, a sparse marker from observed ranges, and Known zero allocation from Unknown. Existing F-COMPLETE range/cancellation cases apply. No new recursive scan or savings estimate. |
| S-EFS: Encrypt / Decrypt | Add independent N-E1 sparse subresults for main data and ADS, files with and without actual holes, already-satisfied actions, ReadOnly/denial, and a large logical file. Verify held identity, EOF, data sentinels/full hashes on bounded fixtures, zero reads in holes, sparse state, before/after ranges and allocated size. An allocation change must be explained by the qualified filesystem behavior; do not promise unchanged physical extents. Key recovery, all-stream decompression consent and the acknowledged pathname boundary still apply. |
| S-C: Compress / Remove compression | Add N-C1/N-C2 subresults for sparse + clear/compressed states, native rejection and no-op. Preserve the sparse attribute, logical contents/EOF and named-stream state. Observe holes/allocation independently. Never clear sparse state, replace the file, preallocate EOF or write zero-filled holes to make a call succeed. If a required preservation condition fails, keep that action unavailable for sparse inputs with its precise reason. The compression-enable size ceiling remains action-specific. |
| S-OUT: existing output paths | Exercise existing `WindowsSparseCopy` and hex/save/copy/archive paths that claim sparse preservation, including an EFS sparse source and replacement destination where those routes are enabled. An EFS output receipt is still required before payload output. A route without sparse preservation must disclose potential allocation growth; a route without EFS admission must refuse before new plaintext output. Do not imply every archive/remote target can represent sparse holes. |
| S-RACE: lifetime and cancellation | Use deliberately prepared disposable fixtures with zero, one and many ranges; changing EOF/ranges, concurrent writes, full disk and device loss. Inventory remains bounded and cancellation cannot retire a started native owner. Exact native outcomes and partial output are recorded; no convergence rescan or automatic repair. Extend T-CAP/T-OUT/T-LIMIT/T-REG and N-ID rather than treating a single round trip as whole-feature acceptance. |

Implementation order: retain truthful inspection/refusals, add the native preservation fixtures, then enable each qualified action/category with the existing review and job protocol. Windows sparse mutation qualification does not establish Linux/macOS support. Their read-only details and existing copy behavior have separate API-view evidence. Native receipts identify filesystem, allocation unit, architecture, initial flags/ranges, the exact action and observed effects; skipped fixtures remain open.

Do not extend `AttributeChangeSet`: this action requires explicit scope, ownership, journal and result semantics without changing Unix/ordinary-attribute behavior. These are contract shapes, not literal final API signatures. `ReviewedStorageRoots` contains immutable bounded original source references, root-index/overlap mappings, captured-origin metadata, observations and an opaque one-shot native lifetime owner. The **native owner alone** is disposable/transferred; immutable sources and outcome mappings remain usable by UI/history after it is released. No raw Windows handle enters portable Core. `StorageReviewApproval` freezes action, scope and review revision; C requires no certificate/output consent object. Later E packages may add typed EFS approval data without making it a dependency of C composition.

The current [held-adapter implementation checkpoint](../validation/filesystem-details/2026-11-17-held-traversal.md) separates `IStorageObjectLease.PrepareMutation(action, ct)` from token-free `ApplyAdmitted(action)`: acquire/validate rights before durable intent, then consume that preparation once after atomic job admission. `StorageMutationResult.NativeCallAttempted` distinguishes no-call outcomes. `StorageObjectIdentity.VolumeBinding` supplements serial/ID with the verified actual volume GUID, preventing collisions across distinct volumes from becoming deduplication authority. These implemented seams do not by themselves close the durable execution or complete native acceptance gates.

For C, object outcomes are disjoint: Changed, AlreadySatisfied, Skipped, Failed, Uncertain or NotProcessed. **PartiallyApplied is a scope result**, derived from an incomplete root with some known changes, not a seventh object count or a partially compressed file state. Use the separate scope/completeness axes and result snapshot in §6.4.1. Conditional E must classify only effects its supported protocol can actually observe. Journal call disposition separately records **NotAttempted** when an intent was persisted but admission canceled/paused before Windows. Windows encapsulates native compression format and diagnostic codes and translates them to typed reasons. Conditional E eligibility includes a bounded, complete named-stream summary; it is absent/Not inspected in C. Never interpret absent E details as a clear stream inventory.

Add `IPlatform.StorageTransforms`, with explicit unsupported behavior in `PortablePlatform` and proposed `WindowsStorageTransforms`. Inject it through `AppServices` → `JobManager` → `JobExecutors.Create`; deterministic tests supply a C-only fake with no EFS services. All P/Invoke, actual-volume checks, relative no-follow opens, identity binding and mutation stay in `FileCat.Platform.Windows`. Add the small EFS key/backup UI seam only if WP6 admits E work, using the existing native-window owner pattern for parenting.

Backend admission is mandatory: an EFS action in the compression build is rejected before taking the reviewed owner, creating a job/journal, setup or native mutation. Validate action/scope enums, payload-kind consistency, 1–64 original local sources, the ordinary-path grammar below, review/action/scope revision, live unconsumed pins and bounded metadata serialization. Never default an unknown action to compression or infer one from displayed flags.

**Ordinary-path grammar:** accept only fully qualified local drive paths, supported extended-drive paths and volume-GUID paths after explicit volume-root parsing/locality validation. Preserve the colon in a recognized drive prefix; reject a colon in every remaining path component. Refuse named-stream and explicitly stream-qualified forms, including `file:ads`, `file:ads:$DATA`, `file::$DATA` and directory-stream spellings, **before review pin acquisition/deduplication and again at manager/native boundaries**. Never strip a suffix and silently target its containing file. Reject drive-relative/root-relative paths, UNC/extended UNC and raw device/object-manager namespaces as user targets. Every relative child open receives exactly one validated name: no rooted path, `.`, `..`, separator, NUL or stream colon. Preserve supported raw Unicode, legal long-path spelling and case. Result/working-set originals obey the same rule. File-ID equality binds file lifetime, not which stream was opened; this grammar enforces C's unnamed-stream scope without an ADS scan.

### 6.2 Admission, bounds, and traversal

1. Capture `SourceSelection` once and reject more than **64 selected roots** without materializing all their `ItemRef`s. Where the cached mark count already exceeds 64, refuse before capture. Once the count is within the bound, copy at most 64 original references into an immutable array, preserving order, hidden-mark status and original source-index mappings. Capture the origin tab and its **current location at capture time**. Release the original `SelectionSnapshot` through `ItemSources.Release` in a `finally` after the copy, or on rejection. The bounded array becomes `JobRequest.Sources`; keep original result references for UI/marks and separately unwrap the actual local targets for native work. Never acquire a fresh selection after review.
2. Reserve the whole requested root-pin allowance atomically from an app-wide **256-pin pool** before preparation. Retain one metadata-only pin per distinct reviewed root, shared read/write/delete, through review, queueing and native-owner retirement. Pins preserve lifetime, not names. Deduplicate only against simultaneously held pins on the same verified volume; maintain every original root mapping. Do not case-fold names. Stored IDs/timestamps are not substitutes for live pins because IDs can be reused. If capacity is unavailable, show the resource reason; do not drop approved pins to admit another job.
3. For recursive scope, prune a selected descendant from physical traversal only when live-pinned verified ancestry shows that an admitted selected ancestor covers it. Preserve both outcome mappings. Selected-only scope does not prune it. An ancestor failure before reaching a covered root leaves that root incomplete. Text prefix/lowercase comparison is not ancestry proof.
4. Traverse with a nonrecursive, no-follow directory cursor per active depth. Include hidden entries and explicit enumeration/access failures. Do not reuse `IgnoreInaccessible=true`, materializing `NtFile.List`, or an all-descendants collection. The admitted directory handle itself owns its cursor (§6.3); no second filesystem handle is opened merely for enumeration. An excluded directory contributes one skipped observation and an unvisited subtree of **unknown** size.
5. **Resource owners:** depth is at most **64 including ancestors above a selected root**; enumeration buffers are **64 KiB**. Preserve the process maximum of **448 storage-feature filesystem handles** as **256 root pins + 188 native slots + 4 evidence slots**. The native allowance is acquired atomically by one independent preparation, active worker or current-object recovery observation; it has 128 traversal/ancestor and 60 scratch slots, including that worker's journal writer. A worker with 64 pins therefore owns at most 252 handles, below the 256 active-transform ceiling. A preparation releases its 188-slot allowance after its delegate actually returns and review adoption/disposal finishes; the review keeps only its root pins. A queued job keeps those pins and acquires the native allowance for execution. An active worker retains its 188 slots across pause/decision waits; other native preparation waits cancellably with no transient handles and the escape in §4.1. Conditional setup borrows from the worker's existing allowance. All opens are charged before execution. Do not wait for more native capacity while holding a partial independent reservation. At a bound, report the unvisited branch and unknown remainder; do not drop approved pins.

   The four evidence slots are reserved separately: **one** for the incremental history directory cursor and an atomic **three-slot envelope** for one header/detail/report-export/acknowledgment operation. This permits history discovery and a bounded live report to coexist without borrowing native slots. A history cursor may wait for the three-slot envelope; an envelope operation must never wait for the cursor. Sequence artifact opens to fit three slots: for example, journal ownership + a temporary-directory cursor + one artifact stream; envelope-local enumeration uses its own slot, never the dedicated history cursor. It closes all evidence handles, including journal ownership, and releases its envelope **before** waiting for native current-object observation. After observation, acknowledgment reacquires evidence ownership and revalidates the exact snapshot. Native mutation/result persistence/finalization never waits for either evidence lane. All started I/O delegates retain their charged ownership through return (`RunOwned` where scheduled). These are fixed ownership limits, not a general resource scheduler. Windows wizard internals and unrelated viewers are excluded from this feature count.
6. Keep compact visited/outcome records bounded by **1,000,000 observations or 64 MiB**, whichever comes first. Store owner-root mappings, effect and subtree completeness; no full descendant paths or handle per visited object. Once its handle closes, an ID is only a deduplication hint. Rediscovery that cannot be tied to a still-live admitted object is ambiguous churn: do not mutate again, infer AlreadySatisfied, or reuse a prior complete outcome. Leave the receiving root incomplete, including a moved partially processed directory. Stable trees have physical-object counts; churn uses observation counts plus ambiguous-duplicate counts. At the cap stop discovery with unknown remainder. Journal capacity can stop mutations earlier.
7. Check pause/cancel between opens and enumeration batches. Mutation cancellation uses the atomic admission point in §6.4, not just `Checkpoint(); NativeCall();`. Use at most two short automatic retries for sharing violations **before a call was admitted**, then a job-scoped Retry/Skip/Stop decision. Revalidate the same pinned/admitted object and current state on every retry. Never auto-retry uncertain or partially applied effects. Apply-to-all covers only this job/action/reason; it cannot authorize conversion, another root, another key or EFS loss on an output route.
8. Hidden files are included. Apply the exact protected-target policy in §5.2, plus reparse/cloud/multiple-link and other physical exclusions. For C, a regular ReadOnly file needing change is refused; a directory's ReadOnly marker is preserved and alone does not exclude the directory or subtree. Panel filters do not narrow authorized descendants. Never add parents/siblings or cross a mounted-volume reparse.
9. **E-only:** named-stream metadata is limited to **1,024 streams and 1 MiB of names/state per object**. Enumerate through the held object; bind stream opens to it, and use scratch slots. Overflow, failed enumeration or incomplete results refuse EFS enable. `NtFile.Streams` and path-materializing helpers cannot silently turn failure into an empty inventory. No payload scan is required. An immediate recheck does not freeze membership; a future E-ID protocol must cover that gap. This entire step is absent from C preparation/execution.

### 6.3 Native binding and identity

**Guarantee and threat boundary.** Authorization is to the admitted physical object, not an immutable set of names. FileCat must not follow a redirected path to mutate a replacement object. It rejects observed reparse/cloud/multiple-link objects and reports detected churn. It does not promise to prevent another equal-privilege process adding an alias or changing metadata during or after the operation. Mutation-handle sharing restrictions exclude relevant competing data opens; attribute/EA access is outside that mechanism. Hard-link creation does not require specific source-handle access rights, and the reparse protocol permits write-attributes access subject to its other checks. Therefore a sharing-only proof of alias/reparse exclusion is invalid.

**C protocol:** enforce §6.1's ordinary-path/component grammar first, then resolve the local volume and walk exact components relative to held directories, no-follow at each component, respecting case-sensitive directories. Resolve the active Windows directory from the platform-known location (the existing WindowsShellServices path uses Environment.SpecialFolder.Windows), and compare verified ancestry/held identities for §5.2's protected-tree policy. Any temporary protected-tree anchor is a charged scratch handle and is rechecked for the current preparation/execution, not an unpinned ID treated as permanent authority. Refuse observed reparse ancestors/leaves. Existing `NtFile.TryOpen` cannot be reused with unconditional case folding. On admission freshly walk the captured root spelling and compare the resulting held object with the still-live review pin; missing/replaced/renamed binding is stale, not authority to chase the old object to a new name. Do not assume `ReOpenFile` accepts the `NtCreateFile` handles used by existing helpers; this plan only considers it for a qualified `CreateFile` handle.

Inspect first with nonmutating held access. If the desired state is already known, do not acquire write rights or call SET merely to obtain an AlreadySatisfied result. For an actual change, acquire a handle through the same held parent while the inspection pin is still alive, compare identity, and re-inspect all C eligibility/state on that handle. Use `FILE_OPEN`, exact component lookup, no-follow/open-reparse-point semantics and synchronous ownership. A regular mutation handle requests `FILE_READ_DATA | FILE_WRITE_DATA | FILE_READ_ATTRIBUTES | SYNCHRONIZE`, with **FILE_SHARE_READ only**, excluding competing data-write/delete sharing. A metadata-only lifetime pin requests attributes/synchronization, no data read/write/delete, and shares read/write/delete. A pre-existing incompatible writer yields refusal/retry. GET/SET/GET use the **same mutation handle**, never a pathname fallback. Inspection acquiring no payload rights must not hydrate excluded cloud/offline content.

**Directory recipe:** the mutation rights use directory names for the same bits: `FILE_LIST_DIRECTORY` (1), `FILE_ADD_FILE` (2), `FILE_READ_ATTRIBUTES` and `SYNCHRONIZE`, with `FILE_DIRECTORY_FILE`, **FILE_SHARE_READ only**, and the same no-follow/synchronous open policy. Perform preorder GET/SET/GET on that handle, then retain **that very handle** as the enumeration/ancestor owner until the branch retires. Its cursor is in-memory state, not a new open. No `ReOpenFile`, duplicate conflicting enumeration open, or close/reopen transition belongs to this path. For an AlreadySatisfied recursive directory, acquire only listing/attribute/synchronization rights through the held parent, using **FILE_SHARE_READ | FILE_SHARE_WRITE and no FILE_SHARE_DELETE**. Keep inspection continuity while comparing identity, then recheck state on this listing handle. If a change is now needed, acquire and validate a mutation-capable handle while the listing handle remains held; its write-sharing makes FileCat's own two opens compatible. Retire the listing handle before enumeration and use the mutation handle for GET/SET/GET and the cursor. External incompatible owners still yield refusal/retry. A no-op listing handle does not freeze the directory default against another writer; record detected subsequent churn under the same stated observation limits. Selected-only directory no-ops need no listing handle.

Keep no-follow parent handles during descent. Compare available cursor identity/kind before child admission (§5.4); root admission also compares the still-live review pin. Re-observe relevant metadata before descent and after mutation; detected redirection/alias change makes the branch incomplete even if its held object changed successfully. These checks detect some churn and do not prove that every transient metadata/alias change was observed. N-C1/N-ID must qualify this exact directory sequence with the metadata review pin simultaneously held, listing across descendants, access failures and cancellation; the proposed recipe is not an already-run native pass.

N-ID must verify same-object binding with leaf/ancestor replacement, case-distinct siblings and an attribute-only adversary, including attempts at hard-link creation and reparse insertion on eligible empty directories. Record whether each competing operation succeeded. Passing requires no wrong-object mutation and truthful observed outcomes, **not** a claim that every alias or metadata change was prevented. If an absolute exclusive-namespace guarantee is required instead, compression is also blocked; this plan deliberately adopts the narrower held-object contract.

**Rejected EFS candidate:** the prior attribute-only leaf hold sharing read/write but not delete permits a writer to compress the main stream after final inspection, close its handle, and let `EncryptFileW` silently decompress it. Denying data-write access instead conflicts with the access EFS itself requires; dropping that hold before the call restores the gap. Stream sharing is per stream, so holding the main stream also does not freeze new compressed ADS membership. This is a contract-level counterexample, not a race stress test awaiting a lucky pass.

E-ID must first produce a **different supported protocol**, with repository-recorded reasoning and exact native contracts for path binding and main/named-stream conflict exclusion, before native qualification. Retain the same honest alias/metadata threat boundary as C; do not revive an impossible universal exclusion claim. Successful stress runs or before/after pathname equality cannot establish that a wrong object was never changed or compression never silently removed. No supported replacement has been identified by this plan. Keep Encrypt and Decrypt unavailable; no unbound retry, invented handle-based EFS API, raw FSCTL, TxF, or account switch. A different conflict-consent policy would be a separate explicit design change, not an implementer's escape hatch.

FileCat must not intentionally change data, unrelated streams, names, DACL/owner or unrelated flags. Qualification in a quiescent fixture compares stream inventories/hashes and security metadata, including creation/last-write times; access/change times may reflect the operation and are recorded. With concurrent writers, detected unrelated changes are reported, not silently restored, and byte invariance is not attributed to FileCat without isolating those writers. Hard links share the transformed object, including a concurrently created alias.

**Scheduler reservation and observer discipline:** tighten the existing scheduler, not its scheduling algorithm. `Schedule` currently publishes canceled state while holding `_lock`, then resumes a materialized queued list; a reentrant observer can already have started a later entry. Reserve cancellation retirement under the manager lock, and perform resource retirement/state/event publication outside it. Immediately before reserving every candidate, recheck that it is still Queued and neither `_admitting` nor `_starting`/retiring. A launch claim is one-shot. A false `TryStart` must distinguish genuine pre-start cancellation from a stale/duplicate attempt against an already-owned worker; the latter never releases that worker's resources or publishes its terminal state.

Every reserved dispatch-batch entry gets a disposition even if an earlier callback fails: start once, return an unstarted claim to the queue, or finalize a proven pre-start failure. Once admission succeeds, isolate notification exceptions **per subscriber**, including Job.Changed/terminal notifications, log them and continue later subscribers/dispatch/scheduling. An exception in a Running notification alone does not veto already-approved work. Admission registration/JobAdded remain the earlier abort-and-rollback boundary. An actual thread handoff failure does enter pre-start Failed completion. One terminal-completion routine owns finalization, native release, terminal state and exactly-once JobFinished, and guarantees a subsequent scheduling pass even if a notification fails. Captured-origin cleanup must run in its subscriber's finally. Do not use notification success or a false TryStart as proof that no native worker exists. Tests must distinguish a contained notification exception (worker may run once) from an injected actual handoff failure (worker never enters).

Pause/Resume gate updates must join Cancel and per-call admission's control-lock protocol; they currently do not take `Job._startLock`. Never dispatch observers while holding the manager/control lock, or hold those locks over native I/O/flush/waits. Use the existing dedicated job thread for traversal/coordinator waits; do not wrap the whole traversal, pause or user decision in a DeviceIoScheduler delegate, whose watchdog would treat that wait as a hung device.

**One-shot owner transfer and exact retirement boundary.** Add a storage-specific native-owner registry to `JobManager` (a proposed `JobManager.StorageTransforms.cs` partial is sufficient). Do not attach these owners to `CaptureReadLeases`, which currently covers Copy/Extract and releases before journal finalization. After validation, atomically take the review's native owner once and register it under `_admitting` before any observer can cancel/start the job. All failures after that point belong to manager cleanup; the review sees an already-consumed owner and must not dispose it again. Failure before transfer leaves the review responsible. A transferred review cannot be submitted twice.

Use `SubmitWithRegistration` to register the invocation's explicit origin disposition while admission still excludes scheduling. A listing-selection callback registers the **captured tab/location/navigation and mark revision**, not `Track(job, tab)` reading later state. A detached one-item callback registers **no selection-cleanup origin**; do not invent an active tab or suppress `RefreshAffected` because that origin is absent. Extend Track/registration narrowly for those two cases. If the callback/JobAdded throws and submission removes the job, remove its registration too. Preserve immutable source-index/overlap mappings for outcome attribution; only listing-origin completion may enter guarded `MarkItems`. The at-most-64 source array remains valid after tab closure and requires no listing-store lease.

The manager releases native pins/transient reservations exactly once after **native return → postcondition attempt → durable result or retained recovery fault → journal finalization/disposal**, and **before** publishing a terminal state or invoking `JobFinished`. This requires a storage-specific outer cleanup path; the existing pre-Finish `ReleaseReadLeases` finally block is too early. Admission/JobAdded rollback, genuine pre-start cancellation, proven thread-handoff failure and eventual worker exit use the same terminal take-and-release path after their last actual owner has stopped. A contained post-admission notification exception is not a retirement trigger; a stale duplicate `TryStart=false` against an existing owner is not either. Immediate pre-start release is permitted only after withdrawing its launch claim and proving no worker can still enter. Cancellation during `_starting` must resolve that claim before retirement. Do not wait for `JobRemoved`, `TrimFinishedLocked` or Clear finished; those are history operations, not native retirement. Failed durable writes retain files/recovery state, not dead native handles. A terminal job must own no root pins or transient allowance.

**Atomic per-call admission.** A plain checkpoint followed by a native call races with Stop. Add a small proposed `Job.TryAdmitStorageCall` synchronized with `Cancel`/pause state using the existing control lock; it must not hold that lock during I/O or Windows execution. Prepare parameters and the held-object inspection, reserve result capacity and flush intent first. Then atomically decide:

- Cancellation before admission: make no native call and durably pair the intent with **NotAttempted / Canceled before call**. A failed pairing remains recovery-pending.
- Pause requested before admission: pair the intent with **NotAttempted / Paused before call**, enter the existing safe pause boundary, and re-inspect before a later fresh intent. The lifetime/root ownership remains held. No silent mutation while Paused.
- Admission succeeds: exactly that one call is considered in flight, even if Stop arrives immediately before OS entry. Invoke it without another cancellation throw between admission and invocation; observe and persist its actual outcome even if Stop was pressed. No subsequent mutation can be admitted after cancellation. An exceptional failure proven before OS entry records NotAttempted; an ambiguous entry/return records Uncertain.

Test both sides of this admission point with deterministic barriers. Do not hold a UI/control lock while the native call or flush runs, and do not describe cancellation as rollback.

#### 6.4.1 One result snapshot, terminal reducer and presentation

Add one proposed immutable **StorageResultSnapshot** to Job/report capture; publish a coherent value after each accounted boundary and at finalization. It contains action/scope/revision, disjoint global observation outcomes, per-selected-root identity/completeness, discovery completeness/unknown remainder, complete reason counts with severity, bounded no-call samples/omission count, current path/action, durable journal-prefix receipt and historical effect/review state. UI snapshots may coalesce; exact native-call evidence still follows its durable protocol. A stable object contributes one final object outcome. Verified overlapping root summaries may describe the same object and are **not additive** into the global totals. Under churn label observation counts and ambiguous duplicates honestly.

| Case | Object accounting | Separate scope/problem fact |
|---|---|---|
| Directory changed, then enumeration fails | One Changed directory; each independently observed child gets its own outcome. | Selected root Incomplete/PartiallyApplied; omitted descendants have unknown count. Never add a second failed directory object. |
| Native error, desired postcondition observed | One Changed object. | Retain Changed-with-issue reason/severity; do not count it again as Failed. |
| Already desired, no native call | One AlreadySatisfied observation. | No mutation intent/result; aggregate no-call counters. |
| Native call, unreadable effect | One Uncertain observation. | Error, stop remaining work, ReviewPending. No success inference from return code. |
| Exclusion or known unchanged failure | One Skipped or Failed observation according to the typed reason. | Complete reason count regardless of whether a detail sample was retained. |
| Known item not reached because Stop/bound | One NotProcessed only if its existence was actually known. | Unseen descendants remain unknown; never compute them as total minus processed. |

For compatibility, update generic counters once from final object dispositions: `ItemsDone = Changed + AlreadySatisfied`, `ItemsSkipped = Skipped`, `ItemsFailed = Failed + Uncertain`. NotProcessed and root completeness remain typed fields; reported settled observations may include NotProcessed, while processed means the five reached outcomes. `ItemsTotal` is discovered observations, never an invented full-tree total. A paused pre-call NotAttempted journal pair is not another object outcome; later processing settles that same observation once. `TotalsFinal` is true only when the authorized discovery completed without unknown omitted scope. Sample count is never total issue count.

The manager uses the following **storage-specific final-state reducer**, before any generic cancellation override:

| Precedence | Terminal state and meaning |
|---|---|
| 1. Uncertain effect, result/finalization persistence fault, or unresolved review-required evidence | **Failed**, error severity and Review storage changes, even if Stop was also requested. Preserve already-known completed changes. |
| 2. Otherwise accepted user cancellation | **Canceled**; severity and summary still preserve known errors/warnings and actual changes. |
| 3. Complete discovery, all selected roots complete, only Changed/AlreadySatisfied, no remaining issue | **Completed**; an all-AlreadySatisfied request is a visible successful no-op. |
| 4. Remaining known partial/incomplete/issues with successful processing | **CompletedWithIssues**. |
| 5. No successful processing and a known error/failure or no progress because an execution/resource refusal prevented work | **Failed**. An all-policy-skipped pass with no error remains **CompletedWithIssues**, explicitly saying nothing was changed. |

Do not let generic `FinalState`, RootCompleted bits, retained JobIssue samples or the later cancellation assignment override this reducer. Severity derives from complete typed facts. A job with omitted scope never becomes Completed merely because no sample exists. Native owner finalization/retirement occurs before the chosen terminal state is published.

**All UI/report surfaces use this snapshot:** compact strip, history row, selected details, taskbar, success/failure/Stop notification, ordinary report and retained recovery report. Always show the storage outcome summary, including successful AlreadySatisfied counts; suppress generic **No issues reported** when typed counts have issues. MainWindow notifications explicitly handle this kind instead of falling through transfer-specific dispatch. Detail sample labels distinguish full reason totals from at-most-16 examples.

For v1 omit **all percentages**, including terminal 100%, all transfer/item rates, graphs, ETA and savings. Bypass the generic estimator for storage. While running/discovering, show an indeterminate activity indicator and text such as **24 checked; folder contents are still being discovered**; show elapsed time and current action. Paused/decision/Stopping states use their state text without a fabricated numeric fraction. The taskbar is indeterminate for running work, uses state-only paused/error indication with fraction zero where required, and does not imply coverage. On finish replace activity with the outcome/completeness summary. Compact current names may be shortened; selected details/accessibility/copy provide the exact current path. No extra permanent metric rows are introduced.

#### 6.4.2 Same-session recovery, report detail and layout

When a storage job retires with ReviewPending, publish one deduplicated candidate, keyed by journal/job identity, into the existing **Needs review** collection immediately after its writer/native ownership closes. Do not wait for MainWindow's startup-only `LoadInterruptedAsync`. Its finished row and notification expose **Review storage changes** and select the same candidate. Removing/clearing finished history never removes pending recovery. Startup/incremental scans merge by the same identity. Acknowledgment removes the pending action only after the validated durable pair exists; its reviewed row says **Reviewed; effect remains uncertain** when applicable.

Extend the existing recovery-row capability/reveal path currently specialized for archive review so storage review actions and Stop review remain visible and focusable. Reuse that drawer and its report window. Storage jobs use **Stop** rather than the generic Cancel label; explain completed changes remain and an admitted call still finishes. A pending/failed result must say **Result not confirmed**, with its actual cause, rather than always claiming a crash. One narrow/high-scale fixture covers a stopped job, pending review and an older reviewed uncertain history with wrapped, keyboard-reachable actions.

Reports have three clearly labelled parts: **Summary** (all selected-root identities/statuses, exact or explicitly lower-bound counters, uncertainty and unknown remainder), **Call details** (exact retained native intent/result evidence, paged/streamed), and **Examples** (bounded no-call samples and omission counts). Preserve unresolved-call facts and every incomplete-root identity before optional successful examples in the bounded retained report. Missing/corrupt facts remain explicitly unavailable; never silently replace them with a sample. Keep summary opening within the existing report-window limits; use its paging/streaming/save mechanisms for exact evidence rather than an all-or-nothing multi-megabyte clipboard string. A storage-specific report projection is sufficient; no general report framework rewrite.

A live report reads only the last fully flushed prefix. The writer publishes `(journal identity, durable sequence, byte endpoint)` as one immutable atomic snapshot **after** flush completes. Capture must not take the writer lock, which may be held in Flush(true). A reader may show current in-memory counters separately as **Live observations at [time]** and the exact calls **Recorded through [sequence]**. An in-flight intent in an active prefix is pending, not a completed uncertain failure. Use the independent evidence envelope from §6.2; a paused worker or blocked later flush must not prevent reading the prior published prefix. Active journals cannot be acknowledged or pruned.

Before acknowledgment explain: **The reviewed summary will remain. Detailed call records may later be removed under the retention policy.** Offer **Save call details…** through the existing save flow before acknowledging; it streams exact retained evidence and is cancellable. Export is optional, not a new mandatory recovery step. Previously authorized output or partial report-export files follow existing owned-output cleanup/reporting rules. Do not call sampled no-call examples a complete per-item log.

### 6.5 Durable records and recovery

#### 6.5.1 Records, counters and retry progress

Add versioned `storage-transform` metadata and per-call intent/result records to `JobJournal`, preserving old named-kind parsing. Every admitted native mutation has exact action/root/scope, review reference, path, held volume/file identity, before state, intended postcondition and observed result; E may later add invoking SID/nonsecret key identifiers. No file bytes, keys, passwords, PFX content or recovery secrets. Flush intent before call admission, then flush the observed result before another mutation. An intent-persistence failure forbids the call. An intent followed by denied admission needs its matching NotAttempted result. Never truncate affected-object identity/path to fit a mutation record.

**No-call outcomes do not get one durable record per object.** AlreadySatisfied, pre-call exclusions and pre-call inspection/access failures use complete per-root/effect/reason counters plus bounded representative details. Keep at most **16 no-call detail samples per job**, each at most **2 KiB UTF-8**, marked as examples and visibly clipped when necessary. These samples are not the identifiers in exact native-call evidence. Do not send every exclusion through a retained JobIssue plus a journal append; update counters and a coalesced UI notification instead. Root/job summaries persist the counters; reports distinguish complete counts from sampled details. During a crash, the last durable summary is only a lower bound for no-call observations since that checkpoint; mark its completeness unknown. Do not invent missing observations.

This permits a fresh request to pass the previous job's already-satisfied prefix without spending its mutation-record budget again. It is not automatic continuation. A prefix that repeatedly **attempts and fails native mutations** can still exhaust the journal, and depth/visited limits still bound a scope. After those limits show §4.2's smaller-scope guidance, never promise that an identical retry always advances.

#### 6.5.2 One collector, two independent recovery states

Add a proposed bounded `StorageTransformJournalCollector`. Its interpretation is shared by live writer state/`NeedsRecovery`, `Finish`, `JournalRecovery.Scan`, **`IsInterrupted`**, **`TryClose`**, report loading, acknowledgment and quota/retention. Do not implement separate end-marker heuristics in those paths.

Track these axes separately:

| Axis | Meaning | What can change it |
|---|---|---|
| Pending call / EffectUncertain | Whether an intended call lacks a durable matching result, or its historical effect remains uncertain. | Exact matching resolved result closes a pending call. A durable Uncertain result records uncertainty; user acknowledgment does not turn it into known success or no change. |
| ReviewPending / Acknowledged | Whether the retained history still requires explicit review. | A clean validated terminal sequence needs no review. Otherwise only a durable acknowledgment bound to the exact inspected history clears ReviewPending. New/changed evidence invalidates an older acknowledgment. |

Set pending **before** attempting to persist intent. Clear that pending transition only after its matching resolved result is durable. Uncertain results, torn/missing/out-of-order records, unknown schema and result-flush faults retain ReviewPending. At most one native mutation may be in flight. Stop the whole job on uncertainty or result-persistence failure.

Current `JobJournal.Finish` appends `end` and removes the manifest; current `Scan`, `IsInterrupted` and generic `TryClose` have independent closure logic, primarily guarded for archives. The storage collector must prevent **all** of them from treating Failed/Canceled/end as proof of resolved effects. Generic `TryClose` must **refuse storage journals without writing**, including ones with a stray end. The live storage writer may finish only a collector-validated clean sequence. A failed outcome flush followed by otherwise successful `Finish(Failed)` must retain recovery on restart. `RequireRecovery` may latch faults but is not the typed state machine.

In `OperationCenterViewModel` and `MainViewModel.Interrupted`, storage rows use **Review storage changes** and **Acknowledge reviewed history**. Disable generic partial-file cleanup, ordinary close/mark-reviewed, rename completion, transfer continuation and Undo for this kind. Do not show source/destination transfer guidance. Historical paths are evidence, never deletion/replay authority. Read-only current observations use fresh no-follow inspection under §6.2's ownership bounds. After restart the old pins are gone, so matching recorded path/ID is not proof of original continuity. Show intent, last result, current observation and historical uncertainty separately.

#### 6.5.3 Exact acknowledgment and retention

**Layering:** the typed storage acknowledgment schema, writer and verifier belong to **Core**, beside `JournalRecovery`/the storage collector. A proposed `StorageReviewAcknowledgment` contract and `JournalRecovery.AcknowledgeStorageReview` entry point are sufficient. Core must not depend on App's report classes. Extend `src/FileCat.App/Services/RecoveryReviewStore.cs` for the retained report UI, adding typed storage facts rather than treating its `ClosureConfirmed` boolean as filesystem certainty.

The acknowledgment binds journal/job ID, record schema/last validated sequence where readable, **exact byte length and SHA-256 of the reviewed journal snapshot**, the **exact retained report identity/length/digest**, and the explicit review choice. The report and acknowledgment together fit the 1 MiB retained budget in §6.5.4. Store only in the application's existing private evidence locations; a report reference is not authority to read/delete an arbitrary external path. Damaged/unknown histories retain that diagnosis; acknowledging them means acknowledging uncertainty, not validating missing records.

Acquire the existing journal writer-exclusion/ownership protection, verify no live owner, and recheck the exact snapshot immediately before acknowledgment. App first writes and flushes the bounded report through the storage-specific save path; Core then validates that actual report and durably publishes the matching acknowledgment. Keep journal ownership through both steps. Only the validated pair can clear ReviewPending or make evidence prune-eligible. Failure leaves pending review and its reservation intact. A changed digest/length/sequence, missing report, missing acknowledgment or active writer requires fresh review. A plain end or stale UI click is not acknowledgment. Do not append to or silently repair damaged call evidence.

**Report immutability:** once a durable acknowledgment binds its digest, do not rewrite that storage report. The existing generic interrupted workflow saves `ClosureConfirmed=false`, closes recovery, then overwrites with `ClosureConfirmed=true`; **storage must not use that sequence**. Derive displayed acknowledgment status from Core's validated acknowledgment. A deliberately revised report needs a new snapshot review and new acknowledgment of its digest.

**Durable retention dependency:** ordinary `RecoveryReviewStore.Prune` must not delete a report while a retained storage journal depends on it. This dependency is reconstructed from the Core acknowledgment/journal association after restart and respected across instances; it is not only an in-memory pin. An active/in-progress storage report write is also protected by the held journal ownership. A missing/stale pair makes the journal pending again, never silently finished.

Prune eligibility is explicit: **no live owner**, a verified exact evidence snapshot, and either a clean terminal sequence or a durable acknowledgment covering that journal and its retained report. Acknowledged uncertain history may become eligible under the storage byte budget and existing age/count policy; its report still says the effect was uncertain. Prune the eligible **journal first** while holding the same ownership/exact-snapshot checks. Only after successful journal removal may that dependency be released and the retained report follow ordinary report retention. If journal deletion fails, keep its acknowledgment/report protected. Clean journals need no fabricated acknowledgment. Unacknowledged pending history and another process's active evidence are never automatically pruned. This permits capacity reclamation without falsely declaring the filesystem effect resolved.

**Crash-orphan temporaries:** the storage-specific save path names temporary report/ack files with a validated job ID plus unpredictable nonce in the private evidence directory, so partial serialization still has a bounded job association. Include these files in the streaming census/byte accounting. Before another save or journal pruning, hold the same journal ownership and reconcile its associated temporary files. Remove only an exact private artifact established as unreferenced by a validated acknowledgment and not part of an active write. Never use historical user-file paths as cleanup targets. Failed deletion retains its byte charge and an issue. Unknown/unprovable artifacts are retained and reported; they are not assumed free. A crash after partial write, flush, report publication or acknowledgment publication must not leave an unbounded new temporary on each retry. All writers retain journal ownership until publication/cleanup; identifiers are not reused. Existing valid bound reports are preserved. This is bounded housekeeping within the existing report save path, not a generic user-file cleanup action.

|---|---|

Do not silently omit roots or rely on the generic 4 MiB line allowance. |

Disk-full can still defeat a reserved write; it produces recovery-pending history, not an assumed unchanged result. |

No-call root summaries are bounded by selected roots, never descendant count. Completed accounting may only be checkpointed once per root; defer it until conservative overlap/churn accounting is final. The fixed allowance prevents summary writes from consuming the current job's capacity reserved for a subsequent mutation. A huge already-satisfied prefix therefore does not create per-object durable writes. Normal mutation cost remains two durable flushes; N-C3 measures that cost without weakening durability through implicit batching.

This remains within the existing job-file namespace. Exclude these candidates from legacy eager Scan **before** materialization and route them to the storage collector/discovery path. Do not retain legacy deletion of headerless storage candidates or silently hide oversized/unreadable ones.

Enumerate incrementally with the dedicated one-slot cursor. Each startup discovery slice examines at most **64 candidates or 1 MiB of header/summary bytes**, whichever comes first; per-record limits still apply. Publish a first page without completing/sorting the whole directory. Retain at most **64 storage row descriptors**, each bounded to 4 KiB of summary/display metadata; exact paths/roots remain in evidence and are loaded on demand. Expose **More storage history** and **History accounting/verification still in progress** rather than silently omitting candidates. A page is not an acknowledgment or deletion limit. Continuation uses bounded sequential/re-enumeration state, not a full candidate array; exact global newest-first order is not a startup promise. Keep the selected review stable by journal identity while discovery continues; its retained descriptor counts within the 64-row limit.

Run the full accounting census and sequence verification cancellably off the UI thread. Admission stays unavailable while the census is incomplete or over budget. History may change across instances: mark changed observations dirty and recheck before admission; this remains the explicitly process-local observed quota, not a cross-process disk guarantee. Use the three-slot evidence envelope for bounded per-journal reads, releasing it between slices/interactive operations. Never block the cursor on user input or hold the evidence envelope while waiting for native observation.

Initially label candidates Review pending; no summary/end marker permits hide/prune before verification. Unknown/oversized/damaged history stays visible through bounded diagnostics; explicit review may stream/hash that exact file with cancellation, never ReadAll/native replay. Report failed current observations. This extends storage discovery/merging in MainWindow and OperationCenter; it does not demand a redesign of unrelated recovery kinds.

**Restart accounting:** before admitting a new transform, reconstruct a **2 MiB review-write reservation for every existing storage history that is ReviewPending or not yet fully verified**. Charge its physical evidence and reserved remaining capacity once, without double-counting existing report/temporary bytes. Release or reduce the review reservation only after verified clean closure or durable acknowledgment. If inherited or concurrent evidence already exceeds the process allowance, refuse new transforms and preserve that evidence. Permit read-only review and acknowledgment using available disk capacity, but do not claim guaranteed headroom for histories admitted outside this accounting policy. Do not solve an over-budget restart by auto-pruning unreviewed history.

The 256 MiB admission/accounting policy is **per FileCat process**, rechecking observed evidence before admission; it is not a coordinated machine-wide quota. Other instances can add evidence concurrently. Their active ownership is respected, and their files are not pruned for capacity. Test concurrent-instance visibility and disk-full faults. The per-journal cap is independently enforceable. `RecoverableTransferIntent` remains Copy/Move-only; any continuation or inverse is a newly reviewed request with fresh pins and preconditions.

## 7. EFS release gates

EFS is deferred. The following is a conditional design, not authorization to implement the rejected native recipe. Activation requires a replacement **E-ID** protocol, a truthful **E-KEY** workflow, and every **E-OUT1–15** route below to be Passed or explicitly Not applicable to the actual shipped route. Planned refusals count as complete only when integrated and verified before the first affected byte artifact. Compression does not depend on these gates.

### 7.1 E-KEY: first use, association, and backup

Availability must not provision keys, enroll, change policy/default keys, prompt a provider, or create a setup file. It can show **Current encryption key not yet established**. The repository supplies no verified current-default-key getter; do not invent `GetUserDefaultFileEncryptionKey` or call a setter as a probe. Reuse `WindowsFileRecords.Efs` only for its actual file-associated inspection; the new setup/key workflow below remains conditional and separately qualified.

Trigger setup lazily immediately before the first actual encryption change, including an unencrypted descendant reached beneath an already-encrypted root. Do not prescan the subtree or require setup for an entirely already-encrypted traversal. If no current reviewed recovery choice exists, enter AwaitingDecision before that item's native call, offer setup/recovery, then reacquire/revalidate the same candidate and resume the captured job. Retain its lifetime pin (including a descendant's scratch pin), root pins and global job reservation while waiting. Releasing a mutation guard does not authorize releasing the lifetime pin; captured-path binding must be checked again. Cancel preserves prior changes and performs no new user-data encryption. The explicit setup/recovery phase is:

1. Show the intended invoking account and the setup wording in §4.2. Suballocate setup handles from the active worker's already-held transient allowance; never reacquire that allowance while awaiting setup. Create one unpredictable `CREATE_NEW` **zero-byte** setup file with `FILE_ATTRIBUTE_ENCRYPTED` under a verified private local NTFS application directory; no user content is written. Windows may create/enroll a key here, only after this explicit action. If this workspace cannot be safely created, stop setup with a reason. N-KEY must qualify this zero-byte setup path before enablement.
2. Verify setup file EFS state and query its actual user certificate hashes. Match exact hashes in `CurrentUser\My`. Never pick an arbitrary EFS-EKU certificate, substitute a recovery agent, set a new default, or rekey. Existing encrypted selections use their actual per-file associations; a folder's certificate list is not proof about all future children.
3. Distinguish certificate present, private-key association, private-key access now, actual data decryptability, and backup evidence. A bounded silent/no-healing `CryptAcquireCertificatePrivateKey` check supporting CAPI/CNG must also establish that the acquired key belongs to the exact observed certificate. Request **CRYPT_ACQUIRE_COMPARE_KEY_FLAG**, **CRYPT_ACQUIRE_NO_HEALING**, **CRYPT_ACQUIRE_SILENT_FLAG** and **CRYPT_ACQUIRE_ALLOW_NCRYPT_KEY_FLAG**; do not request CACHE or USE_PROV_INFO caching. A cached/ambiguous result cannot count as a completed key comparison. Mismatch or unresolved comparison is unavailable/unknown and blocks new encryption, including a managed-recovery declaration path. Honor the returned ownership/key-spec for CAPI versus CNG release. Acquisition success alone is not evidence of file decryptability or backup recovery. The result can be available, interaction required, unavailable or unknown; silent failure is not proof the key does not exist. Explicit parented hardware/provider interaction belongs only to setup/backup; qualify the parent-window interaction mode without SILENT, retaining fresh key-comparison/no-healing semantics.
4. **Back up EFS key…** offers each relevant accessible certificate, identified by account/subject/thumbprint. Launch parented `CryptUIWizExport` with certificate context and proposed private-key-export flag `0x0100` plus disable-key-deletion flag `0x0200`. Do not use no-UI export or handle passwords in arguments/logs. Public-certificate-only export does not satisfy this route. Beside both first-use and existing-key backup actions say **Keep the backup somewhere you can access without this Windows account or EFS key, and keep its password separately.** FileCat does not read the backup file or handle its password.
5. Continue after **Windows reported private-key export completed** (native gate must verify the exact result behavior) or an explicit **I have an existing backup or an organization/hardware recovery arrangement** declaration. Label the latter **Recovery arrangement acknowledged; not verified by FileCat**. Non-exportable/hardware keys are not forced into PFX backup. List why export is unavailable and permit the declared recovery route; without a declared usable arrangement, do not encrypt user data.
6. Failed/canceled export means setup is unfinished. Offer retry, the explicit existing/managed recovery route, or Cancel. Do not silently continue. Cancel makes no further changes to selected items; any earlier job changes remain. It deletes only the verified owned zero-byte setup file and leaves any Windows-created key/certificate intact. Cleanup failure retains a named zero-byte artifact with a cleanup issue, not a reason to delete certificates.
7. After each actual encryption, inspect the resulting user certificate hashes and applicable current-user key access with the same fresh certificate-to-key comparison. A new/unexpected or unresolved relevant association stops the job with a review-required result; the current item may already be encrypted. Do not immediately continue from a new declaration in the same job. Retain its evidence and offer backup/recovery review; remaining work requires a fresh request. Checkpoint consent against the same invoking identity; never treat another account as equivalent. No automatic rekey or inverse on cancellation.

**Limit of setup evidence:** the zero-byte file establishes an observed certificate association, not the key Windows will use for the next file. `EncryptFileW` has no expected-certificate parameter, and the current key can be changed independently. A successful export of A therefore cannot promise that a later item uses A rather than B. Before approval, say **Windows chooses the encryption key when each file is encrypted. If that key changes, the current file may already be encrypted before FileCat stops for another recovery review.** This conditional design promises a recovery choice for the observed setup key and post-call association verification, not that every eventual key was backed up before mutation. If the stronger pre-mutation guarantee is required, E-KEY stays blocked until a supported key-binding mechanism exists. A test switching the current key between setup and mutation must exercise this precise limit in a disposable identity.

A recovery declaration replaces the PFX-backup requirement only; it does not replace actual certificate association and usable current-user private-key access for new encryption. Resolve hardware interaction only in explicit setup. If key access or association remains unresolved, stop new encryption; existing encrypted no-ops and decryption retain their separate policies.

For existing EFS files, an explicit backup action enumerates only the selected files' relevant certificates, with bounded counts. Multiple certificates may require separate exports; do not mark an entire selection covered because one wizard completed. Coverage means an applicable current-user recovery choice for each affected file, not possession/export of every other recipient's or recovery agent's private key. Already-encrypted no-ops do not rekey or demand setup. Decryption does not provision/export a key: it requires reviewed protection removal and whatever key access Windows actually needs. Found public certificates/recovery agents do not prove decryptability or recoverability. A real recoverability claim would require controlled restore/decrypt verification; FileCat does not make that claim.

### 7.2 E-ID: path-based mutation feasibility

### 7.3 E-OUT: finite output/preservation inventory

Authorized ordinary EFS reads return decrypted content; raw encrypted backup uses separate APIs. A new stream, restrictive ACL, TLS/SFTP session, metadata flag copy, or DeleteOnClose does not by itself establish EFS protection at rest. This is a reason to inspect destination creation, not proof that every execution leaked: an encrypted parent or another verified protocol may protect a particular output.

**Enforceable admission, not a cached path boolean:** add a small output-admission contract only to the concrete routes below. Proposed `OutputAdmissionReceipt` contains protection class **EfsDerived / ObservedClear / Unknown / NotApplicable**, contributing opened-source identities/revisions, route/job, destination and intermediate-output policy, and the exact loss consent if any. `Unknown` is never clear. `IContentSource`/`MemoryContentSource` currently have no such provenance (`src/FileCat.Core/Resources/ContentSource.cs:9–24`); the archive path/owner lease alone is not that proof. Derived memory/temporary content retains EFS provenance even after its backing path is renamed, decrypted or replaced.

Bind observation to the **actual opened input** before any payload output, retain the qualifying source ownership while reading/writing, and re-admit on every reopen, retry, new source or newly discovered backing volume. Length/mtime equality is insufficient. In SFTP the metadata/open gap and retry reopen (`SftpJobs.cs:443–457,792–826`) require checks on the actual new stream before remote writes. An output receipt is not itself a native lock: each adapter must establish its validity for the read interval or refuse persistence. Post-output detection is too late. If provider `OpenContent` can itself create a spool, pass admission into that creation path or refuse **before** opening; a check only at the final copy loop misses the artifact.

Provenance is the union of **all actual contributing inputs**: nested parents, multipart volumes, retained sources, and imported patch bytes. ### 10.4 Remaining risks and bounded decisions

- **EFS identity/conflict feasibility is the primary unresolved blocker.** The previous candidate is disproved for its promised invariant. A supported replacement argument must precede a bounded experiment; no argument means defer, not repeated stress testing or a weaker hidden fallback.
- **Compression native fidelity and scope guards remain unrun.** Documented API behavior is not FileCat acceptance. The 30 GB enable boundary is intentionally conservative; differences on current Windows are recorded and reviewed before widening it.
- **Compression stream scope must remain visible.** Main-data compression and alternate-stream state are separate. Do not advertise removal of every stream's compression or let a clear C flag bypass the EFS all-stream conflict gate.
- **EFS recovery is not provable by acknowledgment or a setup canary.** Export completion, declared arrangements and the actual later encryption key are distinct. The current item can already be changed when a key mismatch is detected.
- **Dynamic trees and aliases are not snapshots.** Lifetime pins prevent root ID reuse; they do not freeze names. Closed descendant IDs cannot certify later discoveries. Bounds/churn/exclusions leave incomplete outcomes, with no universal anti-alias promise.
- **Safety has a concurrency/performance cost.** Global job serialization and two durable flushes per mutation are deliberate first-release constraints. Measure them before release; refine only with a separately justified correctness protocol.
- **Plaintext output gate is finite but crosses several backends.** Refusals are acceptable first-release solutions. An unresolved route must be disabled for EFS input before activation, not buried in future work.
- **Unsupported-location expansion is optional.** SMB, detected cloud, reparse formats, multiple hard links, system/drive roots, sparse compression and elevated compression each need a separate scoped proposal. No broad new platform abstraction.
