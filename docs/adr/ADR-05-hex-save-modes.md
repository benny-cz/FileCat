# ADR-05 — P4b fixed-length hex save modes

**Decision.** Windows local files open through the link object itself (a link is refused) with a read/write handle that denies ordinary write and delete sharing for the entire edit session. A sparse overlay allows only fixed-length replacements, with an 8 MiB touched-byte and 32 MiB undo-data budget. The existing-file save mode is explicit journaled in-place writing: a user-local, checksummed record of original and replacement ranges is flushed before the first target write. Each range and the target are flushed, a progress record follows each range, and read-back verifies the result. Once the journal is durable, any failure keeps it: the editor that still holds the protected handle offers Finish saving or Restore original bytes at once, and Tools → Recover interrupted hex save handles journals left by a crash. Recovery proceeds only when the full 128-bit file ID, volume ID, length, and each current byte match a journaled state; a journal whose target was replaced or changed can only be discarded. Save As creates a new file (sparse holes and Mark-of-the-Web kept where the destination supports them), and patch export records exact ranges that Apply patch can later stage after checking every expected original byte.

**Why.** The protected baseline excludes ordinary concurrent writers from the start of editing. In-place writes preserve file identity, hard-link aliases, ACLs, alternate streams, and allocation semantics. A sibling replacement could be more atomic for small files, but its identity, hard-link, sparse, stream, and security effects need an independently validated preservation policy. It is deferred rather than exposed with an implied guarantee. Network paths and file links are refused because the exclusion does not hold for other machines, and a link could retarget the edit.

**Linux and macOS (D-45, 2026-09-29).** Their locks are advisory, so no handle can keep other writers out. The editor checks the path's own entry before and after opening (a link, even one swapped in meanwhile, is refused by device-and-inode identity), shares reading and writing, and every save first verifies that the path still names that file, that its length is unchanged, and that each byte it replaces still holds the original value, saving nothing otherwise. The journal records device and inode as the identity, flushes use F_FULLFSYNC on macOS, Save As keeps the origin extended attributes and writes sparse holes as zeros, and the save confirmation states that a program writing the same bytes during the save itself could still be overwritten.

**Limits.** A sequence of range writes is not atomic or power-loss-proof. Raw-device writers can bypass sharing. Save As may use substantial time and space and creates a new file without the source's ACLs or other alternate streams; it reports a lost download mark. The editor does not insert or remove bytes. Recovery refuses an unrecognized target or unrelated byte change and keeps the journal. Original bytes in recovery records live under the user's local application-data directory, including in portable mode.

**Evidence.** Automated tests cover multi-terabyte synthetic offsets, range overlap and undo/redo, change events and in-place page patching (no stale page after a racing load), write-sharing denial, refusal of empty, read-only, busy, and linked files, new-file Save As including a 1 GiB sparse file with Mark-of-the-Web, patch export/apply, journal interruption before and after writes with per-range inspection, in-editor rollback and resave, guarded resume/rollback, unrelated-byte rejection, discarding, corrupt journals, and a headless editor that types in both columns, undoes, saves, and holds exit while dirty. TV-04's mapped-file, disk-full, process-kill, and hardware checks remain external release gates.
