# I616 — local Copy must not fill sparse-file holes

**Status:** Remediated preliminarily at product `f269f97f67a83fbc464dbf6b86ed93636e924232`, with a Windows EOF-range refinement at `3f5b472c1b1167cfff2b2188721790e563cd5e7e`; both exact-source five-lane CI runs passed. **Severity:** Medium: identical file bytes can still consume thousands of times more space than the source and fail on a volume that has room for the allocated data but not the logical length. The frozen installed candidate remains open. Public preview.5 predates this correction; stable 1.0.0 remains NO-GO.

## Distinct journey and before result

Cycle 39 sampled a user copying a large, mostly empty forensic or VM-image-like file, after read-only NTFS/APFS sparse inspection had already been accepted. This is a Copy/storage consequence, not another metadata report. On disposable Ubuntu 24.04.5 ext4, an owned `sparse.bin` had a 32 MiB logical length, two 4 KiB written regions, `stat` allocation **16 × 512 = 8,192 bytes**, and SHA-256 `ccb8fb7e63f3c8f9a7f0288a4b2b5bf7d790ce504641e35bbdfa014358c1edcc`. The native FileCat F5 review named that file and the empty owned target. Copy reported Completed and the bytes matched, but the target had **65,536 × 512 = 33,554,432 allocated bytes**. A full or near-full destination could therefore fail despite the source fitting. A separate owned 16 MiB NTFS source on the physical Windows workstation had two 64 KiB allocated ranges; the old portable Copy produced a non-sparse, fully allocated target. No physical desktop was controlled.

## Correction and scoped verification

FileCat now asks the source filesystem for data extents before copying a large local sparse file. Linux/macOS use `SEEK_DATA`/`SEEK_HOLE`; Windows uses `FSCTL_QUERY_ALLOCATED_RANGES` and marks the new destination sparse before setting its length. Only reported data extents are read/written; holes retain their logical zero bytes without full allocation. When the filesystem does not support extent reporting or a sparse destination, the existing sequential copy is used before any data are written. A malformed or mid-copy extent failure fails the copy and removes only its newly created destination. Normal source links, content, metadata and conflict review retain their existing paths. Logical progress still reaches the file's full length, including skipped holes; it is not a measurement of physical bytes written.

At exact `f269f97f`, the isolated Ubuntu native GUI App DLL SHA-256 was `01f300798622f8cfc560d0cdff5ba175e854539a1623b70141fb32b387407ad5`; Core DLL SHA-256 was `ef55d5894067699183fff97ce224c80a42a46513a72500fe487a44c475d3bb04`. F5 review again named the 32 MiB source and owned target; after Copy, both panels showed the file and Operations reported Completed. Independent `stat` returned source and target `33554432 16 512`, so each occupied **8 KiB**. Independent SHA-256 matched the exact baseline value on both paths. The ignored local review/result screenshots `.tmp/cycle39-review.png` and `.tmp/cycle39-after.png` belong to the intermediate corrected Unix build before the final Windows-path refactor; their SHA-256 values are `38D5F0DC8BF8849C104985004FAB04755621E5D039DC28513C746EBCE2DF7EF5` and `9BAEB4E2049E0162F21E28EB9528DC884923DA06862BD4FAF47987AACDD11776`. The final-source GUI check is supported by its native accessibility output and independent `stat`/hash receipt.

Focused Ubuntu Core tests passed **4/4**: data extents and all-hole files, each with and without preallocation. On the NTFS workstation, a low-load background Core harness copied both the two-range and all-hole 16 MiB sources with and without preallocation: four byte-identical, sparse targets. `fsutil sparse queryrange` showed the two expected `0x10000` ranges at offsets `0` and `0x800000` for the data source, and no allocated range for the all-hole targets. The Windows Core test project compiled with zero warnings/errors and contains four matching hosted regression rows. The physical workstation VSTest process could not connect to its data collector within 90 seconds; this is **not** counted as a test pass. The disposable Mac APFS test source consumed all 16 MiB immediately after length extension, so Mac Core Copy confirmed byte/length correctness for both copy modes but did **not** qualify sparse allocation preservation on that volume. The Ubuntu fixture, builds and scripts, Windows owned fixture and Mac harness were removed under exact path and hash guards after the checks. Unsupported filesystems and remote protocols are outside this local-copy result.

The Windows API permits allocation-boundary rounding, so `3f5b472c` clamps a reported end to the source's logical EOF before reading. A fifth hosted Windows regression row covers an unaligned 16 MiB + 1-byte sparse source whose only allocated byte is the last byte. In a separate owned NTFS background harness on the physical workstation, that source and its copied target had equal SHA-256 `AEF064BBBFB7C98946A424AB14CBEA3A4534B7F9D571CE5BE5507678BFB17012`, length `16,777,217`, last byte `0x5A`, sparse attribute, and `fsutil` range `Offset: 0x1000000 Length: 0x1`. This particular NTFS response was not rounded beyond EOF, so the local check proves the boundary copy, while the clamp itself is a defensive response to the documented rounding allowance. The exact owned fixture was removed after path, length and hash checks. The Core and test projects compiled with zero warnings/errors; hosted test execution remains to be reconciled.

The implementation follows the Linux [`lseek(2)` extent semantics](https://man7.org/linux/man-pages/man2/lseek.2.html) and Microsoft's [`FSCTL_QUERY_ALLOCATED_RANGES`](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ni-winioctl-fsctl_query_allocated_ranges), [`FSCTL_SET_SPARSE`](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ni-winioctl-fsctl_set_sparse), and [`GetCompressedFileSizeW`](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getcompressedfilesizew) documentation. These sources describe reported allocation ranges and sparse size, not a promise that every filesystem preserves exact physical layout.

## Finite candidate acceptance and stop

On the frozen installed 1.0.0 candidate, copy one owned sparse file with a data region and trailing hole on NTFS and ext4 using the native review, plus one all-hole file through the focused test. Require exact logical length and SHA-256, allocated size less than one-quarter of the logical length where the source filesystem itself remains sparse, a Completed report only for the exact successful target, and no leftover target on an injected extent-read failure. Reconcile the five latest-source CI lanes and tag-only skips. On macOS, qualify allocation only on a volume that independently creates a sparse source; otherwise record the filesystem limit and verify bytes/length. Stop at these boundaries rather than replaying accepted read-only sparse reports or all copy-provider combinations.
