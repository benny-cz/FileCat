# E-I522 — keep manual scroll position during a partial directory refresh

The user found that manually dragging the list scrollbar in a frequently changing folder such as `C:\Windows\Temp` could snap the view back toward the selected row. The listing already tried to preserve a requested top row, but after its 400 ms refresh delay it could replace hundreds of displayed rows with a very short *partial* result. The UI then had to clamp its scrollbar to the partial row count. Repeated filesystem notifications could keep redoing that clamp, even when the user was actively scrolling.

At pushed commit `b6169a1744eaeb39c35f420fdbf1d7c1614ce89d`, `ListingModel` keeps the prior complete rows visible and interactive until a refresh has at least as many visible rows as the old view, or until the refresh finishes with a genuinely shorter result. Its existing 400 ms delay still applies. A final shorter directory is shown normally, and explicit cursor movement still brings the focused item into view.

A new gated Core regression starts with 200 rows and a focus at row 180, then holds a refresh after only one new row past the old 400 ms swap delay. It verifies that the old 200-row view and focus remain available until release, then verifies the 201-row final result and focused identity. The existing streaming-refresh test still passes when enough rows arrive. Focused Core: **2P/0F**. The existing headless App scrollbar/resize/focus test and the three focused I521 App cases pass **4P/0F**. Full Core on this source passes **4,155P/142S/0F**, full headless App **1,656P/44S/0F**, and the production App Release build has zero warnings or errors.

The disposable Windows 11 VMware guest then ran an exact-source private win-x64 publish at `b6169a17` (ZIP SHA-256 `2744321e4884c61dcdeeea5d985fcde8421a81c8229911eb2f3fc2d868947133`; Core DLL `44101791bb32257de4dfd947c746a64358a4df9a5ba77a551bb8898ccf5aed3f`). FileCat ran in Admin's **ordinary** interactive session 1 with isolated state and a 2,000-file owned directory. While 250 create/delete pulses changed that directory over 32.7 seconds, a physical mouse drag moved the left scrollbar's UI Automation value from **0 to 1,182**. It remained **1,182** seven seconds later while notifications continued and after churn ended. Screenshots show row `item-01181` at the top of the viewport while the focused row remains offscreen, then the same view after the directory returns to exactly 2,000 files. The native interaction did not reproduce the snap on the corrected source; it does not provide a paired old-binary failure.

The private test app exited, six temporary interactive scheduled tasks were removed, and the owned file fixture, app payload and temporary Desktop scripts/receipts were removed from the guest. Private archive `V:\FileCat\artifacts\release-evidence\i522-scroll-windows-native-20261016-v1` holds the exact payload, source patch, four TRX files, full/focused logs, screenshots, UI Automation values, churn input/receipt and cleanup. **Disposition:** Medium UI defect remediated preliminarily. The gated test covers the partial-refresh mechanism, and the VM confirms drag/refresh behavior on this commit. A paired old-binary native failure, the exact user's folder and release-candidate package remain untested.
