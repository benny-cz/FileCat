# I564 — Markdown Page keyboard focus on Windows

The owner reported that Page Up and Page Down did not scroll an opened Markdown file. In the installed Windows FileCat viewer, an actual Page Down key left the rendered `README.md` at the same heading and scrollbar position. That is a native baseline observation, not a post-fix pass; the installed executable's exact source was not established.

Source review found two ways the initial focus request was lost. `PageView.FocusPage()` did not retain a Windows request made before its native engine existed, and `WebView2Page.Focus()` did nothing until its asynchronously created controller existed. Windows also did not replay page focus when the viewer was reactivated. The correction at `e2c4043667186029734fd93f4ad1cc0284b2806b` added retention and replay of that request, cancellation when another viewer control takes focus, and an activation replay path. It did not intercept Page Up or Page Down; WebView2 scrolled them normally when focused. The later VM check below showed that activation replay alone was insufficient when the viewer root held focus.

The focused App tests pass **8/8** with a new late-engine and focus-cancellation control. The native Windows WebView2 `PageViewTests` pass **8/8**. The App and Platform Windows test projects build with zero warnings and errors. An isolated rebuilt source instance was then launched on the Windows desktop with `--new-instance` and its own temporary data root. Its actual `README.md` Page viewer scrolled about one viewport on Page Down and returned to the top on Page Up. This is a post-fix native input pass for the source build, not for a packaged release candidate. The isolated viewer and app instances were closed and their temporary state removed. The local `dotnet test` VSTest adapter timed out before connecting to its test host; the same built xUnit v3 test executable ran the focused cases directly.

A local portable ZIP built at `aca939f4` was copied into it; guest and host SHA-256 both matched `4c024bb301475c67bf55ea5c5e9b7af0959a9259d6fa365e8a1871b963d663eb`, and the extracted executable reported `FileCat 1.0.0-preview.3`. Its rendered 100-section `paging.md` exposed a remaining focus case. Clicking inside the native page moved focus to `Chrome_WidgetWin_1`, after which Page Down scrolled. A later Page Up after reactivation again left the page in place. That native result is the documented consequential reason to reopen I564 and the source gate after the earlier source-viewer pass.

## Follow-up correction and verification

At `a5e4925cea9dc35f4e55a6af5a2fff3eec6ba586`, the Windows page host distinguishes a hidden Text surface or window root taking focus from a visible Find or toolbar control taking focus. It replays initial focus once the page loads, tracks the WebView2 controller's actual GotFocus/LostFocus events, and handles Page Up/Down received by the viewer root while the native page lacks focus. That fallback scrolls the already rendered page through WebView2's host-controlled `ExecuteScriptAsync`; page-authored scripts remain disabled. Visible Find and toolbar controls retain their keyboard focus. The focused App suite passes **9/9**, including root-owned Page keys and visible Find/native-focus guards. The native Windows WebView2 `PageViewTests` pass **8/8**; both test projects and the App build have zero warnings and errors.

The exact committed source produced a **clean local preflight**, not an official hosted asset: `FileCat-1.0.0-preview.3-win-x64-portable.zip`, **102,331,918 bytes**, SHA-256 `13838a2a3ab1d318cac2b7ac522812a8cdaaf9bd7c22a1a661afd9a71242625d`.
