# I380 — avoid quadratic sidecar-claim indexing

2026-10-12 CEST. **High I06/V15 resource issue, preliminarily corrected on owned inputs.** A `SHA256SUMS` file under FileCat's 4 MiB per-sidecar limit may contain tens of thousands of claims for the same file. `FolderSidecars.Scan` appended each parsed claim only after searching the growing list with `List.Contains`; coverage names used the same pattern. Every claim has a distinct source/line position, so searching all prior claims did not remove a duplicate in this case. It made a valid manifest increasingly expensive to scan.

An isolated no-package probe against the exact `9800178` Release Core DLL SHA-256 `0c9e355a6506c93bd457c94abd3f00645f66e40a99a4624b86057c37f6f612ce` wrote an owned file and 16,000/32,000/48,000 correct checksum lines, then deleted the root. The manifests were 1,200,000/2,400,000/3,600,000 bytes, each below the 4 MiB sidecar limit. Scans retained every claim but took **1,501/4,969/13,290 ms**. The final corrected build of the same probe retained the same counts and took **99/134/236 ms** (about 56× faster at 48,000 claims). Its Core DLL SHA-256 is `ae71ba867ce34a4e9593e7aee3504c511870d598a704bd26b8110aded4461f82`. These are single-run Windows development-host timings, not a reference-machine performance claim; they demonstrate the specific pathological growth and its removal. An earlier corrected build with an eagerly allocated coverage hash set took 108/154/310 ms and remains in the private record; the final variant allocates that lookup only after sixteen distinct covered files.
