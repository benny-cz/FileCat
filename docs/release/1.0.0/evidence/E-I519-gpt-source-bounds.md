# E-I519 — bound damaged GPT locations before recovery reads

The GPT partition-table reader multiplied untrusted 64-bit sector numbers before checking them against the source length. On a 16 KiB owned source with a damaged GPT header, a sector number just above `long.MaxValue / 512` wrapped negative; the old parser called the source reader at that negative offset. A separate oversized partition-start sector wrapped into a negative volume offset, and an oversized final sector yielded a negative volume length. The first test fixture accidentally put the second case's end before its start and produced **1P/2F**; after correcting that fixture, the three cases on parent `db428662` fail **0P/3F**. Both raw TRX remain. The final test data uses a fixed nonempty partition-type GUID in place of the baseline's random nonempty GUID; this does not change the exercised bounds, but the compiled test assemblies are not byte-identical. No physical device or user data was opened.

The correction checks the entry table's complete byte range before multiplying its LBA; it rejects impossible partition starts and clips a partition end to the actual source. A fourth control checks a table that begins inside the image but extends beyond it. The four corrected malformed-input cases and an existing valid backup-GPT recovery case pass **5P/0F** together. The complete Core suite passes **4,154P/142 explicit skips/0F**, complete headless App **1,654P/44S/0F**, and the final production App build has zero warnings and errors.

It was sealed at 18 files, then amended to include the final build log and matching seal script; the final manifest was independently rehashed against all **31,235,516** retained bytes.
