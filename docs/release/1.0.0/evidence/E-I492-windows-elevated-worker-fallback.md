# E-I492 — elevated token must not enter the ordinary Windows worker fallback

At exact parent `6855fd094cbf0255a340b0179c9e5bd5bca9bae9`, `RestrictedProcess.CanUseFallbackToken` checked only the token's integrity level. In the disposable Windows 11 VM, a full administrator token remained **elevated** after its duplicate was lowered to medium (and, separately, low/untrusted) integrity. The old check returned **true**, so a failed low-integrity worker start could select the ordinary process-creation fallback with that still-privileged token. This is a demonstrated eligibility gap within I08; the test did not force an actual low-integrity start failure or execute third-party code through the fallback.

The correction queries [`TokenElevation`](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-token_elevation) on the exact token before considering the integrity level. Missing/malformed elevation data or an elevated token refuses the ordinary fallback. The existing low-integrity attempt and job restrictions remain. The same compiled Windows Platform test assembly (SHA-256 `763680ce1862eadcf1c05e2db0de559afbc52cede954d1d87ead5fe9d33b45f8`) runs against parent/final packages of 47 members each; **only `FileCat.Platform.Windows.dll` differs**. The old DLL SHA-256 is `cca4b9076d388e5ad2499a78b2245be0c66aa33dbe4076b832ce7735797499a6`; the corrected DLL is `3acdb05a2c03f86e56aba9ea3dbcb1ff2188cd5fcf647675f1a69f2cb6c72434`. Four elevated-token cases change from failure to pass: **4P/4F → 8P/0F**. A separate exact-parent package also fails the same four assertions.
