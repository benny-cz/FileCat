# I376 — Windows case-sensitive directories fold verification identities

2026-10-12 CEST. **High verification-identity issue; remediated preliminarily in a declared local product/test overlay.** Windows supports a per-directory case-sensitive flag. The verification scanner used case-insensitive filename keys on every Windows directory, and the surrounding bounded folder cache used case-insensitive path keys. In a flagged NTFS directory, `item.bin` and `ITEM.bin` and their `.sha256` files can be four different files; sibling `source` and `SOURCE` directories can also differ. This extends the Unix folder and Mac filename findings [I374](E-I374-unix-verification-folder-identity.md) and [I375](E-I375-mac-case-sensitive-sidecars.md) to Windows without changing their original results.

The authorized Windows 11 VMware guest reported Windows build `10.0.26300.0`, NTFS and an elevated Admin token. `fsutil file setCaseSensitiveInfo` enabled the flag on one **owned disposable directory**. A query confirmed it, and enumeration and actual bytes proved both case-distinct file names. A self-contained x64 probe built against exact pushed `adcdc330a721ac7b9f7e12e040b4a74e9278e47e` Core DLL `a9ea07022c63c4274d0fcf88b85664bbce5abdeee4e3b95ee2139280098c7c44` checked two distinct complete payloads and their separate matching SHA-256 sidecars. It also created two distinct child folders with equal directory timestamps, different checked payload bytes and matching sidecars. Both original actual payload hashes equaled their individual expected values, yet the upper file and second folder returned **`Differs`** while the lower ones returned `Matches`. The second folder scan reported the lower-case `source` path. The original probe exited **2**. This is a wrong verification result, not a source write or physical-device test.

The correction reads Windows `FILE_CASE_SENSITIVE_INFO` through `GetFileInformationByHandleEx` on an opened directory (`FileCaseSensitiveInfo` 23, `FILE_CS_FLAG_CASE_SENSITIVE_DIR` 1, `FILE_FLAG_BACKUP_SEMANTICS`), using the installed Windows SDK definitions. A flagged directory gets ordinal filename keys; an ordinary Windows directory retains case-insensitive aliases. If the flag cannot be read, exact names are kept conservatively. The bounded folder cache uses exact path keys so two distinct paths are never merged; different spellings of one ordinary Windows folder can occupy separate bounded entries and cause a conservative rescan. The same probe source rebuilt with the corrected Core returned `Matches` for both files and folders, selected uppercase `SOURCE` for the second scan, and exited **0**. Three ordinary-Windows regression cases preserve mixed-case bare, manifest and detached-signature bindings. The signature case checks claim binding, not cryptographic validity.

The owned guest probe removed its sidecars and child folders after each run. The cleanup script then checked the remaining two original payload names and SHA-256 values, removed the exact owned directory and staged probe files, and recorded `RootAbsent=true` and no staged files. Its first attempt stopped safely before deletion because the script assumed a particular filename sort order; the raw diagnostic remains. The corrected order-independent check passed.
