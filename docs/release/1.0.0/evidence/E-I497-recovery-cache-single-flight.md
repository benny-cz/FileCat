# E-I497 — concurrent recovery cache misses could return different source versions

2026-10-15, I106. Parent source `ec59732e` (its recovery cache is unchanged from the preceding product commits). This is a **controlled source-byte consistency defect** in `CachedSource`, found while checking the remaining I106 concurrent-source scope. It is not evidence that an actual physical scan returned wrong user data: the current `RecoveryScanner.Scan` call path uses the cache sequentially during a volume scan, and the failing source here is synthetic. No release candidate or stable GO follows.

## Same-test failure and correction

`CachedSource.Block` previously checked `_blocks` under a lock, released the lock to load a block, then tried to cache its result. Two readers could therefore miss the same block. The controlled `IBlockSource` holds its first full 16-byte read with bytes beginning `01 02 03 04`, then permits a second full read of the same offset with bytes beginning `05 06 07 08`. The same test on the original product fails **0P/1F**: it expected one source read for the shared block but observed **two**. The raw failure is the read-count assertion; the different input versions are specified by the retained test source, not claimed as a separately captured output mismatch. With a stable source the duplicate work usually returns the same bytes, which is why this requires the changing-source condition.

The correction registers one `Lazy<byte[]>` load per block under the cache lock, performs the device/image read outside that lock, and shares its value with all readers that arrived during the load. The completed value enters the existing bounded LRU cache; a failed load is removed so a later read can retry. Different block numbers still load independently. The corrected focused test passes **3P/0F**: same-block one-version/one-read, a different block completing while the first is held, and retry after a controlled read exception. The test uses dedicated reader threads, finite waits and explicit release in `finally`.

The complete headless Core suite passes **4,120P/142 explicit skips/0F** in 5m41s against the corrected recovery assembly. The final focused rebuild after test-cancellation cleanup again passes **3P/0F** without new analyzer warnings. The complete headless App suite passes **1,646P/43 explicit skips/0F** in 13m28s with `dotnet test tests/FileCat.App.Tests/FileCat.App.Tests.csproj -c Release --no-restore -p:MaxCpuCount=2 --logger "console;verbosity=quiet"`. Exact pushed-source CI is a separate follow-up; it must not be inferred from these local runs.
