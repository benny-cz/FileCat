# E-I487 — Windows drive-letter scans retain the selected backing interface

The Windows **drive-letter** recovery route selected a volume GUID, checked write safety, waited for confirmation or administrator access, then called `RecoveryProvider.ForDevice(device, name, 1)` without the selected backing identity. `SelectedDiskInterfaceSource.Bind` verified that an opened volume currently belonged to one disk, but it did not compare that disk with the one selected before the wait. A replacement disk could therefore take the same volume GUID or disk number while FileCat scanned its deleted items. The whole-disk route already captured a selected PnP interface; this was a separate omission in the mounted-volume route. The issue is potential deleted-data/source-confusion severity within I106. No physical-source testing was used to reproduce it.

The corrected route captures the selected single backing disk's PnP interface and storage identity **before** the confirmation. The volume reader reports that pair as its selection identity, and `RecoveryProvider` refuses a later mismatch before scanning. If either identity is unavailable, the drive-letter action now refuses before asking for approval. A pure Windows test distinguishes byte clones with the same storage GUID on different interfaces and requires an identity and interface. A separate native test binds the actual opened volume of an owned 128 MiB VHD to its current interface without reading source content.
