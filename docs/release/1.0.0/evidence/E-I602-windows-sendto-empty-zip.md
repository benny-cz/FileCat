# I602 — Windows Send to compressed folder created a zero-byte ZIP

## Consequence and cause

On 2026-11-01 the owner reported that **right-click → Send to → Compressed (zip) folder** created a zero-byte ZIP for selected files and folders. In a disposable Windows 11 Insider VM, the native action on owned `owned.txt` reproduced a zero-byte `owned.zip` at `c491e892`, even with `CMIC_MASK_NOASYNC`. The selected Shell target was `Compressed (zipped) Folder.ZFSendToTarget` (command 31, no canonical verb). Holding FileCat's isolated Shell helper alive for 30 seconds produced a readable ZIP instead. This control identifies an asynchronous Shell handler that can outlive the helper; the advisory flag alone was insufficient. The test did not use the owner's physical desktop.

## Correction and native checks

Product `498bbf1c9b05d0cdca98878951ae3fe898a7c3fb` recognizes only a matching installed `.ZFSendToTarget` Send to entry and routes its exact selection to FileCat's existing archive job. The job keeps sources alive through completion, verifies and atomically publishes the archive. A selected link is refused, and an occupied output name receives a numbered sibling instead of being overwritten. Other Shell verbs remain in the isolated helper.

The VM fixture used `C:\Users\admin\Desktop\filecat-i602\source`. `owned.txt` had 48 bytes and SHA-256 `9719F9125251D44767D4FDED68B4D38E0930B2E41078BB330743E6AA8B6BA672`. `folder\nested.bin` had 256 bytes and SHA-256 `40AFF2E9D2D8922E47AFD4648E6967497158785FBD1DA870E7110266BF944880`. On the corrected self-contained package, a native click created a 166-byte readable `owned.zip` (SHA-256 `30AAB63C83D5F30D84537B3D5A99EAADC34D5AA722B6FCE28547825C27005B8B`) containing exactly `owned.txt`, 48 bytes with the matching uncompressed hash. A native folder click with `folder.zip` already present created `folder (2).zip`, 393 bytes (SHA-256 `65ED5BA62D1F7DB1982875AF78D138A78AE20F2CD03AED2E6B568F25E5DD65F8`) containing `folder/nested.bin`, 256 bytes with the matching hash. The preexisting `folder.zip` retained that same SHA-256 after the collision check. The original file and nested payload retained their hashes.

The package initially used App DLL SHA-256 `D8AFFF935F9D1EFCE925F0937D1233B9ED8B27C4FB32F8B002A5E3B624815286`. After the one-line normal-exit logging correction in the committed source, the VM's self-contained package received exact-source App DLL SHA-256 `82699CA45D2FD21B56F47A3E7C85F7B866A65C8B1881D367A47B4F8FD49147C3`. A fresh native click then created `owned (2).zip`, 166 bytes with the same `owned.txt` member/hash, leaving `owned.zip` in place. A VM restart temporarily left a framework-dependent helper unable to start because .NET 10 was absent in the guest; that invalid attempt produced no archive. Rebuilding the isolated fixture self-contained resolved the test setup. Focused Windows context tests pass **7P/0F/0S**. Prior main runs at `c491e892` and docs-only `dc19ade4` passed all five required CI jobs; exact-product [run 41304823137](https://github.com/benny-cz/FileCat/actions/runs/41304823137) was in progress when this record was written.

## Disposition and stopping rule

**High data-integrity/UX issue, Remediated preliminarily.** The local native file/folder bytes and collision route pass. Before accepting stable 1.0.0, require the final installed Windows candidate to repeat file and nested-folder Send to ZIP with readable, nonzero archives and independently matching member paths/byte hashes; verify existing source and occupied neighbor are unchanged, no zero-byte partial is presented as success, and the candidate's exact source CI is green with skips reconciled. Public preview.5 predates I602. Stable 1.0.0 remains **NO-GO**.
