## The owner's decision

- **Question,** asked once `release/1.0` had been synced and CI had passed: "Shall I tag `v1.0.0-rc.1` on `release/1.0` at `8f122365`? Yes, or not yet?" It came with four points:
  - the tag is permanent;
  - the tag's `sign-candidate` job waits for the owner's approval in the `signing` environment, which the release session does not give;
  - a yes accepts PR #7's proposed DEC-09 amendment and is recorded as that decision;
  - the exact commit has had no full native run.
- **Answer, verbatim:** "Yes, tag rc.1".
- **Settled:**
  - The candidate reference `v1.0.0-rc.1` at `8f122365`.
  - **The DEC-09 amendment is accepted.** For `v1.0.0-rc.N` tags, the owner-approved `sign-candidate` job in the protected `signing` environment creates the candidate's private drafts, so signed bytes never pass through workflow artifacts. Previews keep `release` as their only release-write environment.
- **Not settled:** approval of the `signing` run, which the owner gives in GitHub for each run, final qualification, the stable GO and publication.

## What the tag runs

- **Tests:** every test job, as on any tag. The package jobs start only after all of them have passed.
- **Package jobs:**
  - **Windows:** checks the `signing` environment's protections, then builds the unsigned win-x64 and win-arm64 payloads. It keeps them for seven days as the workflow artifact `unsigned-candidate-payload`.
  - **Linux and macOS:** build the tar, .deb, AppImage and macOS ZIP with product version 1.0.0 and the candidate reference.
- **`sign-candidate`:** waits for the owner's approval in the `signing` environment. Once approved, it signs both Windows runtimes with the owner's certificate (114 signing operations) and verifies them. It puts the 24 candidate assets into a private draft, and the signing records into another. Nothing is published ([candidate path](E-SIGN-DRYRUN-20261120.md#candidate-signing-in-the-tagged-pipeline)).

## The candidate's version identity

The packages call themselves `1.0.0-rc.1`: in the app's own version, the .deb version, the tarball's folder and most file names. The two Setups and the macOS bundle say 1.0.0. Published unchanged as 1.0.0, these bytes would offer 1.0.0 to their own users as an update ([I634](E-I634-candidate-version-identity.md)).

So rc.1 is the first real run of the signed candidate pipeline, but its bytes are not the ones to promote. A successor candidate follows the I634 fix.
