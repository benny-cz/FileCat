# E-I441 — bounded Windows folder-icon customization input

**Scope:** I06/I16, preliminary Windows input-memory and availability remediation. Source parent `3f0ddfe11305738ccefd51607d33c193a8be5f2c`; no candidate exists.

`NativeIconSource.CustomFolder` checked the metadata length of `desktop.ini` against `ShellFileIcons.MaxBytes` (65,536), then called `File.ReadAllBytesAsync` without checking the opened target's length. In the disposable Windows 11 VMware guest, an owned 1,048,576-byte file reached through a `desktop.ini` symbolic link reported **0 bytes** from `FileInfo.Length`, while the opened file reported **1,048,576 bytes**. The first PowerShell 5 probe failed before creating a link because its .NET Framework API lacked `File.CreateSymbolicLink`; that failed setup and its cleanup are retained. The corrected probe used `New-Item -ItemType SymbolicLink`, recorded both lengths and removed its owned payload and link.

The paired product test uses the same finite owned target, with a valid icon header and space padding. A source-preserving extraction of the old call into `ReadCustomFolderIconAsync` produced baseline tracked-diff SHA-256 `2099b03e08b3723962497c4effd0ceb182c6e67c25a98d9e4cb4ffc86370570d`; the test source is identical in both packages (`5f179ba89ba2459b67a6c9af4a7ebfc891b20b2f0fc97cdf605c4ef6ea28cf7d`). The old implementation returned a named icon from the oversized target: **one pass, one failure** on the host and again in the Windows VM. The corrected implementation opens the file, caps its actual opened length before allocation, reads exactly that bounded length and refuses a file that grows before the final byte check. The same VM test then passes **two of two**; the ordinary small `desktop.ini` still names its icon. Both VM phases use SDK `10.0.201` and the xUnit runner reports .NET `10.0.5`.

The baseline 95-member package is SHA-256 `df8965b2fdca27d06b001350829c80ae9124cf177f207faab45a37c3a57d0160` (16,685,752 bytes); the corrected 95-member package is `4c1404d4ab3469ec0f854a58ed03f771f6a4718eac3f4cbc56d2c6dabcc95e18` (16,685,842 bytes). Only `FileCat.dll/pdb` and `FileCat.App.Tests.dll/pdb` differ. The guest verified every package member before running. Its before/after fixture-root sets were empty, and a separate cleanup receipt hashes **212 owned guest files** across 14 exact paths and records all 14 absent. The two receipt-transfer helper files were subsequently removed by exact-path VMware Tools calls. No physical source or workstation UI was touched.

The private `V:\FileCat\artifacts\release-evidence\i441-folder-icon-input-budget-20261014-v1` archive contains **22 files / 33,595,797 bytes**. Its self-excluding manifest SHA-256 is `4b69be43e7c149482c8955b8c2d0b0f246fa0128f59c8fa1679a9dcb4b797c60`; an independent all-file rehash passed. It retains the source overlays, stage inventories and full packages, host logs/TRX, raw VM TRX/output bundles, metadata probes, cleanup receipt and verification scripts.

This proves the finite link path and bounded consumer, not peak whole-process memory, arbitrary concurrent rewrites, installed native desktop behavior or exact-candidate qualification.
