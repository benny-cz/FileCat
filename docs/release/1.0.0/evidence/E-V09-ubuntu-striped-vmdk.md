# E-V09 — Ubuntu two-disk striped recovery and topology

At exact pushed source `5e1dc0f734ef1194cb252e3e2a3ef744dffd2fca`, the disposable Ubuntu 26.04 VMware guest received two **separate, owned 256 MiB VMDKs** in previously unused SCSI units 1 and 2. The guest's by-path entries identified `/dev/sdb` and `/dev/sdc`; its existing 200 GiB boot disk remained `/dev/sda`. Device-mapper combined only those two test disks into a 512 MiB `striped 2 128` source. This succeeds the earlier [Windows VHDX fixture attempt](E-V09-multidisk-fixture-attempt.md), which could not form a multi-disk volume. It is a synthetic, native-component qualification, not an installed-app or physical-source pass.

The stripe was formatted FAT32. An owned `KNOWN.BIN` contained 16 MiB of deterministic SHAKE-256 chunks, and the same bytes were saved off-source before deletion. Both copies hashed to `aeb28c695b78f239d63e3799630344e197ad8430e8e37273173e9c3b976c0b5b`; the private auditor independently regenerated that digest from the saved recipe. The file was deleted and the volume unmounted before FileCat opened it.

An exact `linux-x64` private probe linked the built FileCat Core and Recovery assemblies (SHA-256 `5ade818a481843c62de720d4c8e7cbf92e863ee848cf6707f2606f09b9fb363f` and `aad5ead10bd4958614612223ae9fb0a9603bad5913222ce167c107ec0bbe9bdf`) and reused the guest's pinned .NET 10.0.12 runtime (`dotnet` SHA-256 `01d89e0a0191052bfea616cd4ce624c8faf13b05bbddf7f64499c23e2a9d9269`, `libcoreclr.so` `df5cfe7ba5abf7931f4836726f2fbb0d47dc32caa45d3c209ddf7ccd25c32f4c`). The initial private-project restore hit the repository dependency-lock requirement, and disabling locking globally produced NuGet `NU1005` in referenced product projects. The final private project references those already built assemblies directly; repository dependency locks were not changed. Its first and second ZIPs hash to `6763a6cae5b536c594549132daa525a3989e3991454ff0a494ab1f71e48a7e94` and `66e9f4dd288313e6f3c8bb36137ffe29c6dfa9505f2e8307618c68f0404083d4`; all nine members of each rehash under the archived inventories.

The full raw-disk SHA-256 values remained `39c47624fa24f528cf434822016f5249650d839077bd4d633270385d0fd98500` for `/dev/sdb` and `cc93a02d100b84e03b0b2eeb0f28ebd38f1aa0d0b5cc6d2c5a06d2a8743fb8fe` for `/dev/sdc` throughout all three runs. The mapped source stayed `c4c02aecd9c40e7230ef8e60cf81d28079a9d922bfd2fec3428c521823abdbdf`. Each trace contains one source open with `O_RDONLY`, the expected size/sector ioctls, and zero observed write calls addressed to that source descriptor. Full hashes detect changed blocks; the syscall traces cover this FileCat probe and its children, not unrelated OS processes or every possible physical I/O path.

Cleanup removed the mapper, off-source golden file, both private probe stages and all named guest scripts/results. The VM was shut down, its original VMX was restored with exact pre-restart SHA-256 `5624baff2cf9014a8ced617ca7dfed46df322d573264a5bccaf956f2c31e5d56`, and the two owned VMDKs were deleted. After the guest restarted headlessly, VMware changed only `softPowerOff`, `cleanShutdown` and `vm.lastPowerRequestTimestamp` in the VMX; the temporary SCSI slots were absent, the guest showed only its original `/dev/sda` disk, and owned paths were absent. The post-restart VMX hash is separately retained.

The private archive `V:\FileCat\artifacts\release-evidence\v09-ubuntu-striped-vmdk-20261015-v1` retains **48** scripts, source/project files, package inventories, original/active/restored VMX copies, raw guest receipts, three syscall traces and outputs, and restoration checks. Its manifest SHA-256 is `f94576b007abdc7e0ac1611d7f581429d64767e6bdf66aac5eb1bc5da5bff14c`; an independent 48-file rehash found zero mismatches. Audit SHA-256 is `055fe67e5599e5cda8aff779edb78369b07957529b9d4d6892d0a835a0d2e395`.

V09 still needs integrated installed-app navigation and destination refusal, ordinary-user UDisks2/polkit authorization, wider damaged and adverse media, actual physical topology and exact-candidate qualification. This probe ran as root to obtain a test descriptor; it does not qualify those authorization paths or stable 1.0.0.
