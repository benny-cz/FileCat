# I615 — show Finder tag names without plist color bytes

**Status:** Remediated preliminarily at product `ed4922b6a2ffb057d33de8e7a8df5fb82a1ed7e6`. **Severity:** Low UX, because a real Finder tag appeared in the attribute row as the implementation name and an escaped newline/color digit. Exact-source five-lane CI and a frozen installed-candidate check remain open. Public preview.5 predates this source; stable 1.0.0 remains NO-GO.

## Distinct Mac user task

On the physical macOS ARM64 machine, a test-owned 38-byte `case notes.txt` had a Finder tag represented by the 51-byte `com.apple.metadata:_kMDItemUserTags` binary property list containing `Blue\n4`. Source SHA-256 was `573829317E436CEBEB1036F9BA1548DC0D8E9F7240B1E2C0A78C176E23057CCD`; the tag value SHA-256 was `E88EA9B3D6465DEE74D504F3C17014CBF463D1B85E69EABBC1E249B65128A7C9`. The target began empty. A native FileCat process at product `6a9fc6de`, App DLL `4490991F6482F35D2CF775E28993803F209C08E332AE8E07B9C897EEF6A6B5FA`, copied the exact file through its reviewed Copy dialog. Independent `shasum` and raw `xattr -px` confirmed both bytes and tag value were unchanged. File → Inspect → Streams and attributes showed one 51-byte attribute; selecting it announced `_kMDItemUserTags: Blue\u000A4` to the accessibility tree. The generic Info viewer correctly did not claim to interpret a plain text file, and Properties showed its APFS record. The raw attribute remained available in Hex.

The source already had a bounded binary-plist string decoder for other Apple metadata. The correction uses that decoder for this known Finder-tag attribute, removes Finder's trailing newline and one-digit color index from the displayed **name only**, replaces any remaining control characters in the label, and bounds the number and length of names shown. It does not reinterpret or change stored tag bytes, and does not claim a color mapping for the numeric suffix. The focused cross-platform `HiddenDataTests.macOS_attributes_decode_their_binary_forms` case passed **1/1** for two tagged names.

A fresh native macOS `ed4922b6` source publish used Core DLL SHA-256 `C028394D054EA28B0948AA50B2CBB73C537C5488AB856AF1305A1DDFB0626D10`. In the same owned path, File → Inspect → Streams and attributes and the selected attribute now announced **Finder tag: Blue**. Independent source and destination file hashes remained `57382931…057CCD`; both raw tag hashes remained `E88EA9B3…128A7C9`. The isolated app, published build, worktree, scripts and exact owned fixture were removed after verification; no other Finder tags, settings or files were changed.

## Finite candidate acceptance and stop

On the frozen macOS 1.0.0 package, put one named Finder tag on an owned small file, copy it through FileCat, and open File → Inspect → Streams and attributes on the copy. Require the human-readable tag name without the raw `\u000A`/color digit, while the exact file and xattr bytes match the source. A malformed plist should keep a bounded generic raw-attribute view; the existing decoder tests own broader malformed-input behavior. Reconcile the latest product-source CI and expected tag-only skips, then stop this case. This does not require a new Finder-tag editor or a cross-platform tag feature.
