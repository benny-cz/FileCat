# E-I525 — opened-file bounds for three user-visible inputs

At exact parent `03783f278d0143121693a5b815abe48a7b2bd806`, Registry value import checked `FileInfo.Length` for a chosen path and then called `File.ReadAllBytes` on that path. Hex recovery checked a journal path's length before another `ReadAllBytes`. Bulk rename loaded the entire externally edited name file with `ReadAllLinesAsync` without a size limit. These are separate input paths within the still-open I06 resource budget; no whole-process memory or installed UI result is inferred from the local controls.

An owned Windows sparse-file control exercises the old pathname sequence, not a production recovery operation. A symlink's `FileInfo.Length` was **0** while its opened target was **67,108,865 bytes**, one beyond the Registry import limit, so the old check would admit the target. A journal path first reported **44 bytes**, then an explicit replacement before the old read made `ReadAllBytes` consume **94,371,840 bytes**, beyond the **92,274,693-byte** journal bound. The script removed its own fixture and verified the path absent. The former is also asserted against the corrected Registry import in a Windows test; the latter demonstrates the source-level stat/read race, not an observed natural race in FileCat.

Registry import and hex recovery now check the length of the **opened handle**, read exactly that bounded length and reject a following byte if the file grows. Hex recovery obtains creation time from that same handle. Bulk rename likewise caps the opened editor file at the smaller of 64 MiB or 4,096 bytes per expected item plus one allowance, rejects a line over 4,096 characters, retains at most the expected names and preserves the prior surplus-blank-line behavior. On Unix it opens only a regular file with the existing nonblocking descriptor helper, so an editor-replaced FIFO cannot wait for a writer. The UI reports a refused or unavailable name file and lets the user save/reload rather than silently applying partial names.
