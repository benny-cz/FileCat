# E-I483 — bound allocation when reporting SMB tool failures

At exact parent `525365714b2af2b1279f64b341416a8881a1adcd`, `SmbTools.Failure` recognized authentication and connection errors, then split every line of other diagnostic output merely to report the last nonempty line. An automatic SMB listing can return up to one million characters from each helper stream. A 1,000,012-character reply with 200,000 `junk` lines and `final detail` allocates **10,093,840 bytes** on the Windows test thread and fails the 8 MiB control, although the displayed error is only `nas: final detail`. This is transient parser allocation, not retained or whole-process memory.

The correction scans backward through the existing string and materializes only its last nonempty, trimmed diagnostic line. Authentication/connection classification and the reported `nas: final detail` remain unchanged. The identical corrected Windows case allocates **224 bytes**; the focused `UnixNetworkTests` class passes **14 tests/two explicit Unix skips**, full Core **4,112 passes/141 explicit skips/zero failures**, and the Release solution build has **zero errors/42 warnings**. Local runs used isolated scratch SDK 10.0.101 because committed `main` pins 10.0.401, which was unavailable on the host.

Ordinary-user Mac ARM64 and Ubuntu x64 runs use 250-input parent/final package pairs with identical tests; only `FileCat.Core.dll` and its PDB differ within each pair. Both parent classes report **14 passes/one failure/one Samba prerequisite skip**, measuring **10,093,528 bytes** on the new control. Both corrected classes report **15 passes/one skip/zero failures**; Mac measures **536 bytes**, Ubuntu **224 bytes**. All preceding class outcomes, package member hashes and result TAR contents verify. Nine owned Mac and four owned Ubuntu paths are absent after retrieval. No workstation or guest desktop UI was operated.
