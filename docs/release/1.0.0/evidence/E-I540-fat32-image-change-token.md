# E-I540 — refuse recovered content when an image has no change token

At exact base `b44777928ebfeb63be9c88fbf9c7a1ce39add1bd`, `RecoveryProvider` set its held-image content verifier only when `SourceChangeToken.FromPath` returned a token. It could still issue a reader when that token was unavailable. The disposable Windows 11 VMware guest supplied an **owned 128 MiB FAT32 VHD**, mounted as R:, with a 32 KiB regular image. FileCat's actual token API returned null from both path and handle before and after a same-length rewrite with restored modification time; the image hash changed from `09FED9CBFB98B6AB0F3E8FF63B7B1F9B0E07D58B225295C78FDC023CC4985A72` to `BB6F31CFE210789646F8F8F25935C04A76DB019D64D0A7B06E6F420CBBD75F74`. An NTFS control returned equal path/handle tokens before each rewrite and a changed token afterward. The guest volume reported `FAT32`, label `FCI540`, and `File Backed Virtual` bus.

The existing held-read regression, run unchanged on that FAT32 volume against the old Recovery DLL, failed **0P/1F**: a held reader returned 4,096 bytes from the rewritten former image without an error or a token. A new no-token refusal test was compiled once and run with only the Recovery DLL swapped. On the same owned FAT32 VHD, the old DLL failed **0P/1F**, opening content with no error; the corrected DLL passed **1P/0F**, throwing `IOException` before content opened. Both runs used source SHA-256 `AA1E1A00CF6C75E1813A32B29329EECB6B11368DDCA1C355F8F692880C4BBB4F`, naturally had a null native token, and closed/deleted their owned inputs. The corrected NTFS control injects a null token through an internal friend-test seam and also passes **1P/0F**. A local old/final DLL pair with the same compiled test gives the same fail/pass result.

For a regular recovery image without a usable token, `OpenContent` now refuses deleted-file content with a message to move the image to a filesystem with change tracking and reopen it. Listing remains available. This conservative behavior prevents a held reader from claiming bytes that FileCat cannot attest to after a same-size rewrite. The physical-device route is unchanged. The final Windows Release Core suite passes **4,165P/150 explicit skips/0F** (4,315 total), and `dotnet build FileCat.slnx -c Release --no-restore -m:1 -v:minimal` exits zero with **47 warnings/zero errors**.

Private archive `V:\FileCat\artifacts\release-evidence\i540-fat32-image-token-20261016-v1` contains exact old/final Recovery DLLs, the one compiled test DLL, guest FAT32 and NTFS XML/logs, the prior wrong-read XML, token probe and hashes, source snapshots, local focused/full Core XML, build, setup failures, guest teardown and verifier. All **77 manifest-listed files** independently rehash with zero mismatches; audit SHA-256 `556ff2bb99df4af584cc88488d454a870ea31c927320f88d0e9765a562182bf6`, manifest SHA-256 `0651cd6ae3a4a6d7062a28be8ab71f0a1e242ddf29551480a6db38624e4b4b42`. The owned VHD was detached, R: absent, and guest stage removed. An initial test launcher and standalone probe publish failed during setup; their raw outputs remain in the archive and are not counted as product-test results.

This qualifies the owned FAT32 VHD regular-image route and NTFS control in a disposable Windows VM. It does not qualify a physical image host, installed UI, atomic adversary, or release candidate. Exact pushed-source hosted CI is separate.
