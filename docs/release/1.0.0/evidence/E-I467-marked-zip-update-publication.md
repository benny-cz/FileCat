# E-I467 — marked ZIP update refuses unsafe publication

At exact parent `f4451c2d306304bc3b328fab2ebb8b74bde28d30`, a rebuilt ZIP could replace a marked original even if the replacement could not acquire its download mark. The executor read the original mark, called `File.Replace`, then tried to repair a missing mark only after publication; a write refusal became a warning with the changed archive already present. A new owned-file regression fails on that parent **0P/1F**: the job reports `Completed` when the test requires refusal and byte-for-byte retention of the original. No physical device or installed app was involved.

The executor now writes and reads back the mark on the verified temporary ZIP **before** replacement. A marked update uses a same-folder backup of the original. Immediately after replacement it checks the published mark; if the mark is absent or unreadable, it moves the backup back over the replacement and verifies the restored mark. Verified restoration records a failed step and leaves the original bytes. If restoration cannot be verified, the journal records `Uncertain` and a security error tells the user to inspect the archive; a backup that still exists is retained. A successful update removes its backup, with a warning if cleanup fails. Unmarked ZIP updates retain their existing path.
