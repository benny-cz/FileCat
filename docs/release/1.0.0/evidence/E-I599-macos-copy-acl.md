# I599 — macOS Copy silently removed a deny-write ACL

## Observed user and security consequence

In a fresh isolated exact-I598 Mac ARM64 app (`754f8f6ac07edf5daa0566305e3b44e07adff889`), an owned 19-byte file carried an extended ACL entry `group:everyone deny write`. FileCat reviewed its exact empty target and reported **Completed · 19 bytes**. Both data forks matched SHA-256 `0330aee1d9446010b5da58f9d27e7ce205c2d67621f8ab172937b8a0019a3e2f`, but `ls -le` showed the target had **no ACL**. A non-writing `O_WRONLY` open returned `EACCES (13)` for the source yet succeeded on the copied target. The neighboring `keep.txt` stayed SHA-256 `f660a7996deacfbc7560e4240054a8ad82eb02fe25a95064257e07084bcacb85`. This is an effective access-control downgrade, not merely cosmetic metadata loss.

The I598 resource-fork fix used `fcopyfile(COPYFILE_XATTR)` on held descriptors; Apple's native API treats ACLs as a separate `COPYFILE_ACL` flag. The I598 resource-fork pass remains valid at its stated scope. This newly observed ACL boundary is the documented consequential reason for the follow-up. Prior Windows ACL/high-token and Mac quarantine tests do not establish Mac extended-ACL preservation during ordinary Copy.

## Correction and exact-source verification

Product `4eefe1ab78b8f0e0da22cd0ac760568525698ff6` requests both `COPYFILE_XATTR` and `COPYFILE_ACL` on the same held source/new-destination descriptors, then compares the source and destination extended ACL text through `acl_get_fd_np(ACL_TYPE_EXTENDED)` before the destination name is published. A native failure or mismatch aborts the copy and removes its newly created destination; a move cannot advance to source deletion. The resource-fork size check remains. This is an object-bound metadata check, while the rest of the existing copy/review path keeps its own documented race limits.

Focused Mac Core controls passed **2P/0F/0S**: one 128 KiB resource fork plus an extra xattr and deny-write ACL, and one ordinary file without a fork or ACL. Windows x64 compiled the same test class and recorded **0P/0F/2 expected platform skips**. A fresh exact-source Mac package ZIP had SHA-256 `4d7d91257a14705db3b52760692427080814f727346aa911c3749c52536199b2`; the extracted app passed ad-hoc deep strict code-signature verification. Native FileCat copied the same owned `acl.txt` into a new empty target, again reported Completed, and both source and target now showed `group:everyone deny write`. A non-writing write-open returned `EACCES (13)` on **both**; the old I598 target without ACL remained write-openable as a before control. All three data forks stayed at the original SHA-256, the neighbor was unchanged, only `acl.txt` appeared in the corrected target, and the isolated process exited.

## Disposition and finite candidate rule

**High confidentiality/integrity issue, remediated preliminarily.** On the exact installed macOS 1.0.0 candidate, copy an owned file with one deny-write extended ACL and known bytes to an empty APFS target. Require the reviewed destination, completed report, exact source/target hashes and ACL text, and `O_WRONLY` refusal on both without writing. Check a plain-file positive control and that the neighbor and staging directory remain unchanged. If the destination cannot store the ACL, require a visible failed item, an intact source and no successful unprotected copy. Stop after these affected cases and latest-product five-lane CI with skips reconciled; do not reopen passed Windows ACL or I598 fork checks without a new consequential observation. Other ACL forms, network/removable volumes and installed candidate remain unqualified. Public preview.5 predates I599; stable 1.0.0 stays **NO-GO** pending all required gates and explicit owner GO. A proved defect resets the active exploratory clean streak to **0/20**.
