# E-I520 — unmounted Linux mapped source discovery and read-only recovery

At exact parent `a56ee1dd`, FileCat's Linux discovery omitted an unmounted `dm-*` layer even when it had a nonzero size and verifiable device identity. An owned sysfs regression changed the earlier mounted-layer fixture to require `/dev/dm-1` as an unmounted source and failed **0P/1F**. That meant the chooser could not select an unmounted mapped FAT32 volume for recovery. The correction lists an unmounted mapped layer as a whole source, lets the chooser scan it without assuming a known mounted file system, and retains the mounted supported layer as a volume. Unsupported *mounted* layers retain their previous exclusion. The chooser labels the new option “Mapped source,” with its actual unmounted state. The corrected Core and App focused cases pass **1P each**.

In the authorized Ubuntu 26.04.1 VMware guest, an owned 64 MiB image was formatted FAT32, received a deterministic 1 MiB file, had the file deleted and was unmounted. A linear device-mapper layer over its loop device was made read-only; no physical disk or other user's path was modified. Ordinary-user FileCat discovery identified `/dev/dm-0` as a 64 MiB layered source with no file system or mount point yet, and an actual root-authorized **read-only** FileCat scan found the FAT32 volume and deleted `_ECOVER.BIN`. `RecoveryContent` returned **1,048,576 bytes** with SHA-256 `734411806bf2aa799cd4a5c746cb951b045cdda58a994812e749b03b3edf93ad`, identical to the off-source golden file. The complete 64 MiB source image and mapper both hash to `5828f8ab76cdbce704c3661b30dfdaf2656aeea7c69eb53171e6c4582a88a9e6` before and after scan; the image retains the same hash after device cleanup. FileCat's topology deliberately classifies a *read* of a loop-backed device by its loop identity, not the disk holding its image file. No same-destination copy or physical separation claim is drawn from this loop fixture.

The first private probe failed because it expected the host disk rather than that documented loop identity. A second probe demonstrated the FAT32 volume but used the original filename instead of FAT's deleted-first-character name; both raw failures are retained. The third probe passed discovery, exact bytes and source hashes. The setup mounted the owned image only long enough to create/delete the file; the recovery scan ran with both loop and mapper read-only and **unmounted**. Cleanup removed the mapper, loop attachment and mount directory. A final ordinary-user postcheck verified the source hash and absence of the entire owned guest stage; a temporary sudo-input file was removed after each root phase. No VM settings, host UI, USB disk, or Mac state changed. A first default-sandbox full App invocation ended with an empty log and no TRX, so it has **no test result**; the missing-result observation is recorded separately, and the complete App suite was relaunched with execution permission.

The corrected complete Core suite passes **4,154P/142 explicit skips/0F**; the complete headless App suite passes **1,654P/44S/0F**. The final production App build has **zero warnings and errors**.
