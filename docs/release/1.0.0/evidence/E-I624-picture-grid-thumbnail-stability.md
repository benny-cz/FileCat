# I624 — Picture grid thumbnail stability

**Status:** Remediated preliminarily at product commit `b8a5d24a`; installed 1.0.0 candidate and exact-source CI remain open. **Severity:** Medium UX and resource use. **Owner observation:** opening a folder with many photos in Picture view repeatedly reloaded thumbnails and visibly blinked.

## Finding and correction

The grid cleared every decoded thumbnail on each listing refresh, including an unchanged watcher or manual reread. It also kept at most 64 cached entries while a large viewport could demand more than 64 visible tiles. Its render pass recorded only *uncached* thumbnails as visible demand; once an image appeared, the cache considered it offscreen and could evict it on the next completion. These paths caused repeated decoding and redraw without a changed picture.

The corrected grid retains a thumbnail across an unchanged listing refresh, using item identity, size and modification time as its revision key. It includes cached visible pictures in demand, never evicts a visible tile to satisfy the 64-entry offscreen cache limit, and discards completed work that is no longer in the current viewport. Leaving Picture view or navigating to a different tab/location still retires that view's cache. A changed file revision requests a new decode. Offscreen entries remain subject to the bounded cache and can be decoded again after eviction; no unbounded album cache is claimed.

## Focused and native evidence

- The new 65-photo, 1900×950 headless grid test reproduced the old behavior before the final demand correction: **64/65 cached, 468 load attempts, one pending** after a minute. After correction, all **65/65** settled in about six seconds; ten redraws and an unchanged listing refresh kept exactly **65** loads. Changing one BMP and its modification time led to exactly **66** loads and again **65** cached visible pictures. Both Picture-grid rendering tests pass **2/2**. Existing App Picture-grid tests pass **2/2**, including archive-provider thumbnails and ordinary file/folder rows.
- An isolated macOS ARM64 checkout at base `951caad6` plus the exact two corrected control files was built with the pinned .NET SDK `10.0.101`. The ad-hoc signed diagnostic app's `FileCat.dll` SHA-256 was `e41b5e30bf0303af174b7a8c468a7eb18266af92324ffa2f3f79bf90ec0602a2`. It opened an owned 80-photo BMP folder in a native Picture grid; AX reported **0 folders, 80 files** and the grid role. Three consecutive Ctrl+R rereads started **zero** new `--picture-worker` processes. Changing one photo's bytes and time started **one** worker, and the subsequent unchanged reread started **zero**. The exact test process exited and all three disposable Mac test paths were removed. The diagnostic build and fixture were separate from release packages. Screen capture was unavailable from the remote session, so this native result establishes accessible grid continuity and worker activity, alongside the headless bitmap stability check, rather than a pixel-level visual comparison.

## Candidate acceptance and stop rule

On the exact installed 1.0.0 candidate, open a folder with more visible pictures than the ordinary cache limit on a large viewport. After tiles settle, redraw, wait for an unchanged watcher event and press Reread: visible thumbnails must stay drawn without new decodes or blinking. Change one owned picture's content and modification time: that tile alone must update. Scroll away and back with a larger album to confirm the bounded offscreen cache remains usable. Reconcile producer, Windows x64, Windows ARM64, Ubuntu and macOS CI results and skips against the preceding green source. Stop after these finite paths pass; reopen only for a demonstrated repeated visible reload, stale changed-file thumbnail, or consequential resource regression. Existing preview.8 predates I624.
