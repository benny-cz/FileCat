# I567 — Page Find did not take the Windows keyboard

2026-10-30. The owner reported that Ctrl+F in an opened Markdown page exposed Find but left the cursor in the rendered page. The user could still page through the document but had to click Find before typing. This is a new, consequential native focus boundary after I564's accepted Page Up/Down correction; the paging result itself is not reopened.

## Reproduction and correction

An isolated FileCat instance in the disposable Win11 VMware guest opened `FindProbe.md` as a WebView2 Page. Before the correction, the Ctrl+F Find row displayed a focus outline, but the Win32 focus class and UI Automation focus remained `Chrome_WidgetWin_1` / the Markdown document after the shortcut and after typing `needle`. The Find field stayed empty. The baseline JSON and screenshot are retained in the private archive below.

Avalonia's `_search.Focus()` changed logical focus without necessarily moving Win32 keyboard focus out of the embedded native WebView2 window. `PageView` now explicitly hands the keyboard to the active viewer window when Page Find is focused. The Windows page engine cancels an unfulfilled page-focus request and calls `SetFocus` on that window. Escape still restores focus to the Page. The native handoff is Windows-specific; Linux and macOS keep their existing page-host focus route.

The correction is pushed as product commit `07a7f82dfcb2800224ff79a06c15cf2fd9db1cab`. In the same isolated VM, Win32 and UI Automation focus moved to the Avalonia `Find in file` edit control on Ctrl+F. Actual typed text became the field's `needle` value. Escape returned focus to the WebView2 document. Text, Hex and Info modes in that viewer also received `alpha`, `4D` and `Info` respectively in their Find edit control by keyboard alone. These checks used the final non-diagnostic local `FileCat.dll` and `FileCat.Platform.Windows.dll` over the previously isolated test app. Guest SHA-256 hashes of both DLLs matched the local binaries: `86622E3462F7047C4E032D3852CAE23EAFE3BDE31F7E891A8DA3958AA1600C11` and `C55BEA7F42E39377B57A2495EAED76C528B49CBAE4376500869724EE4E6FB8E5`. The tested isolated process was stopped afterward.

The final-source App Page search class passed **9/9**. Native Windows WebView2 `PageViewTests` passed **8/8** after the focus correction. Focused App checks also passed for the other viewer search surfaces: `ViewerFindControlsTests` **3/3**, `HexEditorFindControlsTests` **1/1**, `CompareTextInteractionTests` **7/7**, and `ReportWindowTests` **4/4**. The Compare and Report controls now assert that Ctrl+F focuses their Find field; Report Escape first returns to the report and a second Escape closes it. The App build had zero warnings and errors. No other viewer showed this same failure in the checked routes. Picture mode has no text Find control, so it is outside this case.

## Acceptance and stopping rule

I567 is remediated preliminarily at the local Windows source/native-input boundary. Exact pushed-source producer, Windows x64, Windows ARM64, Ubuntu and macOS CI must pass with skips reconciled before GATE-CI-FINAL can be accepted again. Final Windows 1.0.0 candidate acceptance must use the exact signed, installed candidate: open Markdown, press Ctrl+F, type a query without clicking, find a match, Escape back to the Page, and confirm Page Up/Down still scroll. This local DLL overlay and the earlier unsigned preview.3 do not establish that candidate result; preview.3 predates I567. Stop repeating the accepted local scenario unless a consequential source change, native regression, or invalid receipt appears. Stable 1.0.0 remains NO-GO pending the wider release gates and explicit owner approval.
