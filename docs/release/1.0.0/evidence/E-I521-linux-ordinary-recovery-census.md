# E-I521 — ordinary Linux recovery UI blocked by process census

At exact pushed source `1705d6c1803e281776a880af459524155c2d5fa7`, a private framework-dependent Linux x64 FileCat build was launched as ordinary user `benny` in the authorized Ubuntu 26.04.1 VMware GNOME session. This was an installed native GUI interaction, not a release candidate. The built App DLL SHA-256 was `c8b5a545d453bfbacfe20eef3929eec0b964c1b9104b94ebc754f4530ec1f713`; the 62-file payload ZIP SHA-256 was `d6efc516251731045753fa0a56dc0ca881394fc9ef34c724b6245c1be96883b4`.

An owned 64 MiB FAT32 image with a deleted file was exposed through read-only, unmounted `/dev/mapper/filecat-i522-ui`. The image and mapper SHA-256 were both `5828f8ab76cdbce704c3661b30dfdaf2656aeea7c69eb53171e6c4582a88a9e6` before the interaction and again immediately before cleanup. FileCat's actual Tools → Recover deleted files chooser displayed **Mapped source dm-0: filecat-i522-ui**, with **Mapped source, 64.0 MB mapped volume · not mounted · also finds deleted partitions**. Selecting it did not start a scan. The modal said that other FileCat processes *may* still write to the disk and asked to close them or check access to process information.

The guest process snapshot had one `dotnet` process, this FileCat PID 8423, and the temporary input daemon; no second visible FileCat process. A separate ordinary-user .NET process-census diagnostic excluded itself and PID 8423, saw 366 processes, identified 247 kernel threads, and could not obtain `Process.MainModule.FileName` for **43** other processes, including root-owned `systemd`, `udisksd` and `vmtoolsd`. It therefore could not prove that no renamed FileCat apphost was running. `SingleInstance.OtherFileCatRunning` deliberately returns unknown for inaccessible executables, and `CheckDiskSafety` refuses the scan on unknown. The diagnostic establishes the mechanism and the native UI refusal; it does **not** prove that every ordinary Linux installation has the same `/proc` policy or that an inaccessible process cannot be FileCat. Do not weaken the fail-closed rule merely by ignoring unreadable processes.

The test input used a temporary `ydotool` package and owned root daemon only inside the disposable guest. A GNOME remote-interaction prompt raised by the first X11 input attempt was dismissed without enabling sharing. The UI process exited, the source/mapper hashes matched, the mapper and loop were removed, the input daemon was stopped, the temporary package was purged, and the before/final package inventories compared byte-for-byte. An independent guest postcheck found no owned stage, mapper, app process or temporary input package. The first daemon-stop attempt failed because the daemon had already exited and left a stale owned socket; the corrected cleanup and both logs are retained. The first archive collection attempt failed when its sudo input was still present; the next failed because an archive was written inside its changing source directory. The final collector deleted the one-use input before archiving, wrote outside the source directory and verified the tar had no credential member. These are test-harness failures, not product passes.

The **21** payload files include original GUI screenshots, process-census source/output, guest tar (**103** members), raw setup/cleanup failures and restoration checks. The guest tar SHA-256 is `bc7d2b529767960b4fa74dce1a7d49749234ffed69e05815ac0b61d04e53385f`, with no `.auth` member.

**Disposition:** open High gap in the ordinary Linux recovery path. The I520 chooser discovery is verified in an installed session, but UI scan/authorization cannot be claimed. A safe remedy must establish the absence of other FileCat writers despite inaccessible processes, or explicitly require a supported elevated session. Retest the actual chooser-to-scan flow with exact post-fix source; physical media and final candidate remain separate.
