# E-I580 — Refresh rechecks an open viewer Find query

31 October 2026. A bounded user journey opened Find in the Text viewer, searched an owned note, then replaced that note externally and pressed Refresh. On the prior build, the viewer displayed the new text and retained the query but demoted its result to neutral “Press Next or Previous to count.” This was separate from accepted refresh-byte/position and search-on-type controls: the user's existing query did not run against the refreshed bytes.

## Before and after

The disposable Ubuntu 24.04 VM used an isolated checkout based at `f78638f0` with the later I578/I579 source overlays; ViewerWindow itself was unchanged from current main before this correction. The owned `note.txt` initially contained `alpha needle omega` (31 bytes, SHA-256 `05e4efd3c605f542d60fb2965404e072b800830cfb3afa590521d42aeca26c61`). Native F3, Ctrl+F and typing `needle` showed [one green match](../../../validation/evidence/exploratory-20261031-refresh-find-old-match.png). Atomic replacement with `alpha changed omega` (32 bytes, SHA-256 `4747ee6b03f4182deab8cd99fec53db1a6a79d0675e0890379743d60d83b1018`) followed by F5 showed the new bytes but [neutral, uncounted feedback](../../../validation/evidence/exploratory-20261031-refresh-find-old-neutral.png).

A new headless `ViewerRefreshTests` case was run before product change and failed after the same successful Refresh because the result did not become `0 matches`. Product commit `5ba1b8b3` schedules the retained query only after a successful new reader is published; a failed Refresh does not trigger it. The Page load callback no longer schedules a query while a replacement is still being prepared. The focused before/after test now passes, and affected ViewerRefresh plus ViewerFindControls suites pass **13/13** in Windows Release. The Page search suite also passes **10/10** after the callback change; this is a focused regression check, not a native Page Refresh/Find candidate test.

An isolated Ubuntu rebuild with the corrected ViewerWindow started from the no-match source. Native Find showed [zero red matches](../../../validation/evidence/exploratory-20261031-refresh-find-new-miss.png); atomic replacement with `needle and needle` (30 bytes, SHA-256 `d109dd722f1143c06172d86ea4a9007b4f4200e20ba9cf6fb9c35260c7dbbd06`) and F5 produced [two green matches](../../../validation/evidence/exploratory-20261031-refresh-find-new-hit.png) without typing again or pressing Next. The exact VM app process and fixture path were checked and removed. This VM overlay is not a clean full-head package or a signed installed candidate.

## Candidate stopping rule

On the exact installed Windows x64 1.0.0 candidate, open an owned local text file in Text mode and an owned Markdown file in Page mode. With each Find bar open and an existing query, successfully Refresh after replacing its source with a matching and then a nonmatching version. Without another keystroke or Find button, count, highlight and border must describe the newly displayed version. For one failed reopen, the prior view and its query must remain available without a result from an uncommitted replacement. Stop after those affected viewer modes and latest-product five-lane CI with skips reconciled. Do not repeat generic viewer refresh, search or position tests. Stable signing and final GO remain separate.
