# E-I43, E-I44 — Modified times on FTP servers without MFMT; running jobs seen by a second FileCat

Preliminary automated evidence on development builds. Raw outputs under `artifacts/release-evidence/` (SHA-256 below).

## E-I43 — Modified times kept over FTP without MFMT, and back

**Setup.** The lab of E-V08-L1 (host → lent Ubuntu VM: OpenSSH 8.9p1, vsftpd 3.0.5 for explicit and implicit FTPS),
no added latency. The lab's tree case (40 files of up to 70 KB, a 48 MB file, two folders) now gives every file a
modified time far from now and a minute apart (from 2021-03-04 05:06:07 UTC), checks each time on the server (a stat:
MDTM over FTP) after the upload, and each downloaded file's time after the way back (within 2 s).

**Before** (product code of `e399276` with the new test; `v08-i43-times-before.txt`
`b8d34f27b7a7fb8ec634ca9663dac71a1f121a6b543820b51abb1e0d2bb0124c`): over SFTP the tree passed; over explicit and implicit
FTPS it failed — every file on the server showed the upload's own time:

```
note 00.bin: 2026-10-01T02:38:06.0000000Z on the server, 2021-03-04T05:06:07.0000000Z sent
```

FileCat sent no time when the server lacks MFMT, which vsftpd does. A first version of the fix also showed the second
half of the issue: the times then held on the server, but the files downloaded back took the listing's time, which
vsftpd's LIST gives only to the day for files older than six months.

**After** (`e527a86`; `v08-i43-times.txt` `65495d1fe881fd2cbac7849e3d85f67cb11b80c9355cd339483c723c0e079e20`): 5 of 5 —
the tree over SFTP, explicit and implicit FTPS with every time kept both ways, and the link case over SFTP and explicit
FTPS. Unit test: `SftpJobTests.Uploads_keep_modified_times_and_say_so_where_the_server_does_not` (a server that keeps
no times: one note naming the count; "keep timestamps" off: no time sent).

**Limitation.** One FTP server without MFMT (vsftpd, which sets times through MDTM); a server that neither has MFMT nor
takes MDTM with a time keeps the arrival time, and the job now says so. Listing times on such servers stay coarse
(I45).

## E-I44 — A running job is not interrupted, even to another FileCat

**Test.** `JobEngineTests.A_job_still_running_is_not_interrupted_even_to_another_FileCat`: a job journal held open by
its writer (as a running job holds it) is scanned the way a starting FileCat scans; then the writer goes without an
end record (a crash) and it is scanned again.

| Build | Windows host | Owner's Mac (Darwin 25.6, arm64) |
|---|---|---|
| Before (`2a6f882` with the new test) | passes — by accident: the scan's read fails on the writer's sharing mode | **fails**: `Assert.Empty() Failure: Collection was not empty` — the live job is listed as interrupted |
| After (`e399276`) | passes | passes |

The journal suites (`JobEngineTests` 26, `InterruptedCopyRecoveryTests` 7, `BulkRenameTests` 6) pass on both after the
change. Builds: Debug, built on the host and copied to the Mac (`~/fc-p04`).

**Limitation.** On network home folders (NFS, SMB) .NET takes no advisory lock, so a second FileCat there still reads
a running job's journal as interrupted, as before the change.
