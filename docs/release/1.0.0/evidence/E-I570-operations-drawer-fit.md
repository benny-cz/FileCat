# I570: Operations drawer fits the visible work

2026-10-30. Preliminary source-level UX correction at `e1eeada5`, `9791a496` and `5b545f8d`. The owner first supplied a screenshot of one completed delete with a large empty lower half of the open Operations drawer. After the sizing change, a second screenshot showed a completed create-folder report clipped by the compact drawer, with no right-side scrollbar. This is a consequential regression in access to the report controls, not final installed-candidate acceptance.

The drawer had a fixed 300-DIP default height. Its job list and selected report share a row, so a single short result stretched the list into unused space. The correction sizes an uncustomized drawer from the visible history rows and selected detail/issue content, bounded by the available workspace. More rows or detail increase it; recovery content keeps its existing usable minimum. The resize handle still overrides automatic sizing and saves the user's chosen height. A previously saved nondefault height remains a manual preference; **Fit height** beside the selected job actions restores automatic sizing and persists that reset.

The second report exposed the 140-DIP minimum-drawer case: the selected report's top panels could exceed the available row, and the final issue list did not make those panels scrollable. `5b545f8d` puts the entire selected-detail pane in a vertically scrolling viewport with an automatic right-side scrollbar. Its issue list remains separately bounded. When the window is too short for every detail, the user can scroll to Copy report, Save report and issue content without enlarging the drawer.

Focused `OperationsDrawerLayoutTests` passed **14/14** at `5b545f8d`, including one-completed-job fit, six-job growth, manual override and reset, plus both minimum-window interruption cases. The first placement of Fit height crowded the history heading at minimum size and failed the row-reachability assertion; moving it beside selected-job actions restored that check. The new regression checks that selected details exceed their viewport, an effectively visible vertical scrollbar exists, and scrolling makes **Save report…** fully reachable. Existing interrupted-recovery Stop visibility, keyboard and pointer resize, and workspace-restore cases passed. The one-job regression requires 140–230 DIP, six rows at least 60 DIP taller, and at least 90 DIP of remaining workspace. This is not a visual check of the exact installed Windows 1.0.0 candidate.

**Stopping rule:** On the exact installed Windows 1.0.0 candidate, complete one short job and open Operations: no large blank lower region, its report actions visible or reachable via the right-side scrollbar, and the main workspace usable. Shrink the window until the selected report is clipped, then scroll to Copy report, Save report and the final issue. Add several jobs and a recovery item: the drawer grows within the workspace bound and the recovery Stop control remains reachable. Manually resize it, close and reopen the drawer, then use Fit height to restore automatic sizing. Reconcile producer and four platform CI jobs and any new skips at the latest product source. Public preview.3 predates this change; stable 1.0.0 remains NO-GO until the separate candidate and signing gates pass.
