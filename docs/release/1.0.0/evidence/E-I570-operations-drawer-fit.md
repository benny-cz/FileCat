# I570: Operations drawer fits the visible work

2026-10-30. Preliminary source-level UX correction at `e1eeada5`, `9791a496`, `5b545f8d` and `3256a3d7`. The owner first supplied a screenshot of one completed delete with a large empty lower half of the open Operations drawer. After the sizing change, a second screenshot showed a completed create-folder report clipped by the compact drawer, with no right-side scrollbar. Later full-window screenshots showed six short folder operations occupying a tall drawer while the right report pane was blank. These are consequential failures of the same drawer's content fit and report access, not final installed-candidate acceptance.

The drawer had a fixed 300-DIP default height. Its job list and selected report share a row, so a single short result stretched the list into unused space. The correction sizes an uncustomized drawer from the visible history rows and selected detail/issue content, bounded by the available workspace. More rows or detail increase it; recovery content keeps its existing usable minimum. The resize handle still overrides automatic sizing and saves the user's chosen height. A previously saved nondefault height remains a manual preference; **Fit height** beside the selected job actions restores automatic sizing and persists that reset.

The second report exposed the 140-DIP minimum-drawer case: the selected report's top panels could exceed the available row, and the final issue list did not make those panels scrollable. `5b545f8d` puts the entire selected-detail pane in a vertically scrolling viewport with an automatic right-side scrollbar. Its issue list remains separately bounded. When the window is too short for every detail, the user can scroll to Copy report, Save report and issue content without enlarging the drawer.

Focused `OperationsDrawerLayoutTests` passed **14/14** at `5b545f8d`, including one-completed-job fit, six-job growth, manual override and reset, plus both minimum-window interruption cases. The first placement of Fit height crowded the history heading at minimum size and failed the row-reachability assertion; moving it beside selected-job actions restored that check. The new regression checks that selected details exceed their viewport, an effectively visible vertical scrollbar exists, and scrolling makes **Save report…** fully reachable. Existing interrupted-recovery Stop visibility, keyboard and pointer resize, and workspace-restore cases passed. At that source, the one-job regression required 140–230 DIP, six rows at least 60 DIP taller, and at least 90 DIP of remaining workspace. The later compact-history request supersedes the six-row growth expectation. This is not a visual check of the exact installed Windows 1.0.0 candidate.

The full-window follow-up found that opening an empty drawer and then creating a folder left `Selected` null: the new history row appeared, but its report pane stayed blank. The new regression failed before the correction with **Expected: Create folder; Actual: null**. `3256a3d7` selects new work when the open drawer has no selection and follows each newer job while the newest row remains selected. A deliberate older-row selection stays put until the drawer is reopened; reopening selects the newest relevant job. The correction also restores a remaining row if the selected job is retired. Its first implementation exposed a ListBox binding clear after removal, so the final version captures selection before removal and restores a fallback after the binding settles. Three visible history rows now bound automatic height; the list scrolls to older jobs. A six-job headless window shows selected details, has a visible history scrollbar, and can reach the oldest row. The revised six-job control verifies scrolling and bounded growth rather than the earlier 60-DIP minimum. The focused layout and Operations center classes pass **23/23** at `3256a3d7` (15 layout, eight center). The selected-report scrollbar and deliberate history selection remain covered. This is a headless layout and interaction check; no installed-candidate visual claim follows from it.
