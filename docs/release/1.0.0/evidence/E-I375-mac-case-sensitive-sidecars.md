# I375 — case-distinct Mac files shared verification sidecar claims

2026-10-12 CEST. **High verification-identity issue; remediated preliminarily in a declared local product/test overlay.** `FolderSidecars` used case-insensitive filename keys on every non-Linux platform. A case-sensitive macOS volume can contain both `item.bin` and `ITEM.bin` and their separate `.sha256` files; the scanner's file/claim dictionaries then merged the case-distinct entries. This is separate from [I374](E-I374-unix-verification-folder-identity.md), which corrected the surrounding *folder* cache key. Default case-insensitive Mac volumes did not expose this condition.

An owned 128 MiB sparse image was mounted on the authorized Mac as **case-sensitive HFS+**, with `caseprobe` and `CASEPROBE` observed at distinct inode numbers 20 and 21. The self-contained arm64 probe used exact pushed `930293ee3d2dd6cd31194eadd22e24ae6451c62b` Core code and only created files within its owned fixture on that image. The two payloads were distinct; each file's actual SHA-256 matched its own sidecar. The scanner reported one checksum claim for each queried name but applied a merged claim: the lower file was `Matches` and the upper file **`Differs`**. The raw probe exited **2**, and its fixture was absent afterward. This is a wrong verification result, not a file write or physical-source test.

The correction uses the repository's platform path comparer for sidecar filename dictionaries: Windows remains case-insensitive, Unix (including macOS) is ordinal. On a case-insensitive Mac volume, an exact lookup is preferred; a differently cased spelling is accepted only when a single listed candidate and the requested spelling have the same native device/inode and link type. This retains the existing basename-alias behavior without merging case-distinct files. The same case-sensitive probe source rebuilt with corrected Core code returned `Matches` for both files, exit **0**, and absent fixture. A final-source repeat on the owned image also exited **0**. On the Mac's ordinary case-insensitive volume, final-source bare checksum, manifest and detached-signature claim routes each resolved a mixed-case spelling to the same measured inode; the two checksum checks returned `Matches`, and all three route controls passed. The signature route checks binding only, not signature validity. Both final fixtures were removed.

Independent readers reparse both original nested raw JSON results and exits and the two final-source native outputs; they check exact payload hashes, source/binary pins, case-sensitive mount/inode observations, the ordinary-volume alias identities and owned cleanup. The first local focused build failed because a source import was missing; a later alias refinement first failed on a duplicate local name. Both compiler logs remain failed, followed by passing corrected focused runs. The first `hdiutil` APFSX image-creation attempt also returned `Invalid argument` before mounting; the later case-sensitive HFS+ image passed all controls. None of these setup/compiler failures is counted as a product probe result.

After each native session, the image was detached, its approximately 10 MiB sparse file copied to private evidence with matching local/Mac SHA-256, and the exact owned Mac directory removed and checked absent. No user Mac files, physical disk, host UI or system setting was changed. The final local focused Windows inventory passes two cases with seven explicit platform skips; a separate full Core run passes **4,017 cases/100 explicit skips/zero failures**. An independent reader preserves every I374 Core case-name/outcome/message record, with exactly five new Windows skips (two case-distinct and three Mac-alias controls). The final full-solution build reports **41 existing warnings/zero errors**. Original-push hosted qualification is separate; a case-insensitive macOS runner may skip the two case-distinct cases but should execute the three alias cases. No installed candidate or physical-source HOLD is qualified.
