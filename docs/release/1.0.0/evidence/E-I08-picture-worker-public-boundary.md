# E-I08 — public picture-worker containment wording

At exact source `c93bb2364cab9ec926e4a1c92b14bcb283f97782`, [the capability table](../../../CAPABILITIES.md) said that a damaged or hostile picture “cannot take FileCat down” because decoding uses a separate process. That was broader than the implementation supports. `PictureDecoder.Worker.Start` starts a Windows worker through `SandboxedWorker` with normally low integrity and a job memory cap. On Linux and macOS it starts an ordinary child with the user's UID and inherited filesystem/network authority, no OS memory sandbox, and a private lifetime pipe. Linux x64 additionally applies a process-creation restriction. The parent enforces input, output, time and concurrency bounds, but resource exhaustion and all child authority effects are not eliminated by process separation.

The capability row now states those platform differences and says decoder crashes are reported to the viewer without claiming full containment. This is a source-and-document comparison; it does not claim a new native test, a sandbox implementation, or closure of I08. Actual Unix containment, native resource limits, detached descendants, installed-candidate behavior and the owner risk decision remain open. No device, workstation UI, system policy or release artifact was changed by this documentation correction.
