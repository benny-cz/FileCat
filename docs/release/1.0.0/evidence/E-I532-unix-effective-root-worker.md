# E-I532 — Unix picture worker could decode with effective root rights

The exact `04b054c2` `UnixWorkerIdentity.Drop()` checked only the real UID. An owned Ubuntu process with real UID/GID `1000/1000` and effective UID/GID `0/0` returned `Refusal:null` without changing identity. Its ordinary-user controller could read a root-only fixture after that call. The old self-contained FileCat picture worker, launched with the same mixed identity and paused before a 2×2 PNG reached stdin, showed `/proc` `Uid: 1000 0 0 0`, `Gid: 1000 0 0 0` and nonzero `CapEff=000001ffffffffff`. It decoded successfully. This is a demonstrated containment defect for a hostile picture, not a claim that an exploit was run.

The worker now checks real and effective IDs and probes whether a saved root identity can be regained before reading image input. A privileged worker clears supplementary groups, sets the ordinary GID then UID, and verifies real and effective IDs plus inability to regain either root user or group. Without a verifiably ordinary identity, `PictureWorker` refuses before opening stdin or invoking the decoder. A full-root `sudo` launch uses the recorded ordinary requester; a mixed real-ordinary/effective-root launch uses its real UID/GID. Ordinary launches also require the verified unprivileged result.

The same Ubuntu probe with the corrected Core DLL passes ordinary, full-root and mixed-root cases: after IDs are `1000/1000`, `Unprivileged:true`, and the root-only fixture cannot be read. The corresponding Apple Silicon Mac controls pass ordinary, full-root and mixed-root cases, ending at the ordinary `501/20` identity with no root-only read. The actual Ubuntu FileCat worker old/final pair uses the **same apphost and 2×2 PNG**. A separate Ubuntu **saved-root** control constructs real/effective UID/GID `1000/1000` with saved UID/GID `0/0` *inside* the running managed process. The exact old Core `Drop()` reports no refusal and leaves that saved authority: a subsequent `setuid(0)` succeeds, restoring effective root and reading a mode-0600 root-only file. Replacing only the Core DLL leaves the initial and post-drop real/effective IDs ordinary, but `setuid(0)` now fails and the root-only file stays unreadable.
