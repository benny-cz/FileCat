# E-I531 — Apple Silicon instance locks were created without owner permissions

The exact pushed `e7aaddba` hosted run [38887536744](https://github.com/benny-cz/FileCat/actions/runs/38887536744) **failed** its macOS “Unix instances across sessions and temporary folders” step. Producer policy, Windows x64/ARM64 and Ubuntu jobs passed; the macOS job failed, and four conditional publication jobs skipped. The official macOS job log and downloaded native-process artifact show seven failed scenarios out of eight. Each ordinary same-user forwarder that needed the usual `instance.lock` aborted with `Cannot open the FileCat instance file: Permission denied`; the fixture packer itself could not read one such lock. This is a real second-launch regression introduced by the I528 lock-opener change. The failed run is retained as failed, not promoted by later local success.

The three-argument P/Invoke declared libc's variadic `open(path, flags, mode)` as a fixed-argument method. On Apple Silicon, the created lock lacked the requested owner permission bits: the **same compiled 13-case test assembly** against the exact `e7aaddba` App DLL passes 11 and fails both new lock-creation-mode cases with **Expected UserRead|UserWrite; Actual None**. [Apple's ARM64 ABI documentation](https://developer.apple.com/documentation/xcode/writing-arm64-code-for-apple-platforms) places variadic arguments on the stack; that explains the observed mode mismatch. A separate ordinary-user Mac Python control using the native variadic `os.open` with the same flag values creates mode `0600`, reopens it in a child process and gets only the expected nonblocking lock contention.

The corrected implementation creates a fresh regular lock exclusively through `FileStream` with owner-only `0600` mode. If the usual lock already exists, it opens that pathname through the two-argument native `open` with nonblocking, no-follow and close-on-exec flags, then checks the opened descriptor's type before `flock`. Independent lock creation remains exclusive. A pre-existing FIFO is rejected without waiting. On the same Mac, replacing only the App DLL changes the 13-case class from **11P/2F to 13P/0F**. The original eight-scenario process validator, driven by a self-contained tool and an ordinary-user shim, changes **1P/7F to 8P/0F**, covering same and separate sessions, different and long temporary folders, different data folders, two independent owners, and a normal owner alongside an independent window. Final affected Mac recovery-safety is **27P/11 explicit skips/0F**, and state-save **2P/0F**. Final Ubuntu 26.04.1 App tests pass the same **13P**, **27P/11S** and **2P** classes; its original eight-scenario process validator also passes **8P/0F** with owned `/tmp` scratch and guest stage removed. Final Windows focused state/instance/recovery passes **28P/25S/0F**.
