# E-I536 — in-memory ZIP extraction duplicated the member payload

At base `610f6716eda4af60f8a1d627d4bf44cc70490e35`, `ZipIndex.Extract` preallocated a `MemoryStream` for a member below its 32 MiB in-memory threshold, then called `ToArray()` after extraction. A 16 MiB ordinary ZIP member therefore allocated both the extraction buffer and a second full member array before returning content. The new identical-input focused test fails against the old Core **0P/1F**: **33,895,768** bytes allocated on the current thread exceed its 25 MiB threshold.

The corrected source lends the extraction buffer to `MemoryContentSource` with its exact logical slice. The source reads only that slice, reports its logical length and releases its reference on disposal. When malformed declared-length metadata causes the buffer to exceed its logical length by more than the existing 1 MiB member slack, extraction still trims the overallocated array before retaining it. The same focused case passes at **17,118,528** allocated bytes, **16,777,240 fewer**; a second boundary control verifies that borrowed leading and trailing capacity cannot be read or reported as content. Both final focused cases pass **2P/0F**. The deterministic 16 MiB input SHA-256 is `2E0579BAB99707906AB85B1F66861A866175E6A2D39C8F55AEBCA15995E462D1`; the final test ZIP SHA-256 is `F72629755007110F48E6DB21DF551E5B49252865DAE817FDFEFE540DE8F112E4`.

The complete Windows Release Core run passes **4,161P/150 explicit skips/0F** (4,311 total); it compiled before the second small borrowed-slice test was added, which then passed in the final focused two-case run. The complete Release solution build exits zero with **47 warnings and zero errors**. This is a measured current-thread allocation reduction for one generated member, not an aggregate I06 budget or whole-process cap. Native installed UI and exact pushed-source hosted CI remain separate.
