# I613 — completing a deliberate SFTP host-key review should connect

**Status:** Remediated preliminarily at product `21f66f3d869d45c5242ae604e29205f0d72b05e9`. **Severity:** Medium UX, first connection to a new SFTP host can require an unexplained manual retry. Exact-source five-lane CI and the frozen installed-candidate check remain open. Public preview.5 predates this source; stable 1.0.0 remains NO-GO.

## Distinct user journey and failure

A person opens a PDF directly from a new SFTP server and compares the server's key fingerprint with an independent source before trusting it. This differs from the accepted remote-download-to-local viewer path and the accepted quick SFTP viewer route, neither of which held the first host-key dialog beyond the connection deadline. The owned 2,183-byte PDF SHA-256 was `A633D8D7C312DFB73F3779858019C070E9059574A5B4BB05C6D91046E6A3D9C6`; the local target began and remained empty.

In a disposable Ubuntu 24.04.5 VM, an isolated Xvfb FileCat package (App DLL SHA-256 `9CAE281681C121CA5D247875D4653ECA8E1A31730156701F2F188FA564C34A23`) opened `sftp://benny@127.0.0.1:22/tmp/filecat-cycle32-remote-pdf/server/`. The new-key dialog showed `SHA256:UeJys5LrKbfIVTAoZVRIjZh344WfGGWfFF5gTwC05oE`, which matched independent `ssh-keyscan | ssh-keygen -lf` on the owned server. The dialog stayed open longer than SSH.NET's 20-second connection clock. After **Trust and connect**, the panel said the host had not answered within 20 seconds; the user had to press Ctrl+R to see the PDF. A direct F3 then rendered page 1; Page Down rendered page 2, and Info reported PDF 1.3, two pages, current page 2 and 2,183 bytes. Those results established the PDF/SFTP route, but the first-connect retry was a separate UX failure.

## Correction and native check

The connector now grants **one** new 20-second handshake only when a person approved an exact host-key byte sequence after the first deadline. The approved bytes are compared on the new handshake, so a different offered key cannot inherit approval. Cancellation, rejection and an ordinary silent-server timeout receive no extra attempt. The reviewed approval is scoped to this one call; the normal trust store still owns lasting trust. The existing bounded connect timeout remains. A focused actual OpenSSH integration test on macOS ARM64 delayed the first approved key decision by 3.5 seconds against a three-second test deadline and passed **1/1**; the callback ran once and a fresh SFTP channel listed the owned directory. Windows x64 compiled the same test and skipped it explicitly because no test sshd was installed there.

A corrected `linux-x64` source publish at `21f66f3d` was built on the Mac and transferred byte-for-byte to the Ubuntu VM. The archive SHA-256 was `F56490B730DE48CF4E40B37A5C6B8160ED32A7FA92156AD412849C2CBDBD30EB`; `FileCat.Remote.dll` was `E5F75F7D24B321524D7BA17ACE794ED0F44F8E68A2F1FD570C75A24A9705E57D` and App DLL was `B10929D04393A87B796720C228F2A92A65A5F77145DB5F5437EBE686DDA6A024`. A fresh isolated profile and Xvfb app opened the same owned SFTP path. The host-key review was held from **00:52:26Z to at least 00:52:58Z**, exceeding the production 20-second deadline. Trust was accepted only after checking the same independent fingerprint. By **00:53:17Z** the remote PDF appeared in the panel **without Ctrl+R**; F3 opened its PDF viewer. The source SHA-256 stayed exact and the local folder stayed empty. The after-trust screenshot SHA-256 is `8BA99245A8D5041E62D391C8E2FCCC33DDD500B0E2807799E1DD746E83127783` (ignored `.tmp/pdf-proto/cycle33-sftp-aftertrust.png`). A transient scheduler notification said the host "responds again"; it did not prevent the result or require action. A future notification polish is optional and is not a new release gate.

Both isolated FileCat/Xvfb process pairs and their exact owned folders were stopped and removed under path/PID guards; the Mac build worktree and archive were likewise removed after hash verification. The Ubuntu source hash, empty target and absent-path checks passed. No unrelated user desktop or server files were changed.

## Finite candidate acceptance and stop

On the frozen 1.0.0 Ubuntu or macOS package, use one owned SSH server with an independently checked key and a small file. Hold the *first* key-review dialog beyond 20 seconds, approve it and require the first listing without manual Refresh, with the exact offered key and unchanged source bytes. A cancellation or different offered key must still fail closed; reuse existing host-key refusal coverage unless this candidate check supplies a consequential counterexample. Reconcile the exact-source five required CI lanes and expected tag-only skips. Stop after this bounded case; do not expand to arbitrary remote providers or long-lived trust from this observation.
