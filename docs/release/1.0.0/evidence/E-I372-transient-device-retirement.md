# I372 — transient device work retained idle scheduler and metadata keys

2026-10-12 CEST. **High resource issue; remediated preliminarily at committed `42ddc97`.** `DeviceIoScheduler` kept the final worker asleep indefinitely for every device key it had used, even after all its work finished. The per-device worker cap did not bound the number of keys visited during a long session. `MetadataService` separately retained a zero-valued outstanding-demand entry for every completed device key. These are key/worker lifetime defects, not evidence of a measured process-memory ceiling or of a source-device write.

At exact committed `df10ff0e34a09801fd4baabd793f7e710cb385ec`, with only a declared test overlay, twelve completed synthetic device jobs still had **twelve scheduler queue entries after the real 30-second idle period**; the new test failed after 37 seconds. The source's original idle branch removed extra workers but never the final one. A separate declared metadata test ran against unchanged `MetadataService` (while the scheduler correction was locally overlaid): twelve completed, available demands left **twelve zero-valued outstanding entries** after a five-second bound. Both failures and their raw TRX/logs remain retained. No device or network endpoint was opened by these tests.

The scheduler correction retires its final empty worker and removes that exact queue/key under the queue lock. A concurrent admission either wins the lock and wakes the worker or sees the retired queue and retries with a fresh one. Its usual 30-second timeout is unchanged; an internal per-instance timeout lets the focused tests exercise this boundary quickly. The metadata correction removes only an observed zero counter, so a concurrent increment survives. The existing backlog and cancellation paths use the same release logic.

The corrected scheduler class passes **six focused cases**. The corrected scheduler, metadata-demand and new counter tests pass **thirteen cases** together. A full Core run after the scheduler correction, before the metadata correction, passed **4,014 cases with 93 explicit skips and zero failures**. The first combined full Core run was **adverse: 4,013 passes, 93 skips, two failures**. One failure was a brittle assertion in the new test that all twelve keys must still be present immediately after work completes; under full-suite load eleven had already retired. The assertion now checks that all twelve jobs executed and that all keys eventually retire. The other failure was the existing owned SMB child input fence: only its `started` phase arrived before the 25-second bound. That test does not call the changed scheduler or metadata code; its cause is not established. The corrected new test and that SMB case each passed in an eight-case isolated run. A separate full Core repeat then passed **4,015 cases with 93 explicit skips and zero failures**. A final warning-only test edit supplied the test cancellation token; the thirteen affected cases passed again at that exact final local source. The adverse full run remains failed regardless of later results.

An independent reader parsed all nine raw TRX inventories, rehashed their source/log artifacts and baseline Git blob, and retained both failures separately. The full repeat used the pinned pre-warning-edit test source; the final focused run used the current test source. The final full solution builds with **41 existing warnings and zero errors**, with no warning in the added test. After commit `42ddc97e419d78beba9a2c4bde6e8c77da834bb7` was pushed, a separate no-overlay full Core run passed **4,015 cases with 93 explicit skips and zero failures** at the final test source. No test was replayed for the reader correction.
