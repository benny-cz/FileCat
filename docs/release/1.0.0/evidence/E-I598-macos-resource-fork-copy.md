# I598 — macOS Copy silently dropped a resource fork

## User consequence and distinct scope

On an isolated Mac ARM64 exact-I597 build (`3bf3447705e3e5ef89a7b54ea12730be4a1fda3b`), FileCat copied owned `forked.txt` into an empty target and reported **Completed · 16 bytes**. The source and target data forks both had SHA-256 `af7e07e1b67f2dd17e5d6461f2c63431acac8d29aff845d361275c34a203b1c2`, but the source's `com.apple.ResourceFork` held 19 bytes (`resource-fork-owned`) and the target had **no such attribute** or named fork. The unrelated `neighbor.txt` remained SHA-256 `efada34372b0f05dd42e68072da69e91d7421e03fb5bf0a9a4f194ceb1099d55`. The source remained intact. This is silent file-content loss, not a mismatch in the ordinary data-fork hash.

Prior Mac quarantine-origin transfer, Windows alternate-stream controls and generic byte-copy checks do not establish macOS resource-fork preservation. The portable copy engine streamed only the data fork and set times/mode afterward; its Mac origin-mark follow-up covered `com.apple.quarantine`, not the resource fork. The before package was the signed exact-I597 exploratory ZIP SHA-256 `1059e11bb7b3c8615ddc3304f5112c2d77b75c9efa9e60088eb975150cb3138e`.

## Correction and bounded verification

Product `754f8f6ac07edf5daa0566305e3b44e07adff889` calls macOS `fcopyfile(COPYFILE_XATTR)` on the same held source and create-new destination descriptors after streaming the data fork and before publication. It checks the destination resource-fork size against the source. Any native error, missing fork or cancellation makes the existing copy engine remove its newly created destination and report failure; a move does not reach its source deletion. Other platforms retain their copy route. The call may delay cancellation during a very large native attribute copy; cancellation is checked before and after it, and full publication is withheld until it returns. This is a bounded limitation, not an assertion of instant cancellation.

The focused Mac Core test passed **1P/0F/0S** with a nontrivial 128 KiB resource fork and another xattr, requiring byte-exact data/fork and metadata equality. The same test compiles and skips as platform-specific on Windows x64 (**0P/0F/1S**). A fresh exact-source Mac package ZIP SHA-256 `6f1f721d7c55404ef790d90f9c181f16443c11b626e10bce6de3e2b14da82c39` was extracted and ad-hoc signed; strict deep verification passed. Native FileCat focused the same owned `forked.txt`, reviewed the exact empty `target-after/` path, and completed Copy. Independent SHA-256 of both data forks remained `af7e07e1b67f2dd17e5d6461f2c63431acac8d29aff845d361275c34a203b1c2`; both named resource forks had SHA-256 `a43d8923663955bebd67b7c2107630893b470961ded786062ad6a9c194172349` and `xattr -p` returned `resource-fork-owned` on each. Source and destination both reported 16 logical bytes and the same modified timestamp; the target contained only `forked.txt`, neighbor hash stayed exact, and the isolated process exited. The original failed target remains in the owned fixture for contrast, not as a release artifact.

## Disposition and finite candidate rule

**High data-integrity issue, remediated preliminarily.** On the exact installed macOS 1.0.0 candidate, copy an owned file with a known data fork, resource fork and one harmless extra xattr to a fresh APFS destination. Require a completed FileCat report, exact data-fork and resource-fork SHA-256 and retained extra xattr; source and neighbor must remain unchanged and no staging item remain. Exercise a normal file without a fork as the positive control. If destination metadata cannot be retained, require a visible failed item and original kept, with no successful but forkless copy. Stop after those affected routes and latest-product producer plus four-platform CI with skips reconciled; do not replay accepted Windows ADS, origin-mark or unrelated copy cases. Network/removable file systems and very large fork cancellation remain separate if a concrete failure appears. Public preview.5 predates I598; stable 1.0.0 remains **NO-GO** pending all candidate gates and explicit owner GO. The two preceding clean Mac journeys become historical and the active clean streak resets to **0/20**.
