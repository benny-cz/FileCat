# E-I470 — preserve a download mark added during ZIP update

2026-10-14 CEST. **Preliminary High correction within V04/V07/V23.** At exact parent `485744b9dcd28e5634233046a8638bcaf3488fc9`, a ZIP update read an owned archive as unmarked, then another actor added a real Unix download xattr without changing the ZIP bytes or its last-write time. The original implementation kept no backup for an initially unmarked update. The identical controlled archive class on ordinary-user Ubuntu and macOS each reported **10 passed/one failed**: the update completed and the published ZIP had no mark. The test requires the mark to be readable before checking job status, so its failure is the lost metadata itself. The exact parent package SHA-256 is `8c15b5366d8c394f8631c540e816b10a864c475edade05148784f7862108d0b4`; the first native launch used a Windows-CRLF shell script, failed before tests, and was retained separately with cleanup.

The update now always asks `File.Replace` for a same-folder backup of the actual original, including an original that was unmarked at the earlier read. It reads the backup mark after replacement. If that mark differs from the earlier value, or a marked replacement loses its mark, it restores the backup as a whole and checks the restored mark. An unreadable backup or unverifiable restoration produces an Uncertain security outcome rather than success. This closes the controlled read-to-replace mark change, not arbitrary later external mutations or a simulated restoration I/O failure.
