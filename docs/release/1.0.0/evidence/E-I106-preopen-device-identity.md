# I106 — whole-disk identity between selection and first open

2026-10-12 CEST. **Preliminary Windows virtual-device remediation; I106/I110 physical-source validation remains on HOLD.** This is a different race from the [held-reader VHD control](E-I106-virtual-device-reuse.md). With exact clean `1b86024` product source, FileCat selected owned read-only 64 MiB VHD A as `PhysicalDrive1`, without opening a read handle. A was detached and distinct, same-sized read-only VHD B took disk number 1. The recovery provider's length-only check then opened and scanned B, listing one volume without an exception. No copy, helper or physical source was used. The original raw result and guest restoration are independently pinned; this adverse outcome is not reclassified.

A separate native control queried `IOCTL_STORAGE_GET_DEVICE_NUMBER_EX` on zero-access discovery and read handles for each VHD. Both handles agreed within A and within B; the device GUIDs differed across A and B even though disk number and size were reused. `Win32_DiskDrive.SerialNumber` was null and `Signature` was zero for both in the earlier control, so those fields could not bind this case.

The declared source overlay now captures the Windows device GUID while listing whole disks, refuses a disk with no verifiable GUID, and passes the chosen GUID to the recovery provider. After the actual direct reader or elevated helper protocol opens the disk, the provider compares the identity of that held handle before the first scan read; mismatch or unavailable identity closes the source and refuses the scan. The original size check remains. Ten focused source-selection tests pass, including same-size changed/unknown identity refusal with zero reads and a matching-identity read. The host solution compiles with zero errors and existing analyzer warnings; the private probe build retained one unrelated `WindowsBase` conflict warning.

In the Windows 11 VMware guest, an owned A→B read-only VHD replacement produced **zero FileCat reads and zero entries** through both the direct reader and the actual `RawReadProtocol` pipe server; both routes reported B's same GUID from their opened handles and refused the selected A identity. A separate unchanged-A native control completed both scans: each route read 15 times and listed one volume, with the selected and opened GUID equal. The VM returned to boot disk 0 only; owned payloads, VHDs and processes were removed. The first packaging attempt stopped on a private path-construction error, and the first successful replacement probe observed the helper identity only after pipe disposal; both remain retained and were corrected by the later pinned runs. These are **precommit virtual controls**, not actual UAC-helper, physical USB, installed candidate or cross-platform identity qualification. A physical medium could expose weaker identifiers or cloned hardware IDs; the historical source-hash/capture-attribution failure still blocks FileCat physical-source validation. No contract freeze, candidate or GO follows.
