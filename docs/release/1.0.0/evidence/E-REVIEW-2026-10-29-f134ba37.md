# E-REVIEW-2026-10-29-F134BA37 — recheck of Codex's security-plan execution commit

The owner asked the release session to recheck the concurrent Codex agent's work once it lands. `f134ba37517b45335b1bfd9cfd286c5115934c26` ("Execute FileCat security plan with bounded native protections", 29 October 07:33 +0100) implements acceptance cases AC-15–44 of the [security plan](../../../security/FILECAT_SECURITY_REVIEW_AND_PLAN.md) for FCSEC-012–041. It touches 139 files (+4,848/−228): 44 product files, their tests and 36 security evidence records.

- Windows platform, Shell host and App;
- Core jobs, file system, sync, state and remote;

**Owner decision since the recheck.** `2b62355f` records the owner's choice, in the security session, to keep "safe refusals" for two policy questions:

That part of F-H2 is therefore accepted product policy, not a defect: Linux and macOS Replace, and the Sync updates that need it. The rest of F-H2 is outside that decision and stays below.

## Medium

F-M3 (C5) is now F-H9 above.

- **F-M1 (C3).** The destination review (a full read and SHA-256, up to 64 MiB) runs before the conflict answer or policy applies (`Executors.cs:685, 971`; `StreamTransferExecutor.cs:348`). Skip and Keep both therefore read every existing destination, and each replaced file is read three times.
- **F-M2 (C4).** `TreeCompare.cs:142-145` does not charge failed captures to the 256 MiB comparison budget. Each one-sided folder over 64 MiB reads up to 64 MiB on every Compare, outside the device scheduler and its stop check. Source-side items share the budget, so many new source files can make Mirror silently keep target-only items.
- **F-M4 (C6, W6).** Windows permanent folder delete now runs through `SecureFileOps.DeleteTree`. Read-only files inside the tree are deleted silently (`IgnoreReadOnly`) without the old confirmation, and a child that antivirus or the indexer holds open fails at once, with no retries. `DeleteTreeBound` catches nothing: `IOException`, `UnauthorizedAccessException` and `Win32Exception` from `Walk`, `ToVolumePath`, `GetBasic` and `List` fail the whole job, and the remaining roots are skipped with no Retry or Skip.
- **F-M5 (P3).** The two new Markdown tests cannot fail (`HtmlPageTests.cs:89-91`, `MarkdownTests.cs:13-15`). Their hostile line is rejected in 0 ms by the regex the commit replaced. FCSEC-038's own trigger takes 1.08 s at 64K, under the tests' 5 s limit, so restoring the vulnerable regex passes both. The SFV tests do discriminate.
- **F-M6 (P4, W8).** ZIP add now holds each source with read sharing only (`ZipUpdateExecutor.cs:478` → `LocalIconFileLease.cs:36-37`). A file another process has open for writing (a live log, a database, a download) fails as "contains a link or cannot be held", and one such file aborts the whole Pack or Add. Any junction or mount point on the source path is refused the same way.
- **F-M7 (P5).** `Ntfs.cs:19-20, 259, 273-278`: the caps of 100,000 compression units per file (≈6.1 GiB) and 250,000 per scan (≈15.3 GiB, in MFT order) turn later legitimate compressed files into name-only results. The previous per-file limit was 10 million units.

## Low

- **C7.** F2 rename with a Replace answer still calls `Fs.Move(src, dst, replace)` without a destination review (`Executors.cs:2049-2067`). It is narrowed by the UI pre-check but not closed.
- **C8.** The bound replace renames through handles without write-through, dropping the contract "replacing always writes through" (`Executors.cs:1174`). After a power loss, a cross-volume Move's data may survive only under the staged name, which interrupted-job review offers to delete. Plausible.
- **P6.** The 64 Mi-character name budget rejects a whole large archive where the 1M-entry cap only truncated. `ArchivePaths.TooDeep` counts a directory entry's trailing `/`, so FileCat's own empty folder at depth 256 makes every later update of that ZIP fail.
- **P7.** The mDNS per-datagram budget counts label bytes, not allocations: about 20–45 MB of transient allocation per datagram. Plausible.
- **P8.** At high integrity, verification returns no state, which the metadata view shows as "nothing covers it". This includes a file whose sidecar says it differs.
- **W9.** If cancellation arrives after the old target was moved aside and restoring it fails, the step is journaled as canceled before any change. The backup path then survives only in the reason text.
- **W10.** Types drawn by an icon handler or a packaged app show the stock icon in every session, and `.lnk`/`.url`/`desktop.ini` on removable or network drives lose their icons. Plausible.

## Checked and sound

- **AC-15:** compared deletion binds identity and SHA-256 through no-write handles.
- **AC-31:** the core protocol holds: a handle that denies writers, the old file moved by handle to a journaled recovery name, publication that refuses to overwrite and restores on failure, and a substituted file surviving. The `replacement-recovery` record is written before the rename, and review lists it without deleting it.
- **AC-33:** child identities are snapshotted and links rechecked relative to handles.
- **AC-21/R-M5:** server-to-local Move no longer deletes server originals.
- **AC-16–18, 22, 24, 25, 27, 29, 38–40:** their high-integrity refusals hold.
- **AC-19:** Git is never started at high integrity.
- **AC-32:** its set-based ancestor checks are equivalent to the old scans.
- **AC-43:** linked components on icon, resource and type paths are refused.
- **FAT:** table capacity is checked before allocation.
- **NTFS:** the run lookup gives the same results in one pass.
- **SFV:** the parser accepts exactly what the old regex did, in linear time.
- **Markdown:** the table-delimiter check is equivalent and linear.
- **Archives:** the depth and generated-directory budgets are checked before anything is kept.
- **Spool:** the elevated in-memory spool is capped at 64 MiB.
- **mDNS:** the label and name limits hold.
- **Cancellation:** it propagates through Sidecars, the checksum manifest and HtmlPage.

Side effects of the high-integrity refusals, recorded for the owner rather than as defects:
- An administrator with UAC disabled always runs at high integrity, so FileCat never loads its state, and SFTP is refused without a prompt.
- The certificate dialog's Trust button throws inside the TLS callback at high integrity.

## Fixed by the release session alongside this recheck

FileCat's own archive readers, its SharpCompress build and its RAR reader are release-session code, so these were fixed there ([record](E-I557-archive-pass-budget.md)):
- **R-H5:** a packed 7z header is no longer allocated at the size it claims.
- **RAR-SEC-001's class in 7z and compressed TAR:** members a reader must pass were decoded without the expansion limit (I557).
- **A 7z member read only in part** shifted the next member of its folder (I558).
- **I559, in Codex's RAR-SEC-001 correction (`a718c777`).** That correction holds each passed member of a solid run to its own limits and the run to the expansion ratio, which is sound. But it also capped the run at 8 GiB, the limit for a member of unknown size, and counted bytes the reader had already returned. So a solid RAR with a member over 8 GiB could no longer be read past that member, not even in archive order. Observed and fixed by the release session; see the record.
