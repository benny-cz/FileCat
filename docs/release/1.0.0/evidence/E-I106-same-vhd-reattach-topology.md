2026-10-13 CEST. This is a **virtual-only topology observation**, not a FileCat product pass or defect closure. In the authorized Windows 11 VMware guest, a bounded script first required exactly one boot/system disk. It created one owned 64 MiB expandable VHD, mounted it read-only, captured disk number, storage UniqueId and PnP interface path, dismounted it, and remounted the **same VHD file** read-only. It then dismounted and removed only its owned files. No physical USB or FileCat recovery source was opened.

The second attachment reused disk number **1** and the same storage UniqueId `60022480007260305D2AE42B1D9FD635`, but its interface path changed from the `...000003` instance to `...000001`. The guest returned to its original sole 200 GiB boot disk, and all three owned guest script/root/result paths are absent. The first automation attempt stopped at a precondition because VMware required the VM encryption password; the corrected attempt supplied it without retaining either password and completed. This control does **not** show that a same-interface collision cannot occur under other hardware, snapshots or races. It only shows that reattaching this VHD through Windows' virtual-disk driver did not create one.
