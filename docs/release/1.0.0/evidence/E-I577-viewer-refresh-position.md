# E-I577 — keep the viewer's place on Refresh

31 October 2026. The owner asked that Refresh keep the previous position when the source can be reopened, including edge cases in several viewers. This follows the accepted F5 source-reopen behavior; it reopens that scope only for the consequential viewport loss in rendered Markdown/HTML Page. The work is based on `e937db4e` and is not an installed 1.0.0 candidate.

Text and Info already retained their top offsets, Hex retained its cursor, and Picture retained Fit or numeric zoom with approximate pan center. The rendered Page instead navigated to the new content at its top. Refresh now captures the actual Page viewport before replacement and restores it after the new page loads. The browser clamps the old coordinates when the page becomes shorter. A failed replacement reloads the old page and restores its prior viewport; a source that changes again during loading also rolls back. If a backend cannot measure a position, Refresh still proceeds without treating the optional restoration as a content failure.

The host-only viewport query uses fixed application code and finite, nonnegative coordinates. On Windows, WebView2 executes it with content scripts still disabled. On Ubuntu/WebKitGTK, a named sandboxed native test verifies that enabling host evaluation with JavaScript markup disabled does not run the page's `<script>` or `onload` code; the older engine fallback keeps all scripts disabled and cannot preserve Page scroll. On macOS, `WKWebpagePreferences.allowsContentJavaScript=false` blocks page code while the host evaluation works; older WebKit without that preference keeps all JavaScript disabled and skips Page restoration. [Apple documents the separation between content and app JavaScript](https://developer.apple.com/videos/play/wwdc2020/10188/).

## Focused results

- Windows Release App `ViewerRefreshTests`: **8 passed, 0 failed**. It checks Page success, failed-load rollback and short-page clamp, plus Text/Hex same-revision selection, changed and shortened bytes, Info replacement/failure, Picture zoom/center, provider reopen and close during a pending reopen.
- Windows hidden native WebView2: **1 passed**. It captured `(200, 1200)`, restored that viewport after a long replacement, and clamped to the top of a short replacement while a page script did not run.
- Disposable Ubuntu 24 VM, native WebKitGTK under a temporary named AppArmor `userns` profile: complete `LinuxPageEngineTests` **13 passed, 0 skipped, 0 failed**. The new viewport case restored about 1,200 pixels on the long page and clamped to the top on the short page; its script and `onload` title changes did not run. The original offscreen sandbox/network/script case also passed. The unprofiled Ubuntu desktop cannot display Page under the distribution's restricted-user-namespace policy, so that state is not presented as a Page UX result.
- Mac native `FileCat.PageEngineSmoke`: **PASS**. Host restoration returned `(0, 1200)`, then `(0, 0)` on the short page; its script and `onload` title changes did not run. All 12 two-navigation lifecycle rounds passed without post-disposal events. This is native WKWebView engine verification, not a full FileCat GUI journey; the Mac display was asleep during the session.

## Candidate stopping rule

Keep this source in the 1.0.0 candidate only if the five required CI lanes pass with skips reconciled. On the exact installed candidate, open a long Markdown Page, scroll, change the file and press F5; require the same approximate viewport, then shorten it and require a reachable clamped position. Repeat a failure/retry once, and spot-check Text, Hex, Info and Picture anchors on owned files. Stop at those affected modes; do not replay unrelated viewer or archive suites. Signing, installed-candidate input and final release approval remain separate.
