# E-I428 — held recovery content rechecks the selected device path

2026-10-13 CEST. **Preliminary High source-correctness correction within I106.** Exact preceding source `bfcb6887fd84039bf054a76ab58727346486380e` verifies a recovery device while opening deleted content, but an already-open `RecoveryContent` has a content-read callback only for disk images. A selected device path can change after the content handle opens and before or during a later read. The listing and transfer-destination guards do not cover a held QuickView/preview content read.

One owned FAT image with 4,096 nonzero deleted-file bytes and a controlled `IDevicePathGuard` supplies two identical-test baselines. The preceding Recovery assembly returns all **4,096 original bytes** with no exception when the path changes before the read, and again when the guard changes during the source read: **0P/2F** against the new expectations. The same test class is **16P/0F** after `OpenContent` passes the held device's existing listing/path verifier into `RecoveryContent`, which invokes it before and after each read. The unchanged image-content verifier remains selected for images. A change before reading causes zero later source reads; a change during reading throws before the content read reports success. The test retains exact original bytes, read counts, both raw TRX and the owned-image cleanup.

The Windows VM comparison uses actual `DirectDeviceSource` and actual `DeviceReadHost`/`PipeDeviceSource` on four fresh owned 128 MiB FAT32 VHD pairs.
