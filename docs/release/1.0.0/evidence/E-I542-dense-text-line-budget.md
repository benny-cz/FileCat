# E-I542 — bound newline-dense text comparison before line-list allocation

At exact pushed base `c36b0ee0686b6ac1a10634ddcc58ab7fe59dd6ec`, `TextSide.Load` limited input to 64 MiB of encoded bytes, but `TextSide.FromText` had no line-count limit. A **1,000,001-byte** owned input consisting only of newline characters was accepted and materialized 1,000,001 line entries. The direct `FromText` control measured **33,555,584 current-thread allocated bytes** after its input string already existed. A larger byte-bounded input could grow those lists much further. The App's comparison view first computes exact binary results, then builds optional text lines, so this is a transient memory and availability gap in I06/V13 rather than evidence of incorrect binary equality.

The correction preflights CR, LF and CRLF terminators before allocating either line list, refuses more than **1,000,000** lines with an `InvalidDataException`, and keeps the documented million-line boundary available. The Compare window catches this text limit, retains its exact byte result, and explains that the user can compare as binary. The same compiled three-case Core test assembly was run with only the Core DLL swapped: the old DLL yields **1P/2F**, accepting both the direct and loaded 1,000,001-line inputs; the corrected DLL yields **3P/0F**, rejecting those inputs while accepting exactly 1,000,000 lines. The direct refusal allocates **680 current-thread bytes** after input construction. This measurement isolates line materialization; it is not a whole-process peak or an aggregate I06 budget claim.

On the final local Windows x64 source, affected Core comparison classes pass **32P/0F**, and the complete Release Core suite passes **4,175P/150 explicit skips/0F** of 4,325 tests. The headless App comparison/SFTP set passes **24P/0F**, including a 1,000,001-line window that reports byte-for-byte identity and the text-limit fallback. The full Release solution build exits zero with **184 recorded warnings/zero errors**. The I524 SFTP case's presence in that affected App set is one x64 pass, not evidence of an ARM64 acknowledgement fix.
