Source spot checks covered `PictureDecoder`, both Unix picture sandbox launchers, `WindowsContextMenu`, `GitStatusReader`, `SmbTools`, `IShellServices`, `ToolLauncher`, `ApplyCommand`, and `FreedesktopIcons`. The Linux theme-icon decoder loads desktop-theme assets in-process from configured icon roots; browsing a file does not itself supply icon bytes. This is an exposure distinction, not a general parser-safety pass. The Windows context-menu evidence constructs a real native menu but does not invoke a verb. Neither route justifies reopening an accepted picture or WebKit child without a new, demonstrated input path or failure.

The review found an actionable **claim mismatch**, not a new product failure: `docs/CAPABILITIES.md` and the preview.3 notes still said Linux picture workers retained ordinary-user filesystem/network rights, and the README repeated a vague Unix filesystem caveat. Accepted I550/I552 and the later Linux metadata-denial correction predate the immutable preview.3 source (`8320e18a`). The public-facing text is corrected to describe Linux x64/ARM64 and macOS picture restrictions while retaining the absence of a Unix OS whole-process memory limit and the different boundaries of other parser/helper routes. The private draft's notes must match the corrected file before any public decision; its asset set and tag are unchanged.

**Stop rule for this step:** preserve the accepted child results. Resume a specific child only for a documented consequential source, package, OS-policy or input-route change. Do not mark any parent Accepted until the exact installed-candidate observations above pass and their failures/skips are reconciled. Candidate creation itself remains blocked by signing/provider and other release prerequisites; no source-only or preview.3 observation substitutes for that gate.

## Next prerequisite: Windows signing

The current [SignPath Foundation terms](https://signpath.org/terms) were checked on 2026-10-30. They require an eligible project to have already been released in the form to be signed, plus provider acceptance and manual approval for each signing request. The [GitHub trusted-build documentation](https://docs.signpath.io/trusted-build-systems/github) describes the origin-bound integration. FileCat has a CI signing placeholder, not provider acceptance, roles, policy, credentials or a signed candidate. The preview.3 draft is verified but the owner explicitly kept it private. Therefore the chosen SignPath Foundation route cannot be advanced to signed RC production by this review. A later exact public-preview decision would need to supersede that choice, or the owner would need to choose and supply a different signing route. No provider acceptance or legal eligibility is inferred from these terms.
