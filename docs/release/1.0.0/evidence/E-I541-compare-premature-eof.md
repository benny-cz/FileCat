# E-I541 — refuse equality or complete differences when comparison input ends early

At exact base `2a0e4fc229b9b4937162a6e50fc72ded30e7b5fd`, `BinaryDiff.Compare` treated the first zero-byte read as normal EOF even when `IContentSource.Length` advertised more bytes. Two matching truncated prefixes could therefore be reported `Equal`. It also trusted a longer file's advertised tail after reading just the first chunk, allowing a complete difference range to be reported without reading that tail. `TextSide.Load` accepted an incomplete prefix, and next/previous difference navigation could return no difference after a short required read. These cases affect comparison integrity when a local file shrinks during reading or another content provider ends early.

The corrected binary comparison snapshots known lengths, asks only for the remaining advertised bytes, reads the longer tail, refuses premature EOF, and checks that known lengths did not change before reporting. Difference navigation refuses a short required read. Text loading requires the full known length; unknown-length streams retain their genuine EOF behavior. The input remains read-only and the comparison window reports an I/O error instead of claiming equality or an unverified complete difference.

Six old failures cover binary equality, the unread longer tail, text prefix loading, both difference directions, and two owned NTFS files truncated from 8,192 to 4,096 bytes just before their first read.
