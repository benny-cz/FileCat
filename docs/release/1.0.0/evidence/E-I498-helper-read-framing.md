## Same-test failure and correction

`PipeDeviceSource.Read` previously threw on an out-of-bounds reply count but left the pipe usable without consuming the malformed reply's body. A scripted stream reports 5 bytes for a request of 4, then leaves those 5 bytes followed by a complete later response. The next `Read(0, fourBytes)` consumes the leftover body as a header and returns `00 04 00 00` as file content, rather than the later response's `A1 B2 C3 D4`. The raw original-product result records **two read requests, no second error, and `SecondBytes:"00040000"`**. A reply that stops after two of four declared payload bytes also allowed a second request on a broken stream. A successful zero-byte reply at byte 100 of a described 4,096-byte source returned zero rather than rejecting the impossible short read. A nonzero error status accompanied by content likewise left the session reusable. The ordinary protocol error, status 5 with zero payload, could be retried correctly and is retained as a positive control.

The correction makes malformed counts, error replies with payloads, incomplete payloads, and a successful zero-byte reply before the declared end terminal to that read session. It preserves the ordinary status-error retry. The **same compiled five-test assembly** against the exact parent Platform DLL gives **1P/4F**; against the corrected Platform DLL it gives **5P/0F**. The test DLL SHA-256 is `f63a97dc1da429aebe47362d8f3f86fb7b29a644f1acbe1a4245b10d6bbee02f` in both runs. The parent and corrected Platform DLLs are respectively `3c50476b92e9c39e80142618329e951e7c1f3dee8a38cd5970265617f5b64b06` and `da83db4145db9c2a6dcdda5d12508782a015692acc7fbfd98ff594d0f8d5fce3`. The paired source hashes are `af826537821d11fa9ca554efb761c2ff1dae7a23cf4ddeae5f56a1531679ecfa` and `69b44e874047927769acbef4df0ee45f979acaa13c459e028a8f41da06aa5d29`.

The correction also passes **35/35 affected helper, held-device and valid-read controls**, then the final non-PageView headless Platform suite passes **407P/46 explicit skips/0F**. A final `dotnet build FileCat.slnx -c Release --no-restore -p:MaxCpuCount=2` has **zero warnings and zero errors**. The fake stream is a bounded byte protocol control; the affected valid-read tests include the actual `RawReadProtocol.Serve` over a named pipe, but no live helper fault or user dialog is claimed. The earlier two- and three-case failed discoveries and their corrected focused logs remain retained alongside the final pair.
