# I595 — valid JPEG EXIF reported as unreadable

## User consequence and distinct scope

An expert opening an owned `rotated.jpg` in the exact-`ccf7b64c` native Mac viewer saw **JPEG · 20 × 40 pixels** in Picture mode, then **Dimensions 40 × 20 pixels** and **Orientation rotated 90° clockwise** in Info mode. The same Info heading nevertheless warned **The EXIF block could not be read**. That contradictory damage warning can make a user distrust a valid image or misstate a forensic result. Previous `PictureViewerTests`, `PicturePixelFidelityTests` and `InspectorTests` covered orientation and header parsing separately; they did not cover this native Picture → Info interpretation of a JPEG with two valid APP1 EXIF blocks.

The 953-byte test file contains an orientation-6 little-endian EXIF block and a second, big-endian EXIF block whose main directory holds an ExifIFD pointer with no orientation, camera or date field. Apple's ImageIO independently reported **orientation=6, width=40, height=20** for the same exact file. SHA-256 was `ab401f793029fc9346fed30f059f1fc78297cca0d50ef9039b424759a382f7d8`; an owned empty target stayed empty. The isolated before-state process was stopped.

## Correction and bounded verification

Product `a4a93528` checks the EXIF/TIFF byte order, magic, directory offset and bounded entry table separately from the subset of fields FileCat displays. A well-formed EXIF directory with no displayed fields no longer produces a corruption warning; when it is the only readable EXIF content, Info states that EXIF is present without the displayed orientation/camera/date fields. A malformed directory retains the unreadable warning. This does not expand FileCat's EXIF interpretation to arbitrary nested tags.

A focused Core test failed **0P/1F** before the change and passed afterward, including a malformed second-block control. The affected `InspectorTests` class passed **21P/0F/0S** on Windows x64. A clean Mac checkout at exact `a4a93528ebaec3d071b00d281737e71c84407ff4` built package ZIP SHA-256 `4dfccb16f8ac6f742e579ce308bd21f0b551aa12161ac4300b2f6a66575c7220`; staged `FileCat.Core.dll` SHA-256 `f144b022a8c86475909fb29d741b624364cf61321513d316c0000c9f2bd57031`. The extracted bundle passed strict deep code-signature verification. A fresh isolated native app showed the same oriented Picture status and the Info orientation/stored dimensions **without** an EXIF warning. All three owned source files retained their before SHA-256 values (`base.png` `907f9339569cea6b3de76917b336509868c1f09bc7766fdd246b98cc765a8bee`, `base.jpg` `a5b20e62fc42c447927021f95153f66a6b9c5fe3d5cbc928c8197706764f1331`, and `rotated.jpg` above); the target remained empty. The isolated after-state process was stopped.

## Disposition and finite candidate rule

Medium evidence-clarity issue, **remediated preliminarily**. On the exact installed 1.0.0 candidate, inspect one owned valid JPEG with a recognized orientation and a second valid EXIF directory with no fields FileCat displays. Require Picture to use the oriented dimensions, Info to state stored dimensions and orientation without an unreadable warning, and source hash/target to remain unchanged. The focused test must still warn for a malformed EXIF directory. Stop after this affected route and latest-product five-lane CI with skip reconciliation; do not run a broad EXIF corpus without a new anomaly. Public preview.5 predates I595; stable 1.0.0 remains **NO-GO** until all candidate gates and explicit owner GO. This finding resets the exploratory clean streak to **0/20**.
