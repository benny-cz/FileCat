## Certum's 2026-11-02 reply and workflow consequence

The owner supplied Certum's reply: prices and verification documents are at the [Certum code-signing shop](https://shop.certum.eu/code-signing.html) and [required-documents page](https://support.certum.eu/en/code-signing-required-documents/); Certum defers CI compatibility to the environment provider. A PFX is unavailable because the private key stays on Certum's physical or virtual card. A physical card requires its PIN when signing; the cloud route requires an owner-generated mobile token to log into SimplySign again every two hours. This reply is evidence of the workflow constraints, **not** certificate issuance or FileCat-specific CI approval.

Certum's [cloud-signing guide](https://files.certum.eu/documents/manual_en/CS-Code_Signing_in_the_Cloud_Signtool_jarsigner_signing.pdf) documents Windows `signtool` by certificate thumbprint, RFC 3161 timestamping, a possible card PIN prompt and batch signing in one session. [SimplySign Desktop](https://support.certum.eu/en/installation-of-the-simplysign-applications/) must run on the signing computer. [GitHub-hosted jobs](https://docs.github.com/en/actions/how-tos/write-workflows/choose-where-workflows-run/choose-the-runner-for-a-job) start on fresh runners; installing a certificate into one job cannot make it available to a later job, and an unattended PFX-secret design is unavailable. GitHub [warns against persistent self-hosted runners for public repositories](https://docs.github.com/en/actions/reference/security/secure-use) because untrusted workflow code could compromise the signer. Therefore the current hosted package job remains an **unsigned input producer**. The practical route to assess is an owner-attended, isolated Windows signing station after the hosted build, with a separately protected promotion/verification flow. This is an inference from Certum's and GitHub's documented behavior, not a provider guarantee of compatibility.

Before selecting Certum or creating an RC tag, the owner must approve a change to the SignPath-specific D-40/section 10.4 signing contract. The replacement must retain immutable source identity, protected review, exact unsigned-input and signed-output manifests, signer identity, timestamp, chain validation, final installed bytes, Smart App Control and a separate final GO. A manual signature without those controls cannot qualify stable 1.0.0.
