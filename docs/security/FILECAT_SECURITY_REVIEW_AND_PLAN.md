### Assets and boundaries

Assets are file bytes and metadata, selected source/destination identity, private transfer stages, undo/journal state, recoverable deleted content, remote credentials and trust records, settings and diagnostics, and signed release inputs. The ordinary desktop process may browse hostile local/archive/remote names and contents. Explicit F4/open/tool actions cross into external process execution; an elevated desktop process has a larger token than the ordinary user context. Windows privileged operations cross the native bootstrap, immutable plan, consent and named-pipe boundary. Picture/Shell workers parse less-trusted input with platform-specific authority. ZIP/other archives, recovery images/devices, HTML/Markdown/images, clipboard/drop data and remote protocol replies cross parser, namespace and publication boundaries. Build and installer paths cross dependency, loader, signing and artifact-promotion boundaries.

The original audit's two material High scenarios were distinct. For FCSEC-001, another ordinary process (or concurrent user workflow) changed a selected local path during an explicitly approved remote **Move**; FileCat could delete a replacement never uploaded. For FCSEC-002, a medium-integrity actor in the same Windows account could control an implicitly chosen per-user editor path while the victim ran FileCat elevated and pressed F4; FileCat launched a high-integrity child. FCSEC-003 concerned a raw path logged during a failed sidecar scan. Their accepted corrections have the §8 scopes. The current threat paths add an external drag source's Move completion contract (FCSEC-004), a compromised SFTP host key later revoked in OpenSSH (FCSEC-005), medium-authored persisted tool settings consumed by a high-token process (FCSEC-002-R1), and an attacker-writable file whose stale verification badge encourages trust (FCSEC-006). A genuinely user-selected tool, deliberate shell command or explicit file open is not by itself an exploit; the FCSEC-002-R1 problem is that the elevated session cannot establish who authored its persisted executable definition.

Network use from configured FTP/SFTP connections and the opt-in update check is intentional. `SECURITY.md` excludes an attacker who already has administrator rights; it does not erase a medium-to-high integrity transition induced by a lower-privileged actor. The source contains no public web server or automatic updater. Deliberate remote operations and media/recovery use remain subject to their explicit choices.

### FCSEC-001 — substituted local source deleted after remote Move

**Invariant and trace.** A Move may remove only the local bytes it actually copied and published. `src/FileCat.Remote/Sftp/SftpJobs.cs:14-29` registers the shared upload executor; `src/FileCat.Remote/Sftp/Connections.cs:49-52` selects SSH or FTP transport, so SFTP, FTP and encrypted FTP variants use it. `SftpJobs.cs:411-428` reads `FileSystemItemInfo`, opens the local path with `FileShare.Read | FileShare.Delete`, and defines `unchanged` as size plus `ModifiedUtc`. The upload checks that predicate at `:704-705` and `:723-725`, then publishes. For a Move, `:429-438` checks only size/time once more before `Fs.DeleteFile(local)`. The portable implementation calls `File.Delete(path)` (`src/FileCat.Core/FileSystem/FileSystemOperations.cs:394`); Windows calls path-based `DeleteFileW` (`src/FileCat.Platform.Windows/WindowsFileOperations.Native.cs:321-324`). Neither deletion binds the pathname to the opened/uploaded object. An ordinary peer can replace A at that path with B of the same size and timestamp after the last upload check; A is remote, B is deleted locally and was never copied. A sync client, editor or another file operation suffices; no malicious server or privilege is needed. Scope is one selected file per race, potentially consequential user data. The code establishes the failure path; this audit did not execute the race or establish its frequency.

**Existing controls and lineage.** I49 (`docs/release/1.0.0/FILECAT_1_0_RELEASE_ISSUES_I001_I299.md:37`; issue history `FILECAT_1_0_RELEASE_ISSUE_HISTORY_20261006.md:892-903`) fixed changed-source moves using fresh stat/version and server tests. `tests/FileCat.Remote.Tests/SftpJobTests.cs:269-282` changes the timestamp, and `FtpJobTests.cs:465` covers changed-source retry; they do not distinguish B with matching metadata. Link-admission tests address links, not a regular-file replacement. Local copy-then-delete has stronger byte checks at `Executors.cs:1235-1300`; that is not used by this remote path. This is a new consequential boundary within I49's subject, **not** a repeat of its passed changed-timestamp case.

**Smallest correction.** Capture opened-source object identity and evidence of the exact uploaded bytes; at deletion, require a regular non-link source with the same identity and content. Identity alone misses an in-place rewrite with restored metadata. A last path check alone leaves a check/delete race. The implementation must bind removal to the verified object on each supported platform or conservatively keep the local file and report a partial Move when that binding cannot be guaranteed. A same-volume private quarantine/verified-restore approach or platform object-bound deletion may work, but its native semantics and crash behavior must be proved before selection. A complete predelete reread may cost one extra full local read per successful remote Move, especially on network/removable sources; do not waive the invariant for large files without a safe alternative. ### FCSEC-005 — a local pin masks a revoked SFTP host key

### FCSEC-007 / former GAP-002 — 7z next-header size allocates before input-length validation

**Threat and reachable effect.** An attacker controls a `.7z` file offered to the user. The victim opens it in FileCat, which enumerates the archive in the ordinary desktop process. `Directory.Packages.props:18` pins SharpCompress 0.50.4. `ArchiveProvider.cs:248-285` selects the format and calls `ArchiveFormats.Open`; `ArchiveFormats.cs:653-680` opens it with `SevenZipArchive.OpenArchive`, and `:627-637` immediately enumerates `archive.Entries` in the `SharpArchiveReader` constructor. The per-member limits in `ArchiveProvider` and `ArchiveIndex.Build` run only after this parse. The pinned dependency's `ArchiveReader.ReadDatabase` validates the start-header CRC, accepts `nextHeaderSize <= int.MaxValue`, checks only that the offset fits the file, then allocates `new byte[nextHeaderSize]` before reading the missing bytes. An attacker needs no elevated authority, network server or large file. The crossed boundary is 7z metadata into unbounded main-process allocation. Consequences are memory pressure, a long pause or process failure while user operations may be active; no code execution or file corruption was demonstrated.

**Bounded reproduction on current binary, 28 October 2026.** A disposable probe built with SDK 10.0.101 referenced the existing Release `FileCat.Archives.dll` and locally cached SharpCompress 0.50.4 DLL identified in §2. It made a 32-byte file: bytes 0–5 are the 7z signature, version bytes 6–7 are zero, little-endian `nextHeaderOffset` at 12–19 is zero, `nextHeaderSize` at 20–27 is `67,108,864`, `nextHeaderCrc` at 28–31 is zero, and bytes 8–11 hold CRC-32 of bytes 12–31. `ArchiveFormats.Open(path, ArchiveKind.SevenZip, name)` followed by `reader.List(...).ToList()` threw `InvalidDataException` **after allocating 67,187,352 bytes on that thread**. A prior same-fixture run allocated 67,193,544 bytes, showing small runtime variation. The current dependency alone allocated 67,124,736 bytes on the same fixture. As a healthy control, `tests/FileCat.Core.Tests/TestData/Archives/EmptyEntries.7z` (234 bytes) opened through the same FileCat reader and yielded four entries. The malformed fixture SHA-256 is in §2. The probe did not force a 2 GiB allocation or observe a GUI crash. The source permits up to `int.MaxValue` as the declared size, so the worst case is a source-supported risk, not an executed measurement.

The probe measured `GC.GetAllocatedBytesForCurrentThread()` immediately before and after the synchronous open/list call, with no other concurrent work in that disposable process. The final run was `dotnet run --project .tmp/security-7z-probe/security-7z-probe.csproj -c Release --no-restore` and exited 0 after reporting the caught exception and valid control. The ignored probe directory and generated fixture were removed after their hashes and results were recorded; no product, test or dependency file was changed by the probe.

**Disposition and repair.** **High availability, high confidence for disproportionate allocation; open P0.** The input is tiny and the user action is normal archive opening, making the amplification consequential despite the bounded observed 64 MiB case. [SharpCompress 0.50.5](https://github.com/adamhathcock/sharpcompress/releases/tag/0.50.5) contains the upstream next-header length-before-allocation correction; its [source](https://raw.githubusercontent.com/adamhathcock/sharpcompress/0.50.5/src/SharpCompress/Common/SevenZip/ArchiveReader.cs) compares size with remaining stream bytes before allocation. Service the pinned package and locks through normal dependency review, or apply an equivalent check on the opened stream before invoking 0.50.4 if servicing is blocked. Decide and enforce a finite 7z metadata budget as part of I06; upstream's physical-length check alone still permits a genuinely large header to allocate in process. The guard must be applied before SharpCompress enumerates entries and must use the same opened source/identity assumptions as `ArchiveProvider`. Avoid a full archive-parser rewrite.

### FCSEC-008 — remote directory responses have no finite memory budget

**Threat and reachable effect.** A hostile or compromised SFTP, FTP, or FTPS server controls the number and lengths of directory entries returned after the user opens that server's folder. `src/FileCat.Remote/Sftp/SshNet.cs:186-198` appends every SSH.NET entry to a `List<IRemoteEntry>`; cancellation is checked per entry, but neither count nor total name bytes are capped. `src/FileCat.Remote/Ftp/FluentFtp.cs:210-244` first receives FluentFTP's complete `GetListing` array (and, on MLST servers, a second complete LIST response), then retains wrapped entries without a cap. `src/FileCat.Remote/Sftp/SftpProvider.cs:133-171` allocates an `EntryData` batch sized from `list.Count`, copies entries into it and calls `sink.AddBatch` only after the whole list has been converted. `src/FileCat.Core/Listing/ListingModel.cs:482-486` creates a budgeted, spillable `EntryStore` only for local filesystem locations; every remote location gets `new EntryStore()` whose default `memoryBudgetBytes` is `long.MaxValue` (`EntryStore.cs:43-48`). ### FCSEC-009 — MTP Move can delete the only correct local copy after a size-only check

**Threat and reachable effect.** On Windows, an F6/Move from a local file to a writable phone/camera selects `MtpUploadExecutor` (`src/FileCat.Platform.Windows/Mtp/MtpJobs.cs:21-29`). `Upload` calls `Send` or `Replace`, then `Fs.DeleteFile(source)` for Move after a successful return (`:211-225`). `Send` writes from a `FileStream` into WPD and accepts the device's reported `stored.Size == _sent` (`:233-264`), without reading back destination bytes or comparing a digest.
