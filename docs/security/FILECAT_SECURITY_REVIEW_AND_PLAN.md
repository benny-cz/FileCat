### Assets and boundaries

Assets are file bytes and metadata, selected source/destination identity, private transfer stages, undo/journal state, recoverable deleted content, remote credentials and trust records, settings and diagnostics, and signed release inputs. The ordinary desktop process may browse hostile local/archive/remote names and contents. Explicit F4/open/tool actions cross into external process execution; an elevated desktop process has a larger token than the ordinary user context. Windows privileged operations cross the native bootstrap, immutable plan, consent and named-pipe boundary. Picture/Shell workers parse less-trusted input with platform-specific authority. ZIP/other archives, recovery images/devices, HTML/Markdown/images, clipboard/drop data and remote protocol replies cross parser, namespace and publication boundaries. Build and installer paths cross dependency, loader, signing and artifact-promotion boundaries.

The original audit's two material High scenarios were distinct. For FCSEC-001, another ordinary process (or concurrent user workflow) changed a selected local path during an explicitly approved remote **Move**; FileCat could delete a replacement never uploaded. For FCSEC-002, a medium-integrity actor in the same Windows account could control an implicitly chosen per-user editor path while the victim ran FileCat elevated and pressed F4; FileCat launched a high-integrity child. FCSEC-003 concerned a raw path logged during a failed sidecar scan. Their accepted corrections have the §8 scopes. The current threat paths add an external drag source's Move completion contract (FCSEC-004), a compromised SFTP host key later revoked in OpenSSH (FCSEC-005), medium-authored persisted tool settings consumed by a high-token process (FCSEC-002-R1), and an attacker-writable file whose stale verification badge encourages trust (FCSEC-006). A genuinely user-selected tool, deliberate shell command or explicit file open is not by itself an exploit; the FCSEC-002-R1 problem is that the elevated session cannot establish who authored its persisted executable definition.

Network use from configured FTP/SFTP connections and the opt-in update check is intentional. `SECURITY.md` excludes an attacker who already has administrator rights; it does not erase a medium-to-high integrity transition induced by a lower-privileged actor. The source contains no public web server or automatic updater. Deliberate remote operations and media/recovery use remain subject to their explicit choices.

## 5. Detailed actionable findings

**Historical baseline note for FCSEC-001 through FCSEC-003.** The next three subsections preserve the source traces and proposed corrections from the original `1ff0926` audit. Their vulnerable line references describe that earlier baseline, not a current defect at HEAD. The current corrected behavior and bounded observations are AC-01 through AC-03 in §8; in particular, current remote Move calls `DeletePublishedLocalSource`, and current elevated F4 refuses the implicit fallback. FCSEC-002-R1 below is a different current route through persisted settings.

### FCSEC-001 — substituted local source deleted after remote Move

**Invariant and trace.** A Move may remove only the local bytes it actually copied and published. `src/FileCat.Remote/Sftp/SftpJobs.cs:14-29` registers the shared upload executor; `src/FileCat.Remote/Sftp/Connections.cs:49-52` selects SSH or FTP transport, so SFTP, FTP and encrypted FTP variants use it. `SftpJobs.cs:411-428` reads `FileSystemItemInfo`, opens the local path with `FileShare.Read | FileShare.Delete`, and defines `unchanged` as size plus `ModifiedUtc`. The upload checks that predicate at `:704-705` and `:723-725`, then publishes. For a Move, `:429-438` checks only size/time once more before `Fs.DeleteFile(local)`. The portable implementation calls `File.Delete(path)` (`src/FileCat.Core/FileSystem/FileSystemOperations.cs:394`); Windows calls path-based `DeleteFileW` (`src/FileCat.Platform.Windows/WindowsFileOperations.Native.cs:321-324`). Neither deletion binds the pathname to the opened/uploaded object. An ordinary peer can replace A at that path with B of the same size and timestamp after the last upload check; A is remote, B is deleted locally and was never copied. A sync client, editor or another file operation suffices; no malicious server or privilege is needed. Scope is one selected file per race, potentially consequential user data. The code establishes the failure path; this audit did not execute the race or establish its frequency.

**Existing controls and lineage.** I49 (`docs/release/1.0.0/FILECAT_1_0_RELEASE_ISSUES_I001_I299.md:37`; issue history `FILECAT_1_0_RELEASE_ISSUE_HISTORY_20261006.md:892-903`) fixed changed-source moves using fresh stat/version and server tests. `tests/FileCat.Remote.Tests/SftpJobTests.cs:269-282` changes the timestamp, and `FtpJobTests.cs:465` covers changed-source retry; they do not distinguish B with matching metadata. Link-admission tests address links, not a regular-file replacement. Local copy-then-delete has stronger byte checks at `Executors.cs:1235-1300`; that is not used by this remote path. This is a new consequential boundary within I49's subject, **not** a repeat of its passed changed-timestamp case.

**Smallest correction.** Capture opened-source object identity and evidence of the exact uploaded bytes; at deletion, require a regular non-link source with the same identity and content. Identity alone misses an in-place rewrite with restored metadata. A last path check alone leaves a check/delete race. The implementation must bind removal to the verified object on each supported platform or conservatively keep the local file and report a partial Move when that binding cannot be guaranteed. A same-volume private quarantine/verified-restore approach or platform object-bound deletion may work, but its native semantics and crash behavior must be proved before selection. A complete predelete reread may cost one extra full local read per successful remote Move, especially on network/removable sources; do not waive the invariant for large files without a safe alternative. Preserve ordinary remote Move, resumed upload, read-back, replacement recovery and user-visible uncertainty rather than silently converting all moves to copies. No broad operations rewrite is justified. Estimated effort: **medium**, dependent on platform-specific deletion semantics; expected risk reduction is prevention of irreversible wrong-object deletion.

**Finite acceptance and stopping rule.** AC-01 in §8 is authoritative: synchronize an owned synthetic A→remote upload; (a) replace its local pathname with different B of equal size/restored mtime before final check, (b) rewrite A in place to different bytes with the same metadata, and (c) substitute B in the check/delete window. In each adverse case the bytes not uploaded survive, remote A remains the only published bytes, and the job reports partial/uncertain Move without claiming deletion. Include unchanged A as a positive Move control, one SFTP case and one FTP adapter case exercising the shared executor, and representative Windows/Unix removal semantics without an OS-by-protocol matrix. A failed binding keeps the source; no destructive retry. Stop when these observations pass at the corrected source and the affected existing I49 cases stay passing. If a native object-bound guarantee is unavailable, stop the design attempt with the conservative keep-source behavior; do not substitute a non-atomic final stat. Reopen only for a deletion-semantic change, observed contrary result or a new reachable replacement route.

### FCSEC-002 — elevated implicit editor from a writable path

**Invariant and trace.** A lower-integrity actor must not choose code that an elevated FileCat launches automatically. F4 is an explicit **Edit** action (`src/FileCat.App/ViewModels/MainViewModel.Operations.cs:815-853`), but when neither an edit association nor a saved editor exists, `LaunchEditor` silently calls `ToolLauncher.DetectEditor`. On Windows, `src/FileCat.Core/Tools/ToolLauncher.cs:33-49` checks `%LocalAppData%/Programs/Microsoft VS Code/Code.exe` before Program Files and also checks per-user Zed; existence is the only selection guard. `ToolLauncher.cs:167-185` starts that exact executable with `UseShellExecute=false` and the FileCat process token. Elevated FileCat is supported and shows a general startup notice (`src/FileCat.App/App.axaml.cs:73-106`); there is no per-F4 executable choice. A medium-integrity same-account process can create/replace the per-user executable, then victim F4 yields a high-integrity child. Microsoft documents that `CreateProcessW` runs a child in the calling process security context; see §11. This is a **High** privilege boundary failure with a victim action and an elevated-session prerequisite, not an automatic execution during passive browse. The chain is source-supported and not newly run in a VM here.

Unix `DetectEditor` also searches absolute entries in inherited `PATH` (`ToolLauncher.cs:51-82`). That can select a lower-trust program on explicit F4, but no additional authority follows from an ordinary-user child merely because the directory is user-writable. Treat it as the same selector root and preserve legitimate non-system editor use; do not inflate a second High finding.

**Existing controls and lineage.** I16 is an open automatic-launch parent, and I391-I399/I429 pin or bound other helpers. `docs/release/1.0.0/evidence/E-I397-system-shell-helper-selection.md` covers implicit Open/Reveal, not F4 editor fallback. `ToolLauncher` argument-list transport does not decide whether the executable is trustworthy. A user-configured editor or association remains an explicit choice under `SECURITY.md`'s external-program scope. The Windows elevated implicit path has a distinct trigger and no passed scenario to reopen.

**Smallest correction.** The conservative fix is to refuse **implicit external editing** while FileCat is elevated, with a clear message and a route to configure an editor deliberately. Merely switching to protected `notepad.exe` is not by itself sufficient: `ToolLauncher.cs:176-180` sets the target file's folder as the child's working directory and inherits the environment, while Windows may search current directory and `PATH` for dependent DLLs (primary loader documentation in §11). A protected fallback would also need a safe working directory/environment and a bounded loaded-code check. An ordinary-token launch is another alternative only if token/session semantics are verified. Keep normal-user per-user editors and explicit associations usable; the latter are user choices, and the UI should identify the chosen executable when relevant. Estimated effort: **small** for fail-closed implicit selection, larger for a safe fallback; compatibility risk is loss of one-keystroke implicit editing in an elevated session until the user configures an editor.

**Finite acceptance and stopping rule.** AC-02: in an isolated Windows VM, place a harmless fake at the per-user editor path using a medium token, run FileCat high-integrity with no matching association/saved editor, press F4, and verify **no implicit external child starts** and the refusal clearly explains the edit outcome. Positive controls cover ordinary-token F4 and an explicit configured editor choice. If a protected implicit fallback is chosen instead, also prove a safe working directory/environment and that no untrusted module loads from the selected file's folder or writable `PATH`; a fake-editor non-start alone cannot close that design. A selector test may precede the native control but cannot replace its token observation. Stop once the corrected high-token route and affected ordinary routes pass; no whole I16 matrix repeat. Reopen only if implicit selection, elevated launch authority or the relevant platform token model changes, or a regression appears.

### FCSEC-003 — raw path in default diagnostics after sidecar failure

**Invariant and trace.** With diagnostic mode off, a default diagnostics bundle promises hashed paths (`src/FileCat.App/Services/DiagnosticsBundle.cs:16-25`) and includes the local log in its user-confirmed ZIP (`:26-53`). `src/FileCat.App/ViewModels/MainViewModel.Checksums.cs:219-239,270-275` can catch a sidecar scan failure during explicit verification and logs the literal folder path plus exception; it also stores `ex.Message` as `Unread`. ### FCSEC-004 — external Move drop reports completion before FileCat transfers data

**Boundary, reachability and consequence.** An external drag source may discard its originals when the target reports that it performed a Move. `src/FileCat.App/Services/DropTargetAdmission.cs:39-53` chooses `DragDropEffects.Move` when Shift is held. In the actual Drop handler, `src/FileCat.App/Views/MainWindow.axaml.cs:340-385` first sets `e.DragEffects` to `None`, validates the payload, then sets it to `current.Effect` at `:383` and awaits `DropFilesAsync` at `:384`. Even if the handler continues, target rechecks can return at `:908-912` or `:918-923`, the user can cancel the transfer dialog at `:930-933`, and `Services.Jobs.Submit` is only reached at `:937`. The victim action is Shift-drop followed by Cancel, a disappearing destination, or normal delayed job execution. The source is an external app; FileCat's authority is only to receive the payload until it actually copies or removes it. The extra effect is source deletion without a completed destination. This is **High integrity/data-loss risk** at protocol level, with actual behavior dependent on the source; this review did not observe Explorer or another native drag source deleting an owned file.

**Prior work, correction and bounded acceptance.** The existing inbound native test `tests/FileCat.NativeAcceptance/win-ax-drag-external.ps1:350-357` exercises Ctrl/Copy cancellation and cannot decide Shift/Move semantics. AC-05 must use owned synthetic files and a small standards-compliant drag source, record the returned effect, and verify source/destination byte hashes. A separate Explorer observation is useful but its Shell-specific performed-effect behavior must be recorded, not assumed. The smallest safe containment is to refuse external Shift-Move at hover with `None`, no transfer review and a clear Copy/F5 alternative. Converting Shift to Copy would preserve the source, but a `Copy` result issued before review can still falsely report success after cancellation; that is a separate UX limitation, not truthful completion. If retaining cross-app Move, only return Move when FileCat has synchronously finished a verified transfer and will not independently delete the same source. Cancelled/failed and positive Copy controls must preserve source bytes. Stop when returned effects and byte observations agree; no platform-by-source matrix is needed absent contrary native behavior.

### FCSEC-005 — a local pin masks a revoked SFTP host key

**Boundary, reachability and consequence.** `src/FileCat.Remote/Sftp/HostKeys.cs:61-78` scans FileCat's own `known_hosts` before the user's two OpenSSH seed files. Within each file it rejects an exact `@revoked` match, then immediately returns `Trusted` for a positive match. If FileCat's own file contains host H/key K and the user's OpenSSH file later contains `@revoked H <type> K`, the first file returns `Trusted` before the revocation is read. `src/FileCat.Remote/Sftp/Connections.cs:378-390` silently accepts `Trusted` and refuses `Revoked`; `SshNet.cs:55-56` feeds that decision into SSH.NET's host-key callback before connection. A user who revoked a compromised server key through OpenSSH still has FileCat silently accepting the same key. An actor with K's private key and network position can impersonate H for this user, potentially receiving password authentication and file contents. The necessary prior FileCat pin and later OpenSSH revocation make the route narrower than a generic host-key bypass, but the failed control is precisely the revocation signal. OpenSSH's [known-hosts format](https://man.openbsd.org/OpenBSD-7.4/sshd#SSH_KNOWN_HOSTS_FILE_FORMAT) specifies that a matching `@revoked` key must never be accepted.

**Prior work, correction and bounded acceptance.** `tests/FileCat.Remote.Tests/HostKeyTrustTests.cs:83-105` verifies revocation with no FileCat pin; `:111-125` verifies own-file precedence against an ordinary conflicting seed, not against revocation. The latter precedence is intentional and can remain. AC-06 should create two owned text files, put K in FileCat's file and a matching `@revoked` entry in the seed, then assert `Check(H,K)` is `Revoked` and the connection callback refuses it. Pair that with a non-revoked conflict proving own-file positive precedence still works, a different revoked key proving no false rejection, and the existing first-contact case. Scan all applicable files for exact revocations before applying positive/changed precedence. A revocation-read failure should not be converted to `Trusted` for an already pinned key without an explicit policy decision. No real credential or external server is needed to prove the trust decision. Stop at those cases; broader SSH protocol tests are not required by this defect.

### FCSEC-006 — automatic authenticity badge can describe old bytes

**Boundary, reachability and consequence.** `src/FileCat.Core/Verification/VerificationService.cs:272-285,429-477` keys remembered hashes and results by path, size and modified time, plus sidecar/trust fingerprints. `:444-445` returns an automatic cached result or cached hash without reading the current file. ### FCSEC-007 / former GAP-002 — 7z next-header size allocates before input-length validation

**Threat and reachable effect.** An attacker controls a `.7z` file offered to the user. The victim opens it in FileCat, which enumerates the archive in the ordinary desktop process. `Directory.Packages.props:18` pins SharpCompress 0.50.4. `ArchiveProvider.cs:248-285` selects the format and calls `ArchiveFormats.Open`; `ArchiveFormats.cs:653-680` opens it with `SevenZipArchive.OpenArchive`, and `:627-637` immediately enumerates `archive.Entries` in the `SharpArchiveReader` constructor. The per-member limits in `ArchiveProvider` and `ArchiveIndex.Build` run only after this parse. The pinned dependency's `ArchiveReader.ReadDatabase` validates the start-header CRC, accepts `nextHeaderSize <= int.MaxValue`, checks only that the offset fits the file, then allocates `new byte[nextHeaderSize]` before reading the missing bytes. An attacker needs no elevated authority, network server or large file. The crossed boundary is 7z metadata into unbounded main-process allocation. Consequences are memory pressure, a long pause or process failure while user operations may be active; no code execution or file corruption was demonstrated.

**Bounded reproduction on current binary, 28 October 2026.** A disposable probe built with SDK 10.0.101 referenced the existing Release `FileCat.Archives.dll` and locally cached SharpCompress 0.50.4 DLL identified in §2. It made a 32-byte file: bytes 0–5 are the 7z signature, version bytes 6–7 are zero, little-endian `nextHeaderOffset` at 12–19 is zero, `nextHeaderSize` at 20–27 is `67,108,864`, `nextHeaderCrc` at 28–31 is zero, and bytes 8–11 hold CRC-32 of bytes 12–31. `ArchiveFormats.Open(path, ArchiveKind.SevenZip, name)` followed by `reader.List(...).ToList()` threw `InvalidDataException` **after allocating 67,187,352 bytes on that thread**. A prior same-fixture run allocated 67,193,544 bytes, showing small runtime variation. The current dependency alone allocated 67,124,736 bytes on the same fixture. As a healthy control, `tests/FileCat.Core.Tests/TestData/Archives/EmptyEntries.7z` (234 bytes) opened through the same FileCat reader and yielded four entries. The malformed fixture SHA-256 is in §2. The probe did not force a 2 GiB allocation or observe a GUI crash. The source permits up to `int.MaxValue` as the declared size, so the worst case is a source-supported risk, not an executed measurement.

The probe measured `GC.GetAllocatedBytesForCurrentThread()` immediately before and after the synchronous open/list call, with no other concurrent work in that disposable process. The final run was `dotnet run --project .tmp/security-7z-probe/security-7z-probe.csproj -c Release --no-restore` and exited 0 after reporting the caught exception and valid control. The ignored probe directory and generated fixture were removed after their hashes and results were recorded; no product, test or dependency file was changed by the probe.

**Disposition and repair.** **High availability, high confidence for disproportionate allocation; open P0.** The input is tiny and the user action is normal archive opening, making the amplification consequential despite the bounded observed 64 MiB case. [SharpCompress 0.50.5](https://github.com/adamhathcock/sharpcompress/releases/tag/0.50.5) contains the upstream next-header length-before-allocation correction; its [source](https://raw.githubusercontent.com/adamhathcock/sharpcompress/0.50.5/src/SharpCompress/Common/SevenZip/ArchiveReader.cs) compares size with remaining stream bytes before allocation. Service the pinned package and locks through normal dependency review, or apply an equivalent check on the opened stream before invoking 0.50.4 if servicing is blocked. Decide and enforce a finite 7z metadata budget as part of I06; upstream's physical-length check alone still permits a genuinely large header to allocate in process. The guard must be applied before SharpCompress enumerates entries and must use the same opened source/identity assumptions as `ArchiveProvider`. Avoid a full archive-parser rewrite.

### FCSEC-008 — remote directory responses have no finite memory budget

**Threat and reachable effect.** A hostile or compromised SFTP, FTP, or FTPS server controls the number and lengths of directory entries returned after the user opens that server's folder. `src/FileCat.Remote/Sftp/SshNet.cs:186-198` appends every SSH.NET entry to a `List<IRemoteEntry>`; cancellation is checked per entry, but neither count nor total name bytes are capped. `src/FileCat.Remote/Ftp/FluentFtp.cs:210-244` first receives FluentFTP's complete `GetListing` array (and, on MLST servers, a second complete LIST response), then retains wrapped entries without a cap. `src/FileCat.Remote/Sftp/SftpProvider.cs:133-171` allocates an `EntryData` batch sized from `list.Count`, copies entries into it and calls `sink.AddBatch` only after the whole list has been converted. `src/FileCat.Core/Listing/ListingModel.cs:482-486` creates a budgeted, spillable `EntryStore` only for local filesystem locations; every remote location gets `new EntryStore()` whose default `memoryBudgetBytes` is `long.MaxValue` (`EntryStore.cs:43-48`). Thus the remote protocol response, provider batch and final listing can coexist in the ordinary app process. `RemotePath.ProblemWithName` (`Channel.cs:158-163`) rejects unusable path syntax, but imposes no count or aggregate byte budget. A server that supplies enough distinct valid names can drive memory growth until severe slowdown or process failure. This is a **High availability risk, source-supported**; the exact threshold, peak and GUI failure have not been measured, and the server/user connection premise is narrower than FCSEC-007's local file premise. No claim of code execution or data theft follows.

**Repair and bounded proof.** WP-10 should set one explicit remote-list budget for entry count, aggregate name bytes and working memory, enforce it while the protocol response is read, and surface a clear partial-list/refusal result. A cap after `Channel.List` or after `GetListing` alone would leave the upstream allocation exposed. For SFTP, stream into bounded batches or stop enumeration at the budget. For FTP/FTPS, establish a bounded listing-reader route or isolate the parser with a finite memory limit; confirm what FluentFTP allocates before FileCat receives the array. Give remote entries a finite `EntryStore` budget if they remain supported by the spill format, but do not rely on downstream spill as the only guard. AC-10 uses an owned synthetic SFTP channel and an owned local FTP server that return a normal small listing and a controlled just-over-budget listing, with per-stage entry/byte counts and process peak. Require a bounded, intelligible refusal/partial result, no unbounded post-cancel retention, and ordinary small-list behavior. Stop after one representative SFTP and one FTP/FTPS parser route; do not run an actual OOM or claim the FTP library is bounded merely because FileCat's wrapper stops.

### FCSEC-009 — MTP Move can delete the only correct local copy after a size-only check

**Threat and reachable effect.** On Windows, an F6/Move from a local file to a writable phone/camera selects `MtpUploadExecutor` (`src/FileCat.Platform.Windows/Mtp/MtpJobs.cs:21-29`). `Upload` calls `Send` or `Replace`, then `Fs.DeleteFile(source)` for Move after a successful return (`:211-225`). `Send` writes from a `FileStream` into WPD and accepts the device's reported `stored.Size == _sent` (`:233-264`), without reading back destination bytes or comparing a digest. A device or faulty WPD implementation can retain different bytes at the same length and still satisfy that check; FileCat then deletes the original. `WpdSession.OpenRead` exists (`WpdSession.cs:417-423`), so a full readback is technically available. Separately, the source stream is closed when `Send` returns, and the later `DeleteFile(source)` acts on the live pathname, without checking identity or bytes. A same-account concurrent writer can replace that pathname with a different file during the narrow close-to-delete interval; FileCat can then remove that replacement. The first branch needs an inaccurate same-size device response; the second needs a timed concurrent local writer. Neither adverse branch was run on a native device in this pass. The crossed boundary is untrusted device/namespace state being accepted as authority to destroy a local original. This is **High integrity, source-supported**, scoped to MTP Move and distinct from the already corrected SFTP/FTP source-deletion route FCSEC-001.

**Related cleanup edge and repair.** `MtpJobs.cs:264-288` calls `RemoveUnfinished` on upload failure and finds/deletes a leftover by *name*, not by a retained created-object ID. If another device client creates that name between admission and cleanup, the cleanup may delete its object; this is a conditional wrong-object route and not a separately observed High outcome. WP-11 should bind each upload to its created object, verify complete readback bytes against a digest of exactly the opened local source before removing that source, then move the original local pathname to a private same-directory hold and prove the held identity/bytes still match before deleting only the hold. If the device cannot read back, retain the source and report an incomplete Move. On failed uploads, delete only an object proven to belong to the attempt; otherwise leave a named review item. AC-11 uses an owned WPD fake/test seam: exact bytes control; same-length altered device bytes; source-path B substitution at the post-copy/pre-delete seam; and a failed creation followed by peer-created same-name B. Assert that B and the correct local source survive adverse cases, exact A reaches the device in the healthy case, and no unrelated object is removed. A later owned-device positive observation may be needed for candidate qualification, but no physical-device destructive test is authorized by this review.

### FCSEC-010 — elevated diagnostics trust log names in medium-writable state

**Threat and reachable effect.** On Windows, default logs live under the same account's `%LOCALAPPDATA%\FileCat\diagnostics` (`src/FileCat.Core/State/AppPaths.cs:50-52,122-125`), which a medium-integrity process under that account can ordinarily modify before FileCat starts elevated. `DiagnosticsBundle.Write` (`src/FileCat.App/Services/DiagnosticsBundle.cs:28-54`) checks `File.Exists` for `filecat.log`, `filecat.log.1` and `crash.log`, then uses `new FileStream` and copies every byte into a ZIP on the Desktop after the user's export confirmation (`MainViewModel.Workspaces.cs:327-335`). It does not reject links or bind the opened object to a regular log file under an uncompromised directory. If the medium writer can plant a symbolic link named `filecat.log.1` to a file readable only with the elevated token, the high process copies that file's contents to a ZIP the same account can read at medium integrity. That is a conditional **High confidentiality** crossing, with victim export as a real action and a working link-creation capability as a platform prerequisite. The bundle's preview claims no file contents, which this route would contradict. The same trust pattern affects startup logging: `AppLog.Initialize` selects `filecat.log` and `AppLog.Write` calls `File.AppendAllText` (`Diagnostics.cs:53-61,83-95`); an unrotated planted link can direct high-token log lines into a protected target. The latter is a conditional integrity effect; arbitrary attacker-selected target bytes or a protected-file write were not demonstrated.

**Evidence, limit and repair.** Two disposable owned Windows probes on this host used the exact .NET APIs: a symbolic link named `filecat.log.1` returned true from `File.Exists`, and `FileStream` read `OWNED-SECRET-MARKER` from its target; `File.AppendAllText` through `filecat.log` changed an owned target from `BEGIN` to `BEGIN|APPENDED`. The probes did not instantiate FileCat, access a protected file or run high integrity. Microsoft documents that Windows file opens follow a symbolic link's target unless reparse-point handling is explicitly requested ([CreateFile symbolic-link behavior](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilea)); unprivileged link creation depends on device policy/rights ([CreateSymbolicLink](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createsymboliclinka)). WP-12 should treat the log directory and each exported/opened log as untrusted when elevated: refuse links/reparse points at every path component, bind regular-file identity to the opened handle, cap bytes copied, and fail closed when that cannot be established. The safest elevated fallback is to omit untrusted persisted logs from export and say so in the preview. Prevent high-token appends through the same path, including `crash.log`. AC-12 stages an owned medium-writable linked log and an owned high-only marker, runs the exact elevated export and startup-log routes under a controlled VM/token harness, and asserts no marker bytes leave the protected file and no high-only target changes. Pair with ordinary-token genuine-log export and high-token newly generated genuine-log controls; stop at those routes. No real secret is needed.

### FCSEC-011 — elevated autosave can overwrite through a planted Windows state-temp link

**Threat and reachable effect.** The default Windows state directory is the account's `%APPDATA%\FileCat` (`src/FileCat.Core/State/AppPaths.cs:122-125`), writable by a same-account medium-integrity process even when a later FileCat window runs high integrity. `JsonFileStore.SaveCore` chooses the deterministic Windows sibling `path + ".tmp"`, then opens it with `FileMode.Create` and writes serialized state before any replacement or backup step (`src/FileCat.Core/State/JsonFileStore.cs:125-176`). ### FCSEC-012 — Mirror removes a replacement that is not the compared object

**Trace and effect.** `Compare/Sync.cs:75-119,130-189` proposes target-only Mirror removal and builds a Delete or Recycle job with `OnlyAsCompared = true`. `Jobs/Executors.cs:172-194` decides whether a regular file changed using only size and modified ticks. `DeleteExecutor` then deletes the pathname (`Executors.cs:1610-1699`); Recycle uses the same comparison guard (`:1711-1744`). A second process can substitute different bytes of the same length and restore the timestamp after comparison. The guard accepts the replacement as unchanged and removes it, despite the UI/job promise to remove only what was compared. For a target-only folder, `FolderContents` fingerprints descendant paths, sizes and timestamps; a same-metadata child substitution can likewise leave its fingerprint unchanged before recursive removal. The check-to-deletion gap also permits a later swap. This is a **conditional High integrity** path for an approved destructive Mirror action, not a claim of remote attacker access or an observed production loss. It is separate from FCSEC-001: that corrected local-to-remote Move source binding, whereas this is local synchronization target deletion.

**AC-15 / repair and proof.** Bind each compared target to a strong file identity and contents digest, then retire exactly that held object after a fresh check; for folders, require complete descendant binding or conservatively keep the tree when it cannot be proved unchanged. Review and expose the exact object that will be removed. In one owned target, compare A, replace its pathname with B having identical length and timestamp but different bytes, and run each representative permanent-delete and Recycle route; B must survive. Repeat for one same-metadata child of a target-only folder and one post-check swap. An unchanged A must still be removable. Record filesystem, opened identities/digests and final bytes; do not infer race safety from metadata-only tests (`SyncTests.cs:124-145` currently changes size/time).

### FCSEC-013 — persisted edit session can direct a high-token Save copy read

**Trace and effect.** `Edit/EditSessions.cs:113-133` loads `session.json` from `AppPaths.EditSessionsDirectory` (`State/AppPaths.cs:67`) and checks version plus `Id == directory name`, but does not require `WorkingPath` to be the session's owned work file or bind it to a prior creation. `MainViewModel.EditSessions.cs:323-355` offers “Save copy…” for a loaded record. Its `SaveSessionCopyAsync` (`:608-649`) obtains a user-selected destination and calls `PrepareSaveCopy`, which opens `record.WorkingPath` through the provider and stages its bytes (`EditSessions.cs:503-521`), then publishes that copy. A same-account medium-integrity actor who can write the per-user edit-session directory can plant a valid record pointing at a known high-only file. If the user runs FileCat at high integrity and selects Save copy to a medium-readable path, FileCat can copy protected bytes across the token boundary. The user action, known source path, readable source, finite working-copy limit and writable lower-token destination are explicit prerequisites. This is **conditional High confidentiality, source-supported**, with no high-token end-to-end run. A visible path in the session UI may alert an attentive user; it does not establish record provenance.

**AC-16 / repair and proof.** Treat saved session JSON as untrusted state. Require the work file to be an owned regular file inside the exact session directory, reject reparse traversal and altered parent identities, and bind content and origin to the session creation record before any commit, copy or discard action. High-token reads of medium-authored session records should refuse or require a fresh, independently verified selection. In an owned medium/high Windows fixture, plant a record whose `WorkingPath` names an owned high-only marker and attempt Save copy to a lower-readable destination; assert marker bytes never appear there. A genuine session must still review and Save copy. Capture the UI choice and actual output bytes, not merely `LoadAll` acceptance. Do not test against an unrelated protected file.

### FCSEC-014 — unauthenticated journal rename `via` controls a different object than the review displays

**Trace and effect.** `JobJournal.cs:16,188-230` uses CRC32 to detect torn records; CRC32 is unkeyed and does not authenticate a writer. `JournalRecovery.Scan` (`:382-465`) accepts `job-*.fcj` records from `AppPaths.JournalDirectory` and reconstructs each open intent's `path`, `target` and `via` fields without proving that `via` was created by this job. `InterruptedRenameReview.cs:20-67` checks that `via` and its parents have reviewable current content, then moves `via` to `target` after confirmation, but it does not require `via` to be an owned rename temporary linked to `path`. If a high-integrity victim approves “Finish renaming,” FileCat can move that file under the higher token. This is **conditional High integrity**; moving a high-only file does not by itself prove the bytes become readable to the attacker, so no confidentiality claim is made.

**Bounded observation.** An owned fake interrupted journal with `path=displayed-original.txt`, `via=owned-source.txt` and an owned target passed the exact core scan/review/finish sequence. It reported `accepted=1`, `finished=1`, `sourceExists=False`, and the target contained `OWNED-MARKER`. The record's display path did not name the object moved. A genuine interrupted bulk rename must still finish under its intended identity, and a same-name substitution must remain untouched. Keep all fixtures in disposable owned directories and inspect the actual final bytes.

### FCSEC-015 — a forged hex-save journal can authorize a new byte patch

**Trace and effect.** `State/AppPaths.cs:20-30,48` places `HexRecoveryDirectory` under the per-user local app-data root. `HexSaveJournal.cs:113-167` reads any `hex-*.fcj` there and validates a SHA-256 checksum of its payload, but an actor able to write a journal can compute that checksum. Thus a same-account medium writer who can read a file but cannot alter it can learn its identity and original bytes, write a forged journal, and induce a high-integrity FileCat user to patch that file by approving recovery. The displayed target path and explicit confirmation are prerequisites; there is no automatic write. This is a **conditional High integrity** route distinct from FCSEC-014's arbitrary rename intent and its CRC journal: it is a separate hex journal format, direct in-place byte patch and recovery UI.

**Bounded observation.** A disposable owned harness built a syntactically valid `FCHXJ002` payload for an owned `BEFORE` file, using the file's real identity and one replacement range. The exact public `HexSaveJournal.Read → Inspect → Recover` API reported `accepted=True`, `rolledBack=True`, then changed the owned target to `XEFORE` and removed the journal. ### FCSEC-041 — malformed SFV lines stall automatic checksum-sidecar scanning

**Trace and consequence.** `FolderSidecars.Scan` recognizes `.sfv` files beside ordinary files and, for a sidecar up to 4 MiB, calls `ChecksumManifests.Load` while gathering automatic verification claims (`src/FileCat.Core/Verification/Sidecars.cs:20-51,100-125,251-264`). `ChecksumManifests.Parse` accepts lines up to 65,536 characters and invokes the generated `SfvLine` regex on each (`src/FileCat.Core/Operations/ChecksumManifest.cs:224-238,250-277,353-354`). The pattern `^(?<name>.+?)\s+(?<hex>[0-9A-Fa-f]{8})$` has no timeout. The work is quadratic within a single accepted line. The parser itself has no cancellation token; `FolderSidecars` cannot interrupt the regex once it starts. A malicious `.sfv` with dozens of such lines remains below the 4 MiB sidecar limit and can stall verification scanning during a routine folder browse, even when it contains **no valid checksum entries**. This is **High availability** with a passive listing trigger. It is distinct from FCSEC-038's Markdown table-regex bug: this one sits in a different parser, is reached from automatic sidecar scanning, and needs an independent repair.

**Bounded observation and limit.** A disposable .NET 10 harness referenced the existing Release `FileCat.Core.dll` and invoked the public exact `ChecksumManifests.Parse` method for an `.sfv` path with one malformed line of the form above. A repeat after warmup gave 17, 25, 102, 409 and 1,595 ms. The ratio at 16k/32k/64k supports quadratic matching. Each line stayed under `MaxLineChars`. No GUI listing, long multi-line runtime, exception, crash or whole-window freeze was run. The harness and owned test data were removed.

**AC-44 / repair and finite proof.** Replace `SfvLine` with a single-pass parse: locate the final whitespace-delimited eight-hex-digit token, reject anything else, and keep the existing name/path validation. If regex remains, give it a strict timeout and handle that timeout as a bad line. Add a cancellation check between lines and a finite aggregate parse-work budget for the sidecar. Capture the sidecar bytes, timings, allocation and the actual automatic row callback.

**Trace and consequence.** The ordinary Open terminal command (`src/FileCat.App/ViewModels/MainViewModel.Commands.cs:518`) calls `WindowsShellServices.OpenTerminal`. When the configured shell is `cmd`, or `auto` falls back to `cmd`, `src/FileCat.Platform.Windows/WindowsShellServices.cs:269-293` starts the fixed system `cmd.exe` without `/D`. The typed-command route in `RunInTerminal` starts the same executable with `/K` but no `/D` (`:298-323`); the Windows Terminal helper builds a `cmd.exe /K` command without `/D` (`:180-184`). This is **conditional High code execution**. It has a distinct hook and repair point from FCSEC-021's OpenSSH `ProxyCommand`, FCSEC-022's Shell file association and FCSEC-002-R1's FileCat tool definition; all command-processor AutoRun routes are grouped here.

**Evidence limit.** This pass traced the exact FileCat call sites and read the installed operating system's `cmd.exe /?` behavior, which explicitly names both the HKCU value and `/D` suppression. It did not change the user's live registry, run elevated FileCat, or observe a high-token child. PowerShell profile loading was observed as a related lead because `OpenTerminal` passes `-NoExit -NoLogo` without `-NoProfile`, but is **not** counted separately or relied on for this finding.

**AC-29 / repair and finite proof.** Launch all terminal children at ordinary integrity when FileCat is high, or refuse terminal actions from a high token. If high-token `cmd` is intentionally retained, add `/D` to every direct and Windows Terminal `cmd.exe` invocation and audit the other terminal clients for profile or configuration hooks. In an owned medium/high Windows fixture, save the prior AutoRun value, temporarily set an inert marker writer, invoke each FileCat terminal route and verify no protected marker is written, then restore precisely the prior value in a guaranteed cleanup path. Check ordinary terminal behavior and capture child integrity and command line. Avoid using a production user profile for this probe.

### FCSEC-029 — nonexistent Registry delete headers make import preview quadratic

**Trace and consequence.** The Registry import menu sends a chosen local `.reg` file to `RegistryImport.Preview` in a background task (`src/FileCat.App/ViewModels/MainViewModel.Registry.cs:72-97`). A full FileCat window stall and a larger attack file were not run.

**AC-32 / repair and finite proof.** Count physical directives and total key-path characters before per-header work, including nonexistent deletes, with a small documented preview budget and a cancellable UI task. Confirm scope and ancestor semantics on a fixture with overlapping deletes, creates and values. No actual Registry mutations are needed for the performance proof.

### FCSEC-030 — permanent delete can enter a swapped directory link outside the selection

### FCSEC-046 — Matroska inspection stack overflows on nested EBML headers

**Threat and trace.** `MediaInspector.Inspect` identifies an EBML header and calls `Matroska` (`src/FileCat.Core/Inspect/MediaInspector.cs:18-27`).
