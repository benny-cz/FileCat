# FileCat RAR reader security audit — 29 October 2026

## Scope and baseline

The separate AC-15–44 security-plan execution was committed and pushed as `f134ba37` before this audit began. This audit examines the new product RAR 1.5–5/7 reader in `src/FileCat.Archives/Rar` and `src/FileCat.Archives.Rar15`, its archive-provider handoff, and adversarial read/extract behavior. `FileCat.zip` is excluded. The released reader and OSI-only SharpCompress switch-over were already on `main` at `1caa2532`; the existing E-I14 release receipts report a 76-file libarchive corpus, cross-platform tests and 1.38 million structure-aware fuzz rounds. Those are prior evidence at their stated commits, not a substitute for the source review here.

The audit will seek distinct Critical/High outcomes: unbounded CPU or memory from a small RAR, write outside the chosen destination, bypass of member integrity checks, sensitive-data read or spill, and premature trust in damaged/missing volumes. It will use owned fixtures and the product's public archive route, then stop after each credible route has a bounded adverse and healthy control. Findings and negative results are added below as they are obtained; no severity is assigned to a code smell without a reachable consequence.

**Later continuation at `be40902e`:** A separate current-source pass found the distinct open filter-work issue RAR-SEC-003 / FCSEC-056. Its exact probe and AC-59 plan are in [the filter-work receipt](E-FCSEC-20261029-RAR-filter-work.md) and [security plan §20](../FILECAT_SECURITY_REVIEW_AND_PLAN.md). The prior stopping decision below describes the earlier RAR-SEC-001/002 repair audit, not this later finding.

## Working observations

- 2026-10-29: The combined Release solution at `f134ba37` built with zero warnings/errors after integrating the reader. Security archive depth and Windows extraction/link controls passed at that source; the native handle cases required an out-of-sandbox run. RAR-specific audit tests have not yet been run in this receipt.
- 2026-10-29: On the integrated source, the focused reader, libarchive corpus, multipart, legacy and signature tests passed 255/256 with one intentional Windows rename skip. The existing 23-seed, 150-round structure-aware RAR fuzz run passed all 3,450 damaged inputs in 36.7 s. This checks baseline behavior but duplicates only a small slice of the earlier much larger release fuzz campaign; further work targets paths its in-memory reader harness does not limit.
- 2026-10-29: Source review found a plausible availability gap in solid archives. `RarReader.OpenDecoded` drains preceding members to reach a later member; `RarMemberStream.Drain` checks their recorded size and checksum but does not apply the archive provider's expansion-ratio or output cap. The target member's `MemberLimits` begin only after that hidden preparation. A tiny later member can therefore trigger a large predecessor decode before any target limit or job cancellation check. A bounded crafted control is in progress before assigning severity.
- 2026-10-29: **Confirmed RAR-SEC-001, High availability, user-opened hostile solid archive.** A generated RAR 2.9 solid archive placed 66 MiB of zero output in a predecessor compressed to less than 66 KiB, followed by a one-byte selected member. Opening the selected member through `RarReader` succeeded on the released code although the predecessor exceeded FileCat's 1000:1 ratio threshold; the pre-fix failing test receipt is `E-FCSEC-20261029-RAR-solid-before.txt`. The selected member's public `ArchiveProvider.OpenContent` follows the same hidden drain. No process crash was claimed; the impact is bypass of the finite expansion budget and synchronous CPU/memory work before the selected member opens. The fix applies the existing `MemberLimits` to each drained predecessor and an aggregate budget to the whole skipped run, with a broken decoder state on a budget failure. The corrected direct and public-route case passed, as did a two-predecessor case where each 33 MiB output stayed below the per-member ratio threshold but their combined 66 MiB exceeded it (`E-FCSEC-20261029-RAR-solid-after.txt`, 2/2). Healthy archive and fuzz reruns are recorded below.
- 2026-10-29: **Confirmed RAR-SEC-002, High availability on Unix, user-opened multipart RAR.** `RarVolumes.Of` includes every matching sibling and the released `RarReader.Open(string)` passed each path to `ArchiveFormats.OpenShared`, which used blocking `FileStream(path, ...)`. A sibling named `set.part2.rar` can be a FIFO or a link to one; opening `set.part1.rar` then waits for a writer before the reader can inspect a header or heed cancellation. The already available `UnixFiles.OpenRegularFileForRead` opens with nonblocking flags and verifies the opened descriptor is regular; `ArchiveFormats.OpenShared` now uses it on Unix, so the same boundary protects the selected archive and other archive formats as well. Direct and symlinked FIFO tests pass on macOS through `RarReader.Open` and public `ArchiveProvider.EnumerateAsync` (2/2, 26 ms in the first fixed run; final suite below). This is source-traced pre-fix behavior plus corrected-source native evidence; no pre-fix GUI hang was deliberately run.
- 2026-10-29: The Unix descriptor-based open exposed a catalog compatibility dependency: `FileStream.Name` is not the source path when built from a safe handle. A first macOS broad reader run therefore failed the new solid-archive public-route test with `The set of archive volumes changed since its catalog was built.` The reader now retains each opened volume's discovery path, the 7z reader retains its selected path, and `ArchiveIndex` pairs those paths with the exact opened handles and checks equal counts. This preserves the existing source identity/change-token and volume-set checks. The final macOS RAR reader suite passed 145/145; the final Windows RAR/source-binding group passed 296 with three platform skips.
- 2026-10-29: An expanded macOS archive run initially stalled in an existing compressed-TAR extraction test. A one-change build with the prior blocking archive-open method stalled the same way, excluding this audit's native-open change as the cause. A finite 10-second diagnostic showed `AwaitingDecision` and `Not extracted: The destination folder path contains a link`; the test fixture's `/var/folders` temporary destination on macOS traverses the system `/var` link to `/private/var`. The fixture now selects that same directory through its real path and keeps a deadline. The isolated control passed, then the combined archive-format, source-replacement and multipart RAR group passed 80/80 on macOS. This was a fixture-path correction, not a change to FileCat's destination-link policy.
- 2026-10-29: Ubuntu 24.04.5 x64 exercised the Linux branch of the same nonblocking descriptor helper: `RarReaderTests` passed 145/145, including both FIFO variants and both crafted solid-ratio controls. Separate multipart RAR (14/14), archive-format (27/27), and archive source-replacement (39/39) runs passed; each guest process exited 0. Exact guest outputs and exit receipts are `E-FCSEC-20261029-RAR-ubuntu-{reader,multipart,format,source}[-exit].txt`. The first attempted combined filter failed at the VMware shell-command layer (exit 127, no test output); each class was then run individually and only those completed processes count.
- 2026-10-29: The release session found a consequential healthy-archive refusal introduced by the RAR-SEC-001 aggregate limit: a solid RAR with an 8.5 GiB predecessor could not open its 13-byte successor, even after the predecessor had been read in order. Commit `3bb3d995` removed the aggregate 8 GiB ceiling while retaining each member's declared-size limit and the aggregate expansion ratio. Its [I559 evidence](../../release/1.0.0/evidence/E-I557-archive-pass-budget.md) records the before/after 8.5 GiB control and 232 passing RAR tests; a later focused macOS run passed 260 archive/RAR tests. This is a documented consequential recheck of the corrected route, not a new unRAR security finding.

## Final evidence and stopping decision

- Win11 x64 Release: focused RAR reader/corpus/multipart/legacy/signature controls passed 257, skipped one existing Windows rename case; the new ratio cases are included. After the Unix archive-open and path-preservation changes, the final RAR, archive-format and source-binding group passed 323, skipped three platform-specific cases. Full Release solution built with zero warnings and zero errors. `git diff --check` was clean at the final review.
- Win11 x64 Release: 23 fixture seeds × 150 structure-aware mutations = 3,450 damaged RAR rounds passed on the corrected solid reader in 34 seconds. This is a targeted regression run alongside the already recorded 1.38 million earlier release rounds, not a claim of new million-round coverage.
- macOS arm64, .NET 10.0.12: final `RarReaderTests` passed 145/145, including direct and linked FIFO controls and the crafted solid ratio cases. The combined `ArchiveFormatTests`, `ArchiveSourceReplacementTests` and `ArchiveMultipartRarTests` passed 80/80; this includes 7z, RAR 4/5 and multi-volume healthy controls, source replacement, and the bounded TAR extraction fixture. The initial failed/stalled intermediate runs and their causes are recorded above; only the final corrected runs count as passes.
- Ubuntu 24.04.5 x64, .NET 10 SDK 10.0.403: final `RarReaderTests` passed 145/145 and the three archive classes passed 80/80 in separate processes, all with exit code 0. This is the distinct Linux native-open branch and the same positive archive controls; it does not add new fuzz rounds.
- Before committing, local `main` fast-forwarded through seven release-documentation/SBOM commits to `e924db62`; none changed the audited archive or test files. The integrated full Release solution built with zero warnings/errors, and the final Windows RAR/archive group again passed 323 with the same three platform skips. This is the commit base for the fix.
- No Critical route was established. Source review found the RAR header/name/member/window/filter limits and checksum and missing-volume checks already present; the release corpus and current fuzz runs did not establish a separate High outcome in those paths. Volume discovery can enumerate many neighbors, and normal solid preparation can take noticeable time for a large archive. After I559, the run has an aggregate expansion-ratio limit and per-member declared-size limits, but no absolute 8 GiB aggregate ceiling. That proportional cost is not claimed as a distinct proved High issue here. No cancellation guarantee is claimed for synchronous `OpenContent` or solid predecessor preparation.
- Stop rule applied: for each proved High route, retain one adverse fixture and healthy countercontrols, stop repeating equivalent fuzz or platform cases once the corrected route passes, and do not broaden the fix without a new consequential failure. No additional high-ROI security change is established by this audit.
