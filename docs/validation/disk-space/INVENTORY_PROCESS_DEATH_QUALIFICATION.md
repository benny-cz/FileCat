# Private inventory process-death and close outcomes

This packet tests abrupt termination of a child executing the production private inventory/replacement code. It does not establish power-loss durability, the physical desktop/package matrix, full disk-space plan completion or the final independent review. Product command/action gates remain off.

The test parent starts one exact owned child with an empty generated fixture root. The child creates independent original/neighbor inventories and stops at a selected native worker boundary. Its readiness record identifies its PID and expected complete-byte hashes. The parent verifies that identity, kills that process without managed cleanup, awaits actual exit, checks temporary names and an unrelated canary/neighbor, and opens the remaining private catalog afresh. Reading does not replay recovery. A separate fresh runtime review must explicitly restore or finish any pending replacement, followed by full-byte and metadata checks. Each child is awaited in the test's finally before another tester can use the guest.

The 25 cases cover creation before first write, flushed anonymous bytes, the prepared preserving decision, pending metadata move, incoming publication/close, backup flush/publication/close, immediately before/after atomic switch, actual new main close, new catalog flush/publication/close, previous-copy removal, pending metadata removal, writer close and completed owner close. Additional restore choices exercise both versions at representative pending states. All copies remain in an owner-private generated fixture; these tests grant no generic source authority.

The r959 baseline passed all25cases on Mac and Ubuntu. Windows passed19 and failed6: stage-created, stage-flushed, review-ready, marker-moved, backup-flushed and catalog-flushed left an unpublished `.staging-*` name after actual process exit. Those failed results are retained. Ordinary managed disposal had hidden this cleanup gap; the tests never delete/reopen an orphan to make the assertion pass.

Windows staging now requests FILE_DELETE_ON_CLOSE in the create itself and uses exclusive sharing. No managed instruction is needed to arm cleanup after creation. After create-new held-file publication succeeds, the implementation clears the per-open on-close disposition, flushes and verifies the ordinary private file before confirming publication. Failure remains publication-uncertain; no classic disposition fallback was added. The on-close flag is documented by Microsoft in [FILE_DISPOSITION_INFORMATION_EX](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntddk/ns-ntddk-_file_disposition_information_ex); actual VM tests determine whether the supported guest provides the required behavior.

Two further native controls close the application owner while its prepared review remains outstanding and inject a failure after the actual native root close. The root is closed once. The owner Dispose task retains its close failure, and the review reports uncertainty while retaining a confirmed new-save receipt when one exists. The compound I/O owner exposes only an already completed close failure; it does not await another undecided scope or change ownership of arbitrary returned query resources.

The corrected candidate passes all27 focused controls on Windows, Mac and Ubuntu. Windows r965 passes Core1503/1551 (48 platform skips), native75/75 and rendering395/396 (one platform skip); Mac and Ubuntu r963 each pass Core1529/1533 (four platform skips) and rendering396/396. The r965 test-fixture cleanup correction also passes both focused close controls on Mac and Ubuntu. Product inputs were unchanged for that correction; the cache proof verifies every reused input and restricts the patch to the rendering test assembly/PDB. All three post-run process inventories are empty.

Windows r963 initially failed all27 previews because its free space fell below the private-store reserve, before the new native operation could be tested. That result is retained.
