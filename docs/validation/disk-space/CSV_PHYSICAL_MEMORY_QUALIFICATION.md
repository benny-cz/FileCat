# Pinned CSV scale and native memory instrumentation

The pinned product completed the CSV scale/control cohort on the Windows VM, Mac and Ubuntu VM. Every original controller ended, results were collected once per run and all final process inventories were empty. Exact source/input hashes, terminal handles, the original measurement failure and focused rerun are retained in [the immutable provenance](source-manifest-r1173-csv-physical.json). This is a scoped resource checkpoint; public entry and the full goal remain unfinished.

The instrumentation-only harness references the exact Core DLL already qualified by [r1170](source-manifest-r1170-main-sync-input-capacity.json). It does not rebuild the product. One small bundle per platform runs a 64 MiB allocation/touch/release control, 1K wide/deep preflights, and 1M/10M wide/deep generated indexed datasets. Both CSV redaction choices verify every declared row, output bytes/hash, retained inputs, neighbor preservation and zero final quota. These are inert generated observations, not live filesystem traversal.

On macOS, `.NET` private bytes remain unavailable. Additional instrumentation reads `proc_pid_rusage` physical footprint and the kernel lifetime peak through an ABI checked against independently compiled C. The native C and managed 64 MiB controls pass. A deliberately wrong native struct size is refused before any native counter call or allocation.

Apple describes application footprint using charged dirty/compressed/swapped memory separately from clean mappings and resident size. This counter is reported with its own name and basis; it is not relabeled as committed private bytes. [Apple memory documentation](https://developer.apple.com/documentation/xcode/analyzing-the-memory-usage-of-your-metal-app)

The initial 10M Mac run exposed a sampler assumption: XNU gathers lifetime peak before current footprint, so a concurrent allocation can make the later current value exceed that earlier peak. The corrected helper retains the maximum of both observations, records raw maxima/read-skew diagnostics, and still refuses zero/error counters. A functional control verifies that an above-ceiling current value cannot be hidden by a lagging below-ceiling peak. The native ABI refusal remains required. Original successful 1M cases were reused; only the corrected controls and affected/missing 10M Mac cases reran. [XNU counter ordering](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_resource.c#L3188)

Observed Mac 1M footprint increments are approximately 93 MiB wide and 95 MiB deep. The corrected 10M refusal cases record approximately 74 MiB. Ubuntu sampled private increments are approximately 187 MiB wide and 180 MiB deep at 1M, and 159/166 MiB for the 10M refusal cases. Windows sampled private increments are approximately 152/143 MiB wide/deep at 1M and 122/117 MiB for the 10M refusal cases.

The completed 10M cases on all three platforms reach the independent 4 GiB scratch cap during report capture. They retain the complete source, open no destination, preserve the neighbor and release all source/profile quota. This is safe-refusal evidence, not complete 10M CSV export support.

Windows/Linux private-byte measurements are sampled every 50 ms, so they are not an absolute peak guarantee. Mac instrumentation combines sampled current footprint and kernel high-water observations. Full live traversal, other metrics, global multi-session memory/admission, physical input/accessibility/package and the final independent review remain open. Public feature registration stays off.
