# Native development controllers

These are the exact r60 controllers for the generated disk-space harness fixtures, retained so their evidence can be reviewed. They are not general desktop automation or complete feature/accessibility qualification. Paths and archive hashes identify the isolated r60 guest stages; reruns need a fresh task-owned stage, the corresponding bundle and updated expected hash. Never point them at a user's profile or existing files.

Mac uses System Events accessibility selection/menu actions and native Return/Space. Captures use the unchanged, already authorized FileCatCapture helper through Launch Services. Ubuntu uses observed AT-SPI targets and native X11 pointer/keyboard input. Both controllers gate competing app/test processes and request closure of their exact owned run in `finally`.

The Windows PowerShell script stages a hash-checked bundle or observes the exact owned native process and its exit. The app itself is launched interactively inside the VM with `--windows-input`; input and desktop guards are in `tests/FileCat.NativeAcceptance/DiskSpaceHarness/WindowsInput.cs`. The observer is hidden and does not need interactive mode. Do not run a live UI test on the host. A blocked foreground, competing process, deadline close or incomplete cleanup is not a passing receipt.

The r62 controllers add native navigation-link inspection to the r60 workflow. The final Ubuntu r62c controller also waits for the observed native window to be mapped, then uses native Home and verifies the captured first row before arrow navigation. Its r62/r62b attempts exited safely but are excluded from acceptance; their receipts identify the readiness and visible-row assumptions. All r62c steps use the unchanged r62 production/harness bundle.

The r71 profile controllers run three serial native processes against a fresh generated stage: create, reopen and deliberately corrupt only that stage's closed private-state file. Their reports exclude raw host IDs and require unchanged509 source paths plus owned exit. These are metadata/persistence/visible fallback checks, not physical-input or a11y proof. Mac used unix-native-profile-r71.py; Ubuntu's final r71b controller enumerates owned visible windows then matches the exact title, correcting the first combined-search failure without changing the binary. Windows launch is interactive through VMware Tools; its PowerShell observer remains hidden. Never run these live checks on the host or against user profiles.

The r79 ordering controllers use two serial generated processes. They save both Name directions, reopen them after process restart, compare actual rows and all5 inventory/catalog hashes, retain exact private-state/source bytes and require owned exit. Windows uses a VMware Tools interactive launch and hidden observer; Mac uses existing authorized capture; Ubuntu uses PID-enumeration/exact-title discovery. This is a self-driving functional/native-rendering subset. The inherited hasQualifiedHostProfile receipt field only indicates recorded hp1 context; it is not authenticated host provenance or source/action qualification.

The r95/r95b controllers verify captured ranges. Windows uses guarded native Shift batches/Ctrl clicks and exact row-ID assertions. Mac uses the first exact role/name match in its known single-session owned window, native keyboard and two captures; it does not claim whole-graph uniqueness, physical pointer or full a11y qualification. Ubuntu focuses an observed row before Home, then checks native expansion/shrink. Its one-shot qualification script waits on actual FileCat/dotnet gates, runs the61-case suite, rechecks the gate and runs native input, then asserts real result/cleanup fields. Earlier focus/AX traversal failures and overlap rejection are retained as excluded attempts. Never run these live on the host.
