# Reducing qualification overhead

Use large frozen implementation batches with one build and three platform bundles. While guests run their admitted batches, continue independent code/review work. Preserve exact source and binary hashes so later results identify the tested implementation. Keep a machine's original runner until actual completion; elapsed time alone does not authorize restarting it.

Before broad Windows suites, run a short exact-count core preview and the relevant native/headless workflows. The same previews are useful on Mac and Ubuntu. Stop the batch at a failed preview. Recheck process admission before every phase and postpone if another tester is present. Never close another tester's process to obtain a test slot.

Reuse an unchanged guest build only after verifying all its cached input hashes. For test/helper-only changes, rebuild the affected test project, permit only its DLL/PDB in the delta, and run the affected workflows. Reject reuse when a product input changes. A product change still needs appropriate broad regressions; a helper fix does not by itself justify repeating all successful product checks.

Transfer one bundle per machine per candidate and collect one bounded result archive when that batch actually finishes. Avoid per-case transfers, repeated full directory copies, and repeated result downloads while a suite is still running. Keep generated fixtures and isolated guest profiles in the same batch; finish by closing task-owned processes and recording the process inventory.

Measured in this packet: the production candidate's full build took 169.70 seconds and packing exactly three archives took 23.30 seconds. The two additional indexed-source tests required a 13.25-second rendering-project build. Verified test-only bundles were about 426 KB each instead of full bundles of 42.4 MB (Mac), 39.8 MB (Ubuntu) and 78.9 MB (Windows), reducing combined transfer bytes by over 99%. The already-passing broad suites were reused; only the two new cases ran on each machine. These are observed examples, not an overall completion-time estimate.

This process reduces setup, transfer and redundant regression work. It retains actual native checks and does not substitute headless evidence for the plan's physical desktop, accessibility, display, package, resource or final independent-review requirements.

The current history workflow uses these rules across a complete browsing/opening/pinning/removal/recovery cohort rather than a separate full qualification cycle for each button. Its full three-platform bundles total 168,268,843 bytes. The following pointer-test-only change verifies every cached input and prepares three deltas totaling 1,485,578 bytes, a 99.1% reduction. Preparing those deltas took 6.65 seconds versus 19.10 seconds for the full bundles; rebuilding the rendering test project took 10.36 seconds. The product DLLs are unchanged. Only Ubuntu needed a rerun, so only its 494,903-byte delta was actually deployed. Windows and Mac retain their passing broad product results. These measurements come from `pack-timing-r1036.json`, `test-fix-proof-r1041.json` and `build-r1040.txt`.

For each next cohort, finish the related implementation and review it while an admitted guest runs. Freeze once; choose the exact affected previews and broad suites before transfer. A failed platform/suite keeps its failure receipt and receives a focused diagnosis and the necessary rerun; passing unchanged Core/native/Settings results are reused. Do not restart all platforms' broad suites just to assemble a uniform revision number. Recheck busy guests at useful work boundaries instead of repeatedly polling them, and keep one compiler active at a time. Machine contention is elapsed waiting time, not a reason to reduce native coverage or interfere with another tester.

The lifecycle cohort also qualifies cached product UI deltas separately from test-only changes. Its final delta permits only the App and rendering-test DLL/PDB pairs, verifies every other guest input, and reruns affected renderer/Settings suites on all three. Mac/Ubuntu reuse passing identical Core inputs; Windows runs its broad Core/native checks because its earlier preflight stopped that batch. The three UI delta bundles total about 8.49 MB versus 168.27 MB for the prior full bundles, a 95% reduction. Old-product negative controls explicitly retain the baseline App binaries and cannot qualify the new product. Final evidence retains each raw result archive once and derives a consolidated manifest directly from its XML, avoiding duplicate report copies and repeated manual bookkeeping.

The native fault cohort generalizes the receipt verifier so later batches reuse source/input hashing, archive bounds, exact-count checks, skip-identity checks and process inventories. It supports explicit per-suite revision overlays; a failed renderer rerun does not invalidate unchanged successful Core/native/Settings receipts. Old-product negative controls now preserve every baseline input except the declared test pair. This also avoids mistaking informational-version changes after a commit for unchanged binary inputs. Genuine Core changes still receive full three-platform regression batches.
## Native scale and shared machines

Use one verified bundle per machine and save results after each section. The Windows r1598 renderer finished 40 groups across several idle intervals. When another tester appeared, completed groups remained available and the next run resumed at the missing group. The final r1614 NVDA harness correction reused its verified guest application and transferred 134,294 bytes. Its original candidate transfer was 10,578,155 bytes.

Run independent suites across idle machines. A single guest should process its sections in sequence so each section can report which processes it owns and yield on contention. Keep the same product hashes for focused harness corrections. A later full audit can use the earlier passing cases and the rerun cases when their inputs and expectations are traceable.

The Windows r1618 sample took 155.7 seconds to create 131,072 paths and 39.4 seconds to acquire and index them. A linear creation estimate for ten million paths is about 3 hours 18 minutes. The r1634 pilot completed four 16,384-path samples across one, two, and four workers in 13.0–13.5 seconds each. A worker error stopped the final two trials. The observed spread supports keeping a single writer and persisting its fixture cursor in bounded increments.

Ubuntu's two retained-source scale reruns spent 369 and 487 seconds in the logical baseline walk. Future identical reruns can save that time by reusing a baseline tied to a verified read-only fixture image. Reuse requires a matching fixture identity, digest and baseline. A mutable source still requires a fresh walk.

The focused scratch-budget test can omit the separate DirectorySizer benchmark on a retained fixture. It records that decision in the receipt and still executes the native acquisition and partial-preview assertions. The full scale runs still measure the logical baseline. Mac r1695 yielded during the logical walk. Its r1704 retry reached native acquisition before another tester arrived and the run yielded. That retry did not produce a terminal scale verdict.
