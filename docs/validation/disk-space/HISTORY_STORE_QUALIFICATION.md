# Isolated rolling-history storage engine

The internal native history owner uses the application's separate `analysis-history` directory. The application factory checks its native identity against the named-analysis directory. A named-store owner cannot perform automatic history capture. Noncanonical inventory names, unrelated files, pending maintenance and unresolved published payloads stop automatic changes and preserve existing data.

Memory and indexed revisions are encoded into bounded unpublished staging. Exceeding the configured byte cap discards that incomplete staging and reports the reason. A complete incoming payload is published, closed and verified by native identity and full checksum before any old inventory is removed. Pruning uses the existing exact-object/hash deletion reviews under the same catalog writer lock. The new record is registered only after confirmed removals. A later failure retains the complete new payload and reports the known receipt/removals; unresolved data requires fresh review before further capture. This is not an atomic multi-file transaction.

Five native filesystem cases run on Windows, Mac and Ubuntu under the guest headless renderer. They cover memory/indexed capture, count pruning, full-checksum inspection, byte-cap refusal, protected/disabled preservation, named-file preservation, role separation and unrelated-file refusal. Existing planner tests cover finite count/age/byte proposals. The shared serialization/catalog/deletion primitives also run through the broad Core, Windows-native and rendering suites. [r1010 provenance](source-manifest-r1010.json) records the exact counts, source hashes, builds and retained reports.

Windows initially stopped at the short preflight because only 409 MB remained; its private-storage reserve correctly refused writes. The failed reports are retained. Two reviewed cleanup passes removed only terminal task-owned payload/archive paths, retaining their reports and matching host inputs. The rerun reused all 231 hash-verified inputs without rebuilding or copying the application payload. Its control transfer was 7,661 bytes versus the original 79,256,380-byte Windows bundle. All completed batches have clear final FileCat/test-process inventories.

The process now groups coherent changes into a frozen batch, gates broad suites on short exact-count preflights, supports unchanged Windows cache reruns, keeps focused reruns for helper-only fixes and collects one result archive per machine. The deployment driver also checks room for the incoming archive, extraction, the product's private-storage reserve and 256 MiB of headroom before a Windows transfer. That last check was added after this cohort's deployments and is syntax-checked; it is not claimed as live-qualified here.

This storage component is not wired to automatic completion or Settings. Private-root exclusions, policy lifecycle/recovery, browsing/pinning, full fault/resource/scale qualification and native desktop coverage remain required. Public registration and the complete persistence gate stay open. The final independent UX/UI/functional/security review has not been performed.
