# TV-01: million-entry UI and data scale

Status: **executed 2026-09-27** on one developer machine. The numbers describe that machine. They are not
guarantees (plan §21).

## Environment

| Item | Value |
|---|---|
| Machine | AMD Ryzen 9 5900X (12 cores, 24 threads), 64 GiB RAM, local NVMe, one 3840×2160 display at 100%, 60 Hz |
| OS / runtime | Windows 11 Pro 10.0.26220, .NET 10.0.12, Avalonia 12.1.1 |
| Build | Release. Startup was measured on a self-contained ReadyToRun publish; the other runs used the JIT build. |
| Rendering | Low-latency DXGI swap chain preferred (ANGLE/D3D11), with the other Avalonia composition modes as fallbacks |
| Load | Machine CPU was 7–13% busy during the interaction runs. An earlier run under 100% load from other work was discarded. |

## How to reproduce

```
FileCat.exe --benchmark 1000000 --benchmark-panels 4 [--benchmark-dir <real folder>] [--benchmark-out results.json]
dotnet run -c Release --project eng/ListingScale -- 1000000 4        # core only, no UI
```

`--benchmark` runs on isolated temporary state. Each panel lists N synthetic files with long Unicode names, using the
real record store, spill tier, and indexes. The benchmark then sends keys through the real key routing and writes JSON.

"Input to rendered" means the time until the compositor finished rendering the change on the render thread. That
includes waiting for the display's next frame.

## Results: 4 panels × 1,000,000 entries (native window)

| Scenario | Result | Target (plan §21) |
|---|---|---|

| First rows in all four panels | 566 ms (single panel, core only: 70–95 ms) | ≤500 ms first batch per listing: met per listing |
| All four listings complete | 2.9 s (was 66 s before this validation) | Bounded, with progress shown |
| Real 10k-file folder, warm | First rows 15 ms, complete 15–31 ms | ≤250 ms: met |

| Memory | Peak private 504 MiB; spill files 374 MiB | Bounded configured budgets |

## What changed because of TV-01

- **Spilled sorting reads in place.** Comparisons used one positioned read, plus a name string, per entry per
  comparison. Sorting a spilled 1M listing took 63 s on the core harness and 44 s when re-sorting in the UI.
  - Sorts, merges, and view filters now read through read-only memory mappings of the spill files: `EntryStore.SpillReader` and `EntryComparer`.
  - Names are compared as spans.
  - A sort that starts before the store spills switches to the mapped reader as soon as it spills.
  - Result: 1M × 1 now takes 1.6 s (1.4 s fully in memory). Forced external index takes 1.7 s (was 73 s). 1M × 4 takes 2.3 s (was 106 s).
- **Cell text avoids shaping.** Simple-script cells are glyph runs built from the font's character map. Complex
  scripts, combining marks, and missing glyphs fall back to `FormattedText`. Evicted runs are disposed, and the cell cache keeps about three pages.
  - Held PageDown now allocates 5× less, and GCs dropped from 14/14/2 to 2/0/0 (gen0/1/2) per 240 frames.
- **Low-latency swap chain.** It brought held-key paging from p95 19–21 ms to 16.8 ms. Key-press latency was unchanged.
  - `FILECAT_RENDERING=compat` restores Avalonia's default composition.
- **Cursor stays on the first row while a listing streams in.** Before, it stuck to whichever entry arrived first, which
  ended near row 999,488 in a million-entry folder. Once the user moves it, or a requested name arrives, it follows that item.

## Not covered here

- 150% scaling, slow or removable storage, and 100 ms network latency.
- Screen readers (TV-10).
- Keyboard auto-repeat from real hardware. Scripted keys go through the same routing.
