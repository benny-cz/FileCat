# Sparse streams through the EFS pathname binding

The internal EFS candidate inspects sparse regular files on qualified local NTFS. Before a change, it inventories the sparse flag, EOF and allocated range union for the main stream and each sparse named stream. Named-stream observations use relative opens against the held object and require its identity and actual volume binding. The range query is capped at 4,096 native records per stream and 4,096 retained ranges across the inventory. These are logical ranges reported by Windows. The adapter does not read stream payloads during this inspection.

Preparation and pre-call observations must agree on the sparse streams and their layouts. If a stream's sparse flag, EOF or reported ranges change after the EFS API is attempted, the adapter returns an uncertain result. An unreadable postcondition also returns uncertain. FileCat does not attempt an inverse or clear sparse state to make encryption or decryption succeed. Allocated bytes are observed independently from the range union because the approved encryption action may remove compression. Already-satisfied actions do not enumerate sparse ranges. The approved EFS pathname boundary still applies.

On the Windows 11 x64 VM, a normal user on local NTFS with 4,096-byte allocation units ran reviewed encrypt and decrypt round trips on five 4 MiB fixtures. They covered an all-hole main stream, holes only in the main stream, holes only in a named stream, holes in both streams, and a sparse main stream with no holes. The fixture checked held identity, both full stream hashes, EOF, sparse flags, reported ranges and allocation. Allocation stayed the same on these fixtures. Already-encrypted and already-decrypted requests made no native call. A named-stream write into an existing hole after preparation caused a no-call result. The same write after the real encryption call but before the adapter's observation caused an uncertain result on the now-encrypted object.

The combined native run passed 82 cases with zero failures. The fresh-account first-use case and FAT/exFAT evidence export were skipped in this run because they need separate fixtures. See `.tmp/filecat-sparse-efs-binding-tests.xml` and `.tmp/filecat-sparse-efs-binding-results.log`. The test exercised the held EFS binding and consent. Durable EFS job integration on x64, key and output admission, large sparse files, and further concurrency and failure qualification remain open. Product EFS stays disabled.

Each case submitted reviewed FileCat Encrypt and Decrypt jobs, plus an already-satisfied job for each action, on an all-hole main stream, main-only holes, named-only holes, holes in both streams, or a sparse main stream without holes. The observed allocation remained equal for these 4 MiB fixtures.

This qualifies the tested ARM64 durable-job path only. Large logical sparse files, independent key recovery, output routes, concurrent writes and device loss remain separate gates. Standard FileCat builds still keep EFS mutation disabled.
