# Removable NTFS storage refusal on Windows x64

On 20 November 2026, a physical USB flash drive attached to the disposable Windows 11 x64 build 26340 VM appeared as `E:` with `BusType USB`, `DriveType Removable`, NTFS and 4,096-byte clusters. Its `FCTEST` volume had about 7.45 GB free. The test used only a new FileCat-owned directory containing a 65,536-byte main stream and a named `sentinel` stream; the drive's other three root entries were left untouched.

At medium integrity, the existing prepared-volume case refused both **Compress** and **Remove compression** with `removable-media-unqualified`. A new EFS case used the internal candidate and refused both **Encrypt** and **Decrypt** with the same reason before key setup, a job or a journal. The native VSTest run executed two cases and passed both, with six other prepared-volume cases skipped because their fixtures were absent. The main SHA-256 was `8C59707FC80AFE7B984CD98742A49FD3165E883BC3814C889CF62AFE10C08A20` before and after; the named stream, `Archive` attribute and file ID were unchanged. The exact owned directory was removed, and the USB root entry count returned to three.

The test assembly SHA-256 was `88FEA01A264AE6A6EF353B09CCCB5A8E95EB43FF5ABBDDD6F7AD6B409F0717B0`. The TRX SHA-256 was `BA0A73E6DDDFCC40BE7D853749E7382C4E41530C9124D47C621540172B0807D2`; the independent result JSON SHA-256 was `12BFDF965703C8CA7DF09A2487ABA659BFD3798739A96948FBC6DD1B7C6E367B`. Host copies are under `E:\FileCat\.tmp\filecat-removable-nc2-r3-*`, and the VM's test receipt is under `C:\Users\Admin\AppData\Local\Temp\FileCat-Removable-NC2-r3`. This qualifies the deliberate refusal on the tested physical removable NTFS volume. Device loss during a native mutation on removable media remains unqualified, so the removable scope stays disabled.

A separate [cross-volume sparse EFS copy and move](2026-11-18-efs-native-copy.md#cross-volume-sparse-efs-copy-and-move-on-physical-usb-ntfs-20-november-2026) later passed in both directions on the same USB drive. [Existing EFS destinations](2026-11-18-efs-native-copy.md#existing-efs-destinations-on-the-physical-usb-path) refused Replace in both directions without changing either file. These FileCat transfer results do not change this storage-transform refusal or qualify physical device loss during mutation.

## Attempted physical device-loss fixture

A later opt-in, test-only compression fixture targeted the same `FCTEST` USB device. The exact PnP instance was `USBSTOR\DISK&VEN_UFD_2.0&PROD_SILICON-POWER8G&REV_DL17\220191330237F00268148C7D586&0`; its disk number, USB bus, size, NTFS label and allocation unit were checked before creating an owned 2 MiB source under `E:\FileCatRemovableLoss685`. An idle `Disable-PnpDevice` / `Enable-PnpDevice` cycle removed and restored the expected volume. A VMware named-device disconnect did not remove it, so that command supplies no device-loss evidence.

The focused medium-integrity native test reached root inspection and stopped **before any compression call or device detach**: `CfGetSyncRootInfoByHandle` returned `0x80070001` (`ERROR_INVALID_FUNCTION`) for the held object. FileCat reported `cloud-query-80070001`, because this result does not establish that the object is outside a Cloud Files sync root. The focused TRX recorded one failed test, zero passed; its SHA-256 is `ECAA17CDB3BBCE9A7CD4526819C542546E50FB83E001DD30C293CE74A5501CD9`. The host copy is `E:\FileCat\.tmp\filecat-removable-failed-cloud.trx`. The test-only removable admission change was discarded, and the precisely checked owned USB/control directories were removed. The production refusal remains in place. Physical removable mutation and device-loss recovery remain unqualified on this VM.

### Cloud Files filter A/B on the same USB file

On 21 November, a separate, reversible probe in the same Windows 11 x64 VM inspected `CfGetSyncRootInfoByHandle` on one newly created four-byte file in a fresh FileCat-owned directory on the exact `FCTEST` USB volume. It checked the PnP instance, disk number, USB bus, 7,796,162,560-byte disk size, volume ID, NTFS label, 4 KiB allocation unit and absence of competing .NET processes. The Cloud Files minifilter (`CldFlt`) was absent before the probe. On that same file, the call returned `0x80070001` before filter attachment, `0x80070186` (`ERROR_CLOUD_FILE_NOT_UNDER_SYNC_ROOT`) while `CldFlt` was attached, then `0x80070001` after detachment. The [A/B receipt](receipts/2026-11-21-windows-usb-cldflt-ab-x64.json) has SHA-256 `42B41F2EB89047ED7A3F96771D21DED0437A475F54F801980CE2E2B5A6BFA93B`.

An independent [postcheck](receipts/2026-11-21-windows-usb-cldflt-postcheck-x64.json), SHA-256 `3FBD4F2B72990DE99A83F4A2CECFE76B6040BC367EE6C02F789A3AEE0D37785A`, found `CldFlt` absent again, the probe path gone and only the original three USB root entries. This establishes a filter-state explanation for the observed query result on this VM. It does **not** make `0x80070001` a safe production synonym for outside a sync root or qualify a storage mutation on removable media. A future opt-in test may attach `CldFlt` only to its owned test volume and must restore the filter state afterward; physical in-flight device loss remains the independent release gate.

## Managed sparse-copy USB disconnect attempt

On 21 November 2026, a separate [opt-in Core test](../../../tests/FileCat.Core.Tests/SparseCopyTests.cs) and [scoped controller](../../../eng/validation/Invoke-SparseCopyUsbDeviceLoss.ps1) attempted to copy a 16 MiB sparse file into a new `FileCatSparseUsbLoss-` child on the same physical USB drive. The controller required its exact USB PnP ID, 7,796,162,560-byte disk size, `FCTEST` volume ID, removable NTFS, 4 KiB clusters, Windows 11 x64, a fresh owned destination and no competing .NET processes. The medium-integrity test reached its first 4 MiB write and paused. `Disable-PnpDevice` then returned **Generic failure**; the controller wrote its abort marker. No volume-absent observation or post-detach copy result occurred, so the one-case [xUnit XML](receipts/2026-11-21-windows-sparse-copy-usb-attempt-x64.xml) recorded one failure and zero passes. Its SHA-256 is `2EEE8B1D075AF381C7A3BF92A979EA0E177828EF4722229A63DBFE0878B2C5E2`; the [controller status](receipts/2026-11-21-windows-sparse-copy-usb-attempt-x64.json) has SHA-256 `4B442A3AC52187A462F03592F2286A8130644734557B4AE93010657EA6F848F2`. The test assembly SHA-256 was `8B089803BC1912D651F6842CE9088B56D5A819D79F4B3B6E18D6D5BE467582C5`.

The independent [postcheck](receipts/2026-11-21-windows-sparse-copy-usb-postcheck-x64.json) found the original disk, PnP identity, volume and three original root entries, plus only the empty owned test directory. Its SHA-256 is `644C0FD924D3B3CEB3E7328DCB293833B290D993C4F9899C7630B3E48F1E3EC6`. Exact-identity [cleanup](receipts/2026-11-21-windows-sparse-copy-usb-cleanup-x64.json) removed that empty directory and restored the three-entry root; its SHA-256 is `FB1B0BB1260B7153352781B3D2FCD776F9536A0D0CD53BEA71F22CDDE19E9737`. The preceding idle PnP cycle shows the device can be disabled when idle, but this in-flight attempt does not establish why Windows rejected the disable request. Physical USB loss during sparse copy and storage mutation remains unqualified. The independent VHDX [x64 device-loss result](2026-11-20-windows-sparse-copy-race.md#device-loss-after-a-partial-sparse-copy-on-windows-11-x64) remains scoped to the virtual disk.

## PnPUtil removal attempt and VM snapshot recovery

On 21 November 2026, a separate idle probe used `pnputil /remove-device` for the exact USB PnP instance and `pnputil /scan-devices`. The [idle receipt](receipts/2026-11-21-windows-usb-pnputil-idle-x64.json), SHA-256 `8C4DAE2F33190CA8EF7814626D85432DF132F8CEB1E6D41DFA1A04786A15F9FF`, recorded removal exit 0, an absent `E:` volume, rescan exit 0, restoration of the exact USB fixture and the three original root entries.

An uncommitted, test-only variant of the sparse-copy controller then tried that method after the medium-integrity copy reached its first partial write. The [controller status](receipts/2026-11-21-windows-sparse-copy-usb-pnputil-failed-x64.json), SHA-256 `B8E1193AF39419D734CF7128FB7E4DE0DF11283D3137054CA0AA46C0FDBEAC13`, recorded removal exit **3010**, rescan exit 0, and failure to re-establish the exact PnP/disk identity. The controller rejected the nonzero removal exit before its absence check, so `DeviceAbsent: false` is **not** evidence that the volume stayed present. It aborted without a qualifying post-detach copy result or retained test XML. The test-only variant was discarded; the committed controller still uses its original method.

After this attempt, Windows stalled during startup and the VM owner reverted its snapshot. No independent post-attempt check of the original USB files was completed before that revert. This attempt qualifies neither physical device loss nor removable storage mutation. Do not infer the current VM setup from these historical receipts. The owner has instructed that no VM be restarted without explicit permission and that Windows Sandbox must not be substituted for a failed VM run.
