Inspecting the file through a directory alias into the sensitive volume reported its actual sensitive device. FileCat’s explicit full reports matched all six cases. ## APFS Unicode lookup and stored spelling

On macOS 10.13 and later the full report describes Apple’s documented normalization behavior when the second Darwin response confirms APFS on the observed device. Lookup treats canonically equivalent names alike and the volume preserves the stored spelling. This description comes from the documented filesystem behavior. The case flags still come from the native validity mask. A mismatched device, malformed reply or failed query leaves the normalization row uninspected. [Apple’s APFS filename documentation](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/APFS_Guide/FAQ/FAQ.html)

On macOS 27.2.1 ARM64, the native fixture verified both case variants with names stored in composed and decomposed form. Each alternate spelling resolved to the same inode, directory enumeration retained the original bytes, and an exclusive create of the alternate spelling returned `EEXIST`. FileCat’s full report identified the correct volume through the original files, alternate spellings, a leaf link, and a parent link. The summary omitted the namespace section. The focused suite passed 32 tests and skipped 10 platform or opt-in cases. Both images were detached. The native controls and `apfs-normalization.trx` are under `~/FileCatValidation/filecat-apfs-normalization-98833205-r1`.

## APFS file sharing

The full report queries Darwin’s extended attributes for an ordinary file on the observed APFS device. The second sample must agree on file kind, device, file ID, creation and change timestamps. FileCat displays private bytes, clone ID and the sharing flags from their own returned fields. The summary stays on the minimal metadata request. Links and directories omit the sharing section. [Darwin extended attribute constants](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/attr.h).

On Apple silicon with macOS 27.2.1, a native `clonefile` fixture reported all blocks shared and zero private bytes for the source and its untouched clone. A byte-for-byte ordinary copy reported its full 524,288 bytes as private. A second clone with its first 65,536 bytes rewritten reported possible sharing and 65,536 private bytes. An independent Darwin query observed that this clone’s ID had changed while its sharing flag remained set. FileCat preserved all fixture bytes, and the full report remained metadata-only. The report describes per-file evidence. Total sharing and reclaimable space require a separate observation.

The focused Core suite passed 32 tests with nine platform or opt-in skips. The result is `~/FileCatValidation/filecat-apfs-sharing-8cc99073-r2/apfs-sharing.trx`. The tested `FileCat.Core.dll` SHA-256 is `FE6CD19453D431DCD26F6F33166983529CBD349CD4F3E381D04B15430412D90B`.

The full report now displays the returned APFS sparse representation flag independently of allocation and sharing. On the same Mac, an independent `SEEK_HOLE` and `stat` probe found a real hole in a 64 MiB fixture with 20 KiB allocated and observed the returned `0x10` bit. A 1 MiB seek gap allocated the intervening blocks on that volume and returned the bit clear. The native FileCat fixture used the qualified larger gap, reported **Set** and retained the original logical length. The ordinary and cloned files reported **Clear**.
