# EFS checks in administrator copy

The administrator broker checks the actual opened source before admitting its copy, including children discovered inside a selected folder. A regular file is bound again relative to its held parent and must still have the inspected identity. The broker checks its held EFS attribute before and after each payload read and before publication. An observed change aborts the copy and cleans the owned stage. An encrypted source or directory recognized during admission is refused before its destination is created. Ordinary download-mark handling remains in the copy path.

Replacing an existing EFS file is refused. The broker reopens the replacement name relative to its held destination directory at publication and checks its identity and EFS state. A destination initially absent uses a no-replace rename even in a Replace copy, so a later arrival cannot be replaced by that call. The pre-rename check does not establish atomic identity or EFS-state protection for an existing replacement target with a concurrent namespace writer. That case remains open under E-OUT5.

On local NTFS in the Windows 11 x64 VM, fixtures refused an encrypted selected source, an encrypted child found after entering a clear directory, an encrypted existing destination and a destination encrypted during staging. A newly arriving EFS file survived a no-replace publication attempt. An attempted `EncryptFileW` through Windows itself succeeded even with an existing reading handle that denied write and delete sharing. The revised broker observed this change before reading payload, refused the copy and removed its empty stage. Ordinary share-mode admission alone did not establish stable EFS state in this fixture.

The limited-session run passed 40 tests with zero failures. Its high-integrity-only control was skipped. The high-integrity run passed all 41 cases, including the protected-destination runner control. See `.tmp/filecat-efs-broker-copy-b-tests.xml` and `.tmp/filecat-efs-broker-copy-b-high-tests.xml`. The original sharing assumption is recorded by the failing control in `.tmp/filecat-efs-broker-copy-tests.xml`. The tested checks do not prove continuous EFS state against a transient change between observations.

## NTFS transaction follow-up, 18 November 2026

The broker holds a transacted clear read of the same file identity on a volume that advertises EFS. The read lease spans the payload, mark review and publication. When replacing an existing file on an EFS-capable volume, it checks the identity both on the transacted handle and relative to the held destination directory. It moves the exact original to a private name and prepares the new file and its download mark in that same transaction. It publishes with a handle-relative no-replace rename. It also refuses an observed EFS directory default before creating output. A volume that advertises EFS must allow the applicable transaction before the broker copies. Windows documents the EFS exclusion and the isolation of transacted file changes. [Microsoft TxF programming considerations](https://learn.microsoft.com/en-us/windows/win32/fileio/programming-considerations-for-transacted-fileio-)

The Windows 11 x64 VM ran 22 broker cases at integrity level 8192 and another 22 at level 12288. All passed. Windows refused attempts to encrypt the held source and held replacement target during the copy. The marked replacement retained the original name externally during staging, committed the new bytes and mark together, and kept the original identity, bytes and mark when the test stopped after staging payload. The encrypted source, recursive child, existing destination, newly arriving destination and encrypted destination default cases all preserved their intended protections. The protected-directory runner control passed at high integrity. See `.tmp/filecat-broker-efs-transaction-medium-tests.xml` and `.tmp/filecat-broker-efs-transaction-high-final-tests.xml`.

Standalone native canaries also verified commit and rollback with the volume-GUID path, a held-folder rename and an alternate stream. Holding the original ordinary stage creation handle while trying to attach a transaction conflicted with NTFS, so the replacement stage is created inside the transaction. The results establish the tested x64 local NTFS path. Wider filesystem and architecture qualification belongs to N-OUT and the release gates.
