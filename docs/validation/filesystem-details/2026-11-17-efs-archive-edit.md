# EFS at archive edit and working-copy capture

Legacy ZIP edit creation now holds the actual outer archive while checking the EFS attribute, reviewing the member and creating the session. The ZIP content provider also checks the index's held source before extracting a member for an edit. The reviewed native ZIP route makes the same held index check in addition to its existing native outer archive admission. Ordinary ZIP viewing uses its existing path.

Commit and Save Copy refuse a currently EFS-encrypted working file before writing a snapshot or temporary payload. Native sessions check the held working handle in the private edit namespace. Legacy commit and Save Copy hold the file while checking it, and the local content provider's own handle is checked in Save Copy. Read-only review continues to recognize the existing file.

The Windows 11 x64 VM ran as a normal user on local NTFS. A legacy edit refused an outer ZIP encrypted after the original item was captured and whose earlier byte count and modified-time baseline still matched. No edit store was created, and ordinary member reads still worked. Separately, both native and legacy edit records refused commit and Save Copy after their original working file was encrypted outside FileCat. The tests observed no new captured output, unchanged file contents and retained EFS state. The Windows archive and edit regression run passed 94 with zero failures or skips. See `.tmp/filecat-efs-archive-edit-tests.xml` and `.tmp/filecat-efs-archive-edit-results.log`.

The portable ZIP and edit regressions passed 86 cases each on the Ubuntu VM and Mac. Each skipped 19 Windows-only sharing and byte-lock controls. The remote XML is under `.tmp/efs-archive-edit-check/results.xml` in the existing test checkouts. These cases cover the direct outer ZIP and working-file capture boundaries of E-OUT8. Nested container origin and broader recovery/output admission still require their own qualification.

## Temporary output and recovered Save Copy

Working-file and capture writers now check the actual opened temporary file before the copy loop reads any payload and again before each write. Windows native capture also checks the held file and its download-mark stream during verification. A recovered native capture checks the retained payload and its mark before hashing, during guarded reads and again after the complete review. Recovery identifies a protected capture as needing review and keeps it. Recovered Save Copy checks its actual native output when created, during writes and at verification.

Five new medium-integrity Windows 11 x64 NTFS cases passed. The legacy and native-backed live Save Copy captures refused a temporary file that inherited EFS from its parent. Both left their working file unchanged and removed the temporary folder. Recovered Save Copy refused a snapshot encrypted before review and the same change made after the destination stage was created. The initial refusal left no intent or destination payload. The later refusal kept the intent, and any destination artifact had zero length. A separate encrypted destination fixture refused the inherited stage before payload and kept its intent. All three kept the verified capture's bytes and wrote no saved copy. The wider Windows run passed 466 cases with 16 fixture-specific skips. Ubuntu passed 630 edit cases with 31 skips, and macOS passed 628 with 33 skips. See `.tmp/edit-efs-output-r3.log` and `edit-efs-output-core.trx`.

These checks qualify the observed source and stage boundaries. The checks take samples on held handles during the operation.

## Live Save Copy publication

On local NTFS with transactions available, live Save Copy checks the captured payload and opaque download mark while holding the actual source against EFS changes. It writes and verifies the stage inside a transaction in the held destination directory. Replacement holds the reviewed clear file in that transaction and publishes by handle. The prepared stage and removal of the prior name commit together. An EFS snapshot, an EFS destination, an EFS destination folder or a competing newly created destination stops publication. Cancellation before commit rolls the replacement back. [Microsoft's transacted file I/O considerations](https://learn.microsoft.com/en-us/windows/win32/fileio/programming-considerations-for-transacted-fileio-).

The FAT32 fixture advertised EFS support and an EncryptFile call produced an `Encrypted` file with an AES-256 key association reported by `cipher /c`. Save Copy declines publication on this volume, which lacks transactional EFS isolation. The tested Samba share accepts a new name and declines existing destinations before staging. A destination that cannot retain the capture's download mark produces a warning after successful publication. Broader providers, native architectures and recovery qualification remain open.

All nine live publication cases passed on the medium-integrity Windows 11 x64 VM. The wider native regression passed 475 cases with 16 fixture-specific skips and zero failures. The Ubuntu VM passed 630 portable edit cases with 31 skips. The Mac passed 628 with 33 skips. See `.tmp/edit-live-save-copy-r8.xml` and `live-edit-copy-core.trx`.

## Working-file and recovered-snapshot holds

Windows commit capture, live Save Copy capture and recovered Save Copy now hold an EFS-capable input in a read transaction. The transaction open must match the identity of the actual readable file. An already encrypted input refuses before capture. An EFS-capable source whose protection cannot be held also refuses. The ordinary read-only working-file review keeps its existing sharing behavior. [Microsoft's transactional EFS contract](https://learn.microsoft.com/en-us/windows/win32/fileio/programming-considerations-for-transacted-fileio-#encrypted-file-system).

The Windows 11 x64 NTFS tests attempted encryption after the working-copy stage existed, in commit and live Save Copy with each storage mode. Windows refused the encryption during each capture, and each capture contained the full clear payload. The same working file could be encrypted when capture ended. The recovered Save Copy fixture attempted encryption of its actual retained snapshot after opening the destination stage. Windows refused the change, and FileCat published the verified bytes. An initially encrypted recovered snapshot and a stage inheriting EFS still refused. This qualifies the tested working and recovered sources. Outer archive provenance, live native snapshot use by later jobs and broader output qualification require their own evidence.

The medium-integrity Windows regression passed 476 cases with 17 fixture-specific skips. The Ubuntu VM passed 630 portable edit cases with 31 skips, and macOS passed 628 with 33 skips. All three runs had zero failures. See `.tmp/edit-capture-protection-r2.xml` and `edit-capture-protection.trx` in the Unix test checkouts.

## Live native snapshot hold and retirement

An ordinary write handle let Windows encrypt a retained snapshot and caused a transacted read open to fail with `ERROR_TRANSACTIONAL_CONFLICT`. FileCat now holds a second handle to the completed file, closes the writer, and opens a transacted reader with delete access. The transacted file must match the held file and its name in the private directory. FileCat rechecks the captured hash and exact download mark before it publishes the capture receipt. The transaction remains live across every job reader. Verified cleanup retires the same held file through the transaction. If the capture is kept for recovery, closing the read transaction leaves the payload and its records in place. [Microsoft's transacted file I/O considerations](https://learn.microsoft.com/en-us/windows/win32/fileio/programming-considerations-for-transacted-fileio-).

On local NTFS, Windows refused encryption during reads of both marked and unmarked edit snapshots. The job-facing readers returned the exact bytes and repeated reads retained the same input. Disposal removed FileCat's own captured file and left the working edit available. Recovery and exact-cleanup regressions passed in the same run. The medium-integrity Windows suite passed 478 cases with 17 skips. Ubuntu passed 630 portable edit cases with 31 skips and macOS passed 628 with 33 skips. All three runs had zero failures. See `.tmp/live-edit-snapshot-seal-r2.xml` and `live-edit-snapshot-seal-r2.trx` in the Unix checkouts.

## Legacy commit-copy hold and cleanup

The legacy Windows commit route records the file identity when it creates the temporary payload. After closing the writer, it reopens the same identity, holds its clear EFS state in a read transaction, and compares the complete contents to the capture hash before submitting the job. The ordinary ZIP job can still open the path while the protection hold is active. Cleanup on EFS-capable volumes uses a separate transaction to remove only the recorded clear file. It keeps a protected file or one whose identity or protection cannot be established. [Microsoft's transactional EFS contract](https://learn.microsoft.com/en-us/windows/win32/fileio/programming-considerations-for-transacted-fileio-#encrypted-file-system).

On local NTFS, an attempt to encrypt the legacy commit copy during the job reader's lifetime was refused. The actual ZIP job committed the expected edited member, and FileCat removed the temporary copy while keeping the working file. A fixture independently encrypted a finished capture before it could be sealed. FileCat refused preparation and kept both the protected capture and the working file. A Save Copy refusal also kept its independently encrypted temporary source. The Windows regression passed 480 cases with 17 skips. Ubuntu passed 630 edit cases with 31 skips, and macOS passed 628 with 33 skips. All three had zero failures. See `.tmp/legacy-edit-snapshot-seal-r2.xml` and `legacy-edit-snapshot-seal.trx`.
