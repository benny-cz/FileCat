# Windows EFS copy and move qualification

An EFS fallback decision names the source, destination and any temporary copy. Skip is the initial action. An approval applies to one native copy attempt. A failed attempt first tries preservation again before asking for a new approval, and the job cannot reuse a decision made for another file. A copy-then-delete move checks output protection as part of rechecking bytes and checks it again before attempting deletion. An observed clear or unreadable output leaves the EFS source in place when loss was never approved.

The Windows 11 x64 VM passed 20 focused tests. Native NTFS copy and NTFS-to-FAT32 copy and move retained EFS without asking for a clear copy. A fixture forced a copy-then-delete schedule between NTFS directories and decrypted the published file before retirement. The job retained the encrypted source and reported the loss of protection on the copy. Replacement and extraction regressions passed in the same run. Two target-specific tests skipped because a destination that refused EFS had yet to be prepared. Ubuntu and macOS each passed 16 portable transfer tests, with six Windows-specific skips each. They verified that retry and a second input cannot reuse an earlier fallback decision.

The FAT32 and exFAT probes on this Windows build each advertised `FILE_SUPPORTS_ENCRYPTION` on the actual destination handle. `CopyFile2` without the loss flag returned success, and both `FileEncryptionStatusW` and `QueryUsersOnEncryptedFile` confirmed EFS on the new file. These results cover those specific mounted VM filesystems.

On the authenticated Samba share backed by ext4, `CopyFile2` without the loss flag failed with `ERROR_ENCRYPTION_FAILED` and left no file. An approved attempt holds the EFS source and the output parent through the question. Windows opens the stream handles and FileCat checks the source ID and the output's ID under the held parent before the stream starts copying. The tested SMB server rejected `FileIdInfo`; it returned matching nonzero serial and file index fields for the simultaneous output handles via `GetFileInformationByHandle`. Unknown or mismatched identity refuses the stream. [Windows CopyFile2 stream messages](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-copyfile2_message) · [Windows handle information](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfileinformationbyhandle)

The final Windows x64 suite passed 25 tests, with no skips. It covered authorized clear copy and move, explicit refusal that kept the encrypted original, an empty encrypted source, and a Keep Both conflict that exposed both the stage and final names in the question. Renaming the reviewed output folder and putting a new folder at its former name while the question was open caused Windows' copy to be canceled. Neither folder received a file and the original remained encrypted. Results are in `.tmp/filecat-efs-copy-bound-final-tests.xml`. Wider server, destination and architecture qualification remains open.

## Sparse allocation reporting

The copy and copy-then-delete paths report possible allocation growth in Operations when a nonempty source has the sparse attribute and the published copy lost it. Direct copies use the confirmed destination metadata. Staged copies check the final name after publication because the sparse attribute observed at the staging name can differ on SMB. The clear-copy EFS question also discloses possible growth for a sparse source before an approved attempt can write bytes.

On 2026-11-19, the Windows 11 x64 VM (build 26340, medium integrity RID 8192) copied 4 MiB sparse sources from 4 KiB NTFS. On NTFS the ordinary and encrypted copies retained the sparse attribute. On the 1 KiB FAT32 test volume, an ordinary copy and a staged EFS Keep Both copy lost the attribute and produced an Operations warning at their published names. The encrypted copies retained EFS on both volumes. The authenticated ext4-backed Samba fixture verified the allocation disclosure and the exact temporary path before approval, then checked the warning against the published clear copy. All five copies preserved the expected bytes and left the source ranges unchanged. The staged copies preserved the pre-existing destinations and left no temporary siblings.

The Windows suite passed 78 cases. Two cases skipped because they require separate fresh NTFS and large-file fixtures. The FAT32 image was detached after testing. See `.tmp/filecat-sparse-copy-121afad6-r4-FileCat.Platform.Windows.Tests.xml` and `.tmp/filecat-sparse-copy-121afad6-r4-controller.log`. Ubuntu passed 773 portable transfer regressions, with nine Windows-only skips. The TRX is in `~/FileCatValidation/filecat-sparse-copy-121afad6-r4/portable.trx` on the Ubuntu VM.

## NTFS main data, named streams and protected destinations

The Windows 11 x64 VM ran seven cases at medium integrity (RID 8192) on 4 KiB NTFS. Native copy and same-volume move preserved EFS and the exact main and named stream bytes without a decryption prompt. The move preserved the original file identity. A copy-then-delete move retained its encrypted source when the output lost EFS before source retirement. The remaining four cases refused replacement of an EFS destination, including protection changes before and during bound replacement, and kept the original data. All seven cases passed with zero skips. The x64 receipt is `.tmp/filecat-arm64-efs-copy-3adf9280-r1/x64-results-r2.xml`.
