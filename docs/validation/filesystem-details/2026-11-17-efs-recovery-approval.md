# EFS recovery declaration and changed key detection

The guarded EFS binding requires an explicit recovery declaration for a certificate actually associated with its reviewed zero-byte setup file. The declaration is tied to the invoking user, scope, action, review revision and original object bindings. Preparation and call admission both require a fresh silent match of the exact private key. A different scope and a missing or inaccessible reviewed key prevent a new encryption call. Already-encrypted items need no setup, and decryption needs no encryption-key recovery declaration.

Windows still chooses the key for each encryption. After the call, the adapter queries the original held object's actual user associations and checks the invoking user's key again. An unexpected or unresolved association returns an uncertain result for review, with the observed encrypted state and relevant reviewed and unexpected thumbprints when available. The adapter does not undo encryption. An existing recovery arrangement is a user declaration, and FileCat does not verify restored access from it.

On the Windows 11 x64 VM, a raw probe used a disposable standard account with a loaded local profile. On NTFS, Windows associated key A with an encrypted file and with a directory marked for encryption. After `cipher /k` created and selected key B, the earlier file still used A, while a newly encrypted file and a new file inherited from that directory each used B. A folder association cannot establish the key used by its descendants. See [Microsoft's cipher command reference](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/cipher).

The guarded binding then passed the native key-change regression in the same isolated test account. The test rotated the real Windows default after preparing a file with a recovery declaration for the previous key. The API encrypted the file under the new key. The binding returned `Uncertain` with `efs-recovery-review-required`, both thumbprints, and successfully re-read the held association. The file retained its synthetic content. The combined normal-user suite passed 82 cases with zero failures. It also verified missing or mismatched approval, successful encryption with the expected key, and the already-encrypted no-op without a recovery declaration. Three fixture-specific cases were skipped in the combined run. The rotation case passed in its dedicated run, while the fresh-account setup and FAT/exFAT export fixtures were absent from this run.

Evidence is retained in `.tmp/filecat-efs-key-switch-probe-results.log`, `.tmp/filecat-efs-recovery-tests.xml` and `.tmp/filecat-efs-recovery-rotation-tests.xml`. The declared recovery path is qualified here at the held-object boundary. Parented backup/export, provider UI, structured durable job evidence, recursive orchestration and the output gates remain open. Product EFS remains unavailable.
