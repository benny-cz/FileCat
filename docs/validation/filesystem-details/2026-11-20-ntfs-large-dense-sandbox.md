# Large dense NTFS removal on Windows 11 x64

On 20 November 2026, the opt-in N-C2 fixture passed in an isolated x64 Windows Sandbox running Windows 11 Enterprise build 26100.9877. Its separate fixed NTFS `S:` volume was a 76 GiB expandable VHDX, labeled `FCATDENSE`, with 4,096-byte clusters. The guest had no network access. The test ran as `FileCatDenseFixture` at medium integrity (`S-1-16-8192`), without Administrators group membership. The Cloud Files minifilter was attached to the test volume, and the test account could create a private journal directory there. The test assembly SHA-256 was `314138FECCC91286F13AC912C8A9AED7FB3BF88F6B438D3FE4691500B1363B07`; its native broker bootstrap built with zero warnings and errors. The [volume preflight](receipts/2026-11-20-dense-ntfs-x64/volume-preflight.json), [NTFS facts](receipts/2026-11-20-dense-ntfs-x64/ntfsinfo.txt), and [token receipt](receipts/2026-11-20-dense-ntfs-x64/standard-user-token.json) preserve the setup facts.

The short [end-to-end preflight](receipts/2026-11-20-dense-ntfs-x64/small-preflight.trx) passed after the volume was remounted and its VHDX compacted. It exercised review, private journal creation, native Remove compression and the observed call result with a 1 MiB compressed file. The large test used the exact filter `Reviewed_removal_above_the_enable_limit_preserves_dense_NTFS_streams`. VSTest 18.0.1 x64 reported one executed, one passed, zero skipped and zero failed in 16 minutes 54 seconds; the [TRX](receipts/2026-11-20-dense-ntfs-x64/large-dense.trx) has SHA-256 `CB7027F4E5F22B1B43EF467413D443887A204FEACF9834F779A4590EC209ED21` and the [controller](receipts/2026-11-20-dense-ntfs-x64/large-dense-controller.json) recorded test exit 0.

The fixture seeded an actual LZNT1-compressed, nonsparse main stream of 30,000,000,001 bytes. At the last flush, Windows reported 11,264,286,720 allocation bytes and 40,065,564,672 free bytes on `S:`. FileCat's reviewed job completed with exactly one changed item. The durable review had an observed native call, with compression enabled before and disabled after, and no pending review. The original file identity `EAAA7A74AA7A3CDF:2D00000000000B000000000000000000` remained unchanged. Full main-stream SHA-256 was `0DE5095AE6D94C8C4CA0E07E708ADCE2AD882AEE27142846C37D4442E5585115` both before and after; the named stream retained its original compression format and exact payload. The test also asserted the unchanged 30,000,000,001-byte EOF and absence of a sparse attribute.

The first 36 GiB volume exhausted free space while seeding, before any FileCat call. A diagnostic run failed at 27,845,984,256 bytes of logical input, with 10,539,003,904 bytes of stream allocation and 45,056 bytes free. At an earlier 10.1 GB checkpoint, `fsutil volume diskfree` showed about 3.9 GB used and 10.2 GB reserved. The fixture now requires 74–78 GiB and an additional 35 GiB of free space above the target length. Detaching the VHDX for expansion removed its `CldFlt` attachment, and Windows Sandbox's overlaid system drive did not admit the temporary evidence directory. Reattaching `CldFlt` to `S:`, placing the journal on that volume, and granting the test account rights to establish its private ACL resolved those setup failures. A retrim and VHDX compaction reclaimed the earlier trial's allocated blocks before the passing run.

This passes the x64 large **dense** removal case. It does not qualify large sparse removal, physical removable media, device loss during a native call, or another Windows architecture. The compression-enable ceiling remains 30,000,000,000 bytes.
