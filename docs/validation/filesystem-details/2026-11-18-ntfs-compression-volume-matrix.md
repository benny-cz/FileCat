# NTFS compression volume admission and directory defaults

The Windows 11 x64 VM ran the production candidate under medium integrity. Native GET/SET/GET distinguished compression of the main stream from both compressed and clear alternate streams. The folder tests verified that newly created files and directories inherit the current default, entries already present retain their state, and same-volume renames in both directions preserve the moved file's state and contents. Removing the parent's default affected later creation and left the previously created child default intact. [Windows compression attribute](https://learn.microsoft.com/en-us/windows/win32/fileio/compression-attribute)

The ordinary 4 KiB NTFS system volume admitted a compression review on an owned file. The 64 KiB NTFS VHD refused both actions with the allocation-unit reason. A read-only 4 KiB NTFS VHD identified its volume as read-only, and FAT32 and exFAT reported the filesystem boundary. An inspection-only review of the active Windows tree refused the target. Three sparse logical lengths, 29,999,999,999, 30,000,000,000 and 30,000,000,001 bytes, confirmed that enable admission ends above the ceiling and that an already-clear file may be reviewed for removal above it.

The Windows enumeration tests also passed the existing ordinary parity fixture, long Unicode paths, exact junction and symbolic-link tags, and empty and missing directory handling. ReFS, mapped SMB and the separately measured scale case were the three fixture skips in this combined run. The result was 59 passes with zero failures. See `.tmp/filecat-compression-volume-matrix-tests.xml`. Platform release flags remain gated.

A reviewed job removed compression from a 30,000,000,001-byte sparse file on the 4 KiB NTFS volume. The file identity, logical length, two allocated ranges, two payload sample bytes and the last hole byte were preserved. Main-stream allocation changed from 8,192 to 131,072 bytes, and the named stream's digest, allocated ranges and compression state matched its independent baseline. The case passed with completed durable call evidence. See `.tmp/filecat-storage-extra-large-removal.xml`.

Five native details cases passed. The summary and fresh metadata full report identified the actual volume format and main-stream allocation on 64 KiB NTFS, read-only NTFS, FAT32 and exFAT. The base NTFS summary/full case also passed. ReFS was the fixture skip. See `.tmp/filecat-storage-extra-details.xml`.

## Native ARM64 ABI qualification

The manually dispatched [Windows ARM64 qualification workflow](../../../.github/workflows/ntfs-arm64-qualification.yml) prepares a new fixture directory on a disposable Windows 11 hosted runner with 4 KiB NTFS. It requires a native ARM64 process, medium integrity and two executed passes. The workflow records the exact build, test binary hash, volume type and .NET runtime with the test receipt.

The compression fixture changes the main and named streams independently through the production held-stream API. It checks native formats, file identities and exact payloads after enabling and removing compression. The EFS fixture uses Windows to encrypt and decrypt an owned file with two streams. FileCat's summary and metadata-only full report observe the state transitions on the original identity. Both fixtures passed in the Windows 11 x64 calibration at medium integrity with 4 KiB NTFS. See `.tmp/filecat-storage-abi-d02cde90-r1.xml`. These fixtures cover the native ABI and read-only details. Storage job admission, key recovery, broader output routes and UI require their own ARM64 qualification.

The [hosted native run](https://github.com/benny-cz/FileCat/actions/runs/44462102280) passed both cases with zero skips on Windows 11 Enterprise build 26200, native ARM64 .NET 10.0.15, medium integrity and 4 KiB NTFS. The uploaded TRX identifies the compression and EFS details cases separately.
