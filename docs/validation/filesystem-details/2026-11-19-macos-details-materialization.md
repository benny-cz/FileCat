# macOS Details and dataless materialization

File-system Summary and Full Details set Darwin's thread-local materialization policy to Off before the first native metadata request. They restore the previous policy when the request returns. If restoration fails on a device worker, the scheduler retires that worker. Direct synchronous callers use an isolated thread. A first-query `EDEADLK` yields an unavailable observation that names the dataless item or parent boundary. A known `SF_DATALESS` object displays the returned cached information and skips the additional link, volume and sharing queries. [Apple TN3150](https://developer.apple.com/documentation/technotes/tn3150-getting-ready-for-data-less-files?language=objc)

On macOS 27.2.1 arm64, an independent two-thread probe set policy Off on one thread, obtained ordinary APFS metadata, and restored the original value. The other thread's policy stayed at its starting value. The Core fixture independently checked the live policy inside a device worker's successful full request, a simulated `EDEADLK` and cancellation. It checked the prior policy after each path and confirmed the isolation of direct callers. The APFS protection fixture passed in the same run. The focused suite passed 86 tests with 14 conditional skips. Its receipt is `.tmp/filecat-mac-dataless-policy-32120650-r1.trx`.

Apple defines `SF_DATALESS` as read-only. A scratch `chflags` experiment left the flag clear. Qualification of a live File Provider domain, including its fetch and folder-enumeration callbacks, remains open. [Apple FileFlags.dataless](https://developer.apple.com/documentation/system/fileflags/dataless)
