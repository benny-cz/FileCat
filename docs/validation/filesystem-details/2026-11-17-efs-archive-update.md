# EFS protection at archive update admission

The Windows native archive backend checks the EFS attribute on the held outer archive during target review and job scope creation. An encrypted target is refused before assessment, rebuilding or snapshot reservation. The same check runs before the native transaction, on the transaction's bound original and before retaining original bytes. The restoration lease checks the current target and retained snapshot before feeding them to its preparation path. The legacy ZIP executor independently checks the input handle actually opened for rebuilding before it digests the input or creates the temporary ZIP.

The Windows 11 x64 VM test covered the native backend and legacy executor independently. Each fixture reviewed a clear ZIP, encrypted that same file and restored its modification time. The prior baseline still matched its bytes, size and time. Both execution paths reported the EFS reason, produced no stage or snapshot, and left the outer file encrypted with identical contents. The native test calls the actual execution entry and expects refusal before any worker is needed. The test does not exercise a successful native transaction on an encrypted archive.

The medium-integrity VM run passed 22 tests across `WindowsArchiveEfsUpdateTests`, `WindowsArchiveTargetProbeTests` and `WindowsFileOperationsTests`. The elevated-only probe was skipped. Clear-target regressions include the legacy ZIP update with its original download mark. Results are retained in `.tmp/filecat-archive-efs-update-tests.xml` and `.tmp/filecat-archive-efs-update-results.log`. The build had zero warnings and errors.

This is the tested admission portion of E-OUT7 and E-OUT9. Native restoration and concurrent state changes during publication need additional qualification. Packing other EFS inputs, member editing and archive viewing/spooling are separate routes with their own requirements.

## Protection changes while the archive is open

Native review and execution bind the clear-source requirement to the actual original. The same handle checks EFS before and after every payload read and before reserving or creating rebuild artifacts. Restoration applies the read guard to both the current target and the retained snapshot. The native test opened a read view of a clear original, read one byte, then encrypted the same file through Windows. The next read returned the typed EFS refusal, left the destination buffer and stream position unchanged, and left the original encrypted with identical bytes.

Legacy ZIP rebuilding checks the held original before making its stage, around member reads, and before publication. If Windows has already replaced the original and the actual backup is observed encrypted, FileCat uses its existing replacement review to restore the backup. It verifies the restored bytes, origin mark and EFS attribute before reporting restoration. The VM ran separate fixtures that encrypted the held original during preparation and encrypted the backup during replacement review. Both retained the original file identity, contents and EFS state with no ZIP artifacts left. A protection change noticed during later backup cleanup causes FileCat to keep the backup and report its location.

The normal-user Windows 11 x64 run passed 25 cases and skipped the elevated-only target probe. The portable ZIP and publication suites passed 31 cases each on the Ubuntu VM and Apple silicon Mac. Legacy publication still uses separate pathname checks and ReplaceFile. The fixtures demonstrate refusal or verified restoration at the tested samples. They do not establish a continuous EFS-state guarantee across the Windows replacement call.

The same normal-user VM ran two native restoration cases with a real transactional TAR update, its retained snapshot and the confined worker. One encrypted the current archive after the initial update. The other encrypted the retained snapshot. Fresh restoration refused both with the EFS reason before preparing a replacement. The fixture verified the current archive, snapshot and original job journal bytes, the artifact names and the selected file's EFS state. Both cases passed with zero skips. See `.tmp/filecat-archive-efs-restoration-tests.xml` and `.tmp/filecat-archive-efs-restoration-results.log`.

## Legacy revision and catalog reads

Legacy ZIP mutation now uses a guarded reader for the revision hash and catalog in command preparation, the source in the executor, and the fresh revision check before publication. On Windows the reader checks the EFS attribute on its own open file handle before and after each read. Legacy edit creation, commit review and rebase also use this reader. An archive encrypted after editing began has a specific EFS refusal in commit review, and the working copy remains available.

The Windows 11 x64 VM passed 23 focused tests at medium integrity, with one elevated-only probe skipped. A new fixture encrypted the ZIP after the revision reader opened and before its first hash read. The reader reported the EFS refusal and left the encrypted archive intact. A second fixture encrypted the outer ZIP after creation of a legacy edit and restored its previous modified time. Commit review reported EFS and left the edited working file and original ZIP intact. Ubuntu and macOS each passed 79 focused Core tests and 545 App archive and edit tests, with 65 fixture-specific App skips per host. Windows receipts are in `.tmp/filecat-legacy-zip-guarded-reads-r1-tests.xml` and `.tmp/filecat-legacy-zip-guarded-reads-r1.log`. The Unix TRX files are named `legacy-zip-guarded-reads-core.trx` and `legacy-zip-guarded-reads-app.trx` in the validation checkouts.

These checks cover the identified mutation-read windows. The final legacy replacement still uses a pathname API and has a separate publication qualification boundary. [Windows replacement contract](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew).

## Rebuilt ZIP and publication checks

Legacy updates record the rebuilt file's identity when created and capture its complete digest through the same checked stream used for ZIP verification. On Windows, FileCat checks the stage's EFS attribute before writing and during readback, then rechecks the stage identity and digest before replacement. After the call it checks the published ZIP's protection, identity and bytes before reporting success. An EFS-protected stage stays at its temporary name with a job issue identifying it. Deletion through the Windows owned-file adapter checks the actual object's identity and EFS state on the deleting handle.

The original backup's initial verification uses the guarded reader. When protection is observed on the published ZIP, or the backup becomes protected before it can be verified, FileCat retains both names and records an uncertain outcome that identifies the backup. The existing case of a backup protected after its digest was observed still restores the whole encrypted file when the replacement and backup pass the restoration checks.

All four new cases passed on the Windows 11 x64 VM at medium integrity. They covered a changed or encrypted stage after verification, an encrypted publication and a backup encrypted before its first digest read. The wider Windows platform selection passed 45 cases with one elevated-only skip. The archive update, publication, move and edit selection passed 52 on Windows, 93 on Ubuntu and 89 on macOS, with 42, one and five platform-specific skips respectively. Windows evidence is in `.tmp/filecat-legacy-stage-policy-r2.xml`, `.tmp/filecat-legacy-stage-policy-r2.log` and `.tmp/filecat-legacy-stage-core-r2.log`. The Unix receipts are named `legacy-stage-policy-r2.trx`.

The legacy replacement and rollback still use pathname calls. The Windows replacement can merge original metadata before returning. The remaining qualification must cover the interval inside that call and partial native failures that move the original name. [Windows replacement contract](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew).

## Partial replacement recovery

FileCat flushes the exact backup name to the legacy ZIP journal before invoking replacement. Windows can report `ERROR_UNABLE_TO_MOVE_REPLACEMENT_2` after moving the original to that backup and merging metadata into the stage. The handler also retains recovery when it observes a backup or cannot verify the original at its name after another replacement error. An ordinary sharing failure with the original still at its name and no backup closes as a failed update.

When recovery can open the exact original under the backup name in a held Windows directory, it can return that file to a vacant original name by handle. The rename keeps its EFS protection and attached streams. A changed backup or an occupied original name leaves the current files for manual review. The journal keeps the archive, backup and rebuilt ZIP paths available in the Operations report across restarts. Generic partial-file cleanup does not read or delete those ZIP artifacts. Acknowledging the report can close the reminder without modifying files.

The Windows 11 x64 VM passed three cases at medium integrity. The fixtures modeled the documented partial return after moving the original and encrypting it and the rebuilt ZIP. The actual Windows recovery rename preserved the original file ID, ZIP bytes, EFS state and named stream when the original name was vacant. A separate file at the original name survived the refusal. Another case substituted a different file at the backup name and verified that it stayed there. The platform selection passed 48 cases with one elevated-only skip. Evidence is in `.tmp/filecat-legacy-partial-recovery-r1.xml` and `.tmp/filecat-legacy-partial-recovery-r1.log`.

The Core selection covering archive updates, journal recovery and sharing failures passed 49 on Ubuntu and 45 on macOS, with one and five platform-specific skips. All 26 App archive recovery-report and review-store tests passed on each host. The Unix receipts are `legacy-partial-recovery-core.trx` and `legacy-partial-recovery-app-full.trx`. The fixture models the Win32 failure at the call boundary. The race inside the native replacement and direct induction of its partial failure remain unqualified. [Windows partial replacement result](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew#return-value).

## Handle-bound rollback after publication

After a successful Windows replacement that fails an integrity check, FileCat opens the exact original and published rebuild in the held local folder. It checks their file identities, bytes, EFS state and download marks. It renames the rebuild to the reserved stage name and returns the original to the archive name. Both renames require a vacant destination. If another file takes the archive name, FileCat retains the files for Operations review. An adapter without held-file rollback also retains the evidence for review.

After the original returns, cleanup checks the held rebuild for EFS, extra links, unexpected streams and extended attributes. A failed check leaves the rebuilt ZIP available for review. The Windows 11 x64 VM verified a real ZIP replacement followed by download-mark loss, preserving the restored archive's identity and mark. Two more cases exercised an unrelated file arriving at the archive name and a named stream added to the parked rebuild. They verified that the unrelated file and added stream survived and that the retained original kept its EFS protection and bytes. The Windows platform selection passed 88 cases with six environment-specific skips, including archive move and legacy edit. Ubuntu and macOS passed 49 and 45 Core regressions, with one and five platform-specific skips respectively. The receipts are `.tmp/held-zip-rollback-r2.xml` and `held-zip-rollback-core.trx`.

The rollback evidence covers the two held-file renames and the tested metadata changes. The original `ReplaceFileW` publication interval and metadata changes concurrent with backup cleanup remain open. [Windows file rename](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information), [Windows file streams](https://learn.microsoft.com/en-us/windows/win32/fileio/file-streams).

The Windows Core selection passed 219 cases with 42 platform-specific skips. Its portable-adapter fixture verified that an original remains available for review when the adapter cannot run the held-file rollback. See `.tmp/held-zip-core-r3.log`.
