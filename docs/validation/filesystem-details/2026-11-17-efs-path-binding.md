# EFS pathname and NTFS decompression comparison — 17 November 2026

The user approved the [cooperative pathname boundary](../../design/FILECAT_EFS_PATH_API_CONCURRENCY_AMENDMENT_PROPOSAL.md) after reviewing the wrong-object risk, and separately requested decompression analysis. This note records a deterministic laboratory comparison. It does not enable EFS, qualify file-content preservation, or close E-ID/N-E1/N-ID.

The supplied disposable Windows 11 x64 VM ran the probe as medium-integrity `admin`, build 26340, .NET 10.0.15. All subjects and targets were generated **empty directories** under one verified temporary root. No user-file payload, certificate/private-key bytes, raw private encryption FSCTL or elevated transform was used. Directory EFS observations concern the **default for newly created content**, not encryption/decryption of existing descendant bytes.

Each case kept a full-sharing metadata review pin, a separate no-delete-sharing guard on the reviewed directory, and a metadata handle to an unselected sibling directory. The guard was either attributes/synchronization shared read/write, or list/add-file/attributes/synchronization shared read only. Native held-handle basic attributes and compression state were observed before and after the call. A separate **write-attributes-only** handle established a junction on the reviewed directory after its initial observations. The schedule was deterministic within one laboratory process; it was not an external-process stress test or a complete ancestor-guard qualification.

The final matrix has 24 completed cases: Encrypt/Decrypt/Remove compression × two guard recipes × direct/competing-state-clear × no-link/junction controls. No ADS was present, removing the earlier directory probe's ADS confound.

| Observation | Result |
| --- | --- |
| Ordinary rename/deletion | Not exercised in this probe; those remain independent required gates. |
| Attribute-only junction insertion | Succeeded in every one of the 12 attempted cases, including directories already marked encrypted or compressed. No selected name was deleted or replaced. |
| EFS Encrypt, no-link controls | Attributes guard succeeded. Read/write-data guard failed with sharing violation 32. |
| EFS Encrypt after junction insertion | All four cases returned success and changed the **unselected target directory's EFS default**. The held reviewed directory remained the junction object. |
| EFS Decrypt, no-link controls | Attributes guard succeeded. Read/write-data guard failed with decryption error 6001. |
| EFS Decrypt after junction insertion | Three cases returned success and removed the **unselected target's EFS default**. One attributes-guard case first cleared the reviewed directory's EFS flag; the subsequent Decrypt returned success without changing the target. |
| NTFS Remove compression through the held read/write-data handle | All four cases succeeded, including both junction cases. The held reviewed directory's default changed from LZNT1 (2) to none (0); the unselected target stayed LZNT1. |
| Attributes-only compression SET control | All four calls failed with access denied 5. The target's compression default stayed unchanged. |

This is an observed EFS redirection counterexample on directory defaults, rather than merely a theoretical sharing limitation. A strong main-directory data guard can reject an ordinary EFS call yet still allow that pathname call to affect the junction target. It therefore cannot be described as fail-closed identity protection. API success does not establish that the held reviewed object changed.

The decompression primitive behaved differently in this fixture: its GET/SET used the retained physical object's handle and did not resolve the junction target. This supports the held-object contract for this specific ordinary NTFS mount-point scenario. It does not prove universal exclusion of metadata churn, malicious filesystem filters, all reparse types, file/ADS cases or the entire product traversal. The product adapter still needs its own deterministic after-preparation regression and full N-ID matrix.

The approved EFS candidate is now: fresh case-aware no-follow admission; retained original review pins; continuously held ordinary leaf/ancestor guards excluding deletion/rename; actual invoking identity; explicit independent pathname-risk and all-stream decompression consents; supported EncryptFileW/DecryptFileW; and held-object/path post-observation that stops on detected churn or an unestablished postcondition. In-place equal-privilege reparse conversion is outside the disclosed exclusion guarantee. Guard compatibility and ordinary name-substitution prevention must still be qualified for the exact file/folder/ADS/ancestor recipe; these observations are not that complete qualification. Key/recovery, output provenance/admission and per-architecture native/UI gates remain mandatory.

Execution must use the worker's existing 188-slot native allowance, claim every open before it starts, and retain the reviewed/ancestor/current-object owners until each pathname call actually returns, even after Stop or window close. It must not acquire an independent second allowance while holding these owners. Directory listing ownership and native key/output helpers must fit the same traversal/scratch budgets; their complete compatible recipe remains to be qualified.

This candidate relies on the supported [EncryptFileW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-encryptfilew), [DecryptFileW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-decryptfilew) and [CreateFile sharing](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew) contracts under the explicitly amended threat boundary; it makes no claim that a pathname API acquires a supplied lifetime pin or freezes attribute/stream membership. The separate [API investigation](2026-11-17-efs-api-investigation.md) continues to reject private FSCTL use and the old no-decompression proof argument.
