# Reviewed Save As for EFS-derived hex edits

Save As and patch export use the same review owner for frozen ranges, observed input protection and an exact EFS output folder. Save As displays the selected destination and the exact temporary sibling. Cancel is the default. Known EFS input requires explicit approval before stage creation. Unknown input protection refuses output. The existing new-name requirement applies through publication, including a competing creation after the review opens.

The writer samples the held source before each Windows read and before writing that chunk. It revalidates the source before publication. For sparse EFS-derived input it uses the bounded held range inventory. It copies the download mark through a named stream that is verified against the held temporary file, then publishes the same file by relative no-replace rename. The approved scope covers an output that may be stored without EFS. If Windows cannot keep the temporary artifact safe during cleanup, the error includes its path.

The Windows 11 x64 VM passed 55 native tests covering hex output and sparse transforms and 24 application tests. Native results include an approved clear copy of an EFS source with and without a download mark. A sparse fixture kept the observed allocation ranges and produced the expected digest after editing, including zero reads through the holes. The dialog fixture used Enter to cancel and confirmed zero files at the displayed output paths, then deliberately approved a new review and verified the edited bytes. Ubuntu and macOS each passed 19 hex and storage review regressions. See `.tmp/filecat-efs-saveas-sparse-tests.xml` and `.tmp/filecat-efs-saveas-ui.xml` on the build host and `saveas-results.xml` in each guest's `.tmp/efs-review-controls` directory.

This covers both E-OUT3 export actions on the tested local NTFS route. The FAT32 result below covers Save As for sources without a download mark. The wider output matrix is tracked in the implementation plan.

## Sparse Save As on FAT32

On 2026-11-19, the Windows 11 x64 VM (build 26340, medium integrity RID 8192) saved 4 MiB sparse files from 4 KiB NTFS to a disposable 256 MiB FAT32 volume with 1 KiB allocation units. Both the clear source and the explicitly approved EFS source produced the expected bytes, including an edit inside a hole and zero reads through the remaining holes. Save As reported that it wrote the full logical length. The output had neither the sparse nor EFS flag, and the source retained its allocation ranges and protection state. Attempting the EFS export without approval left the destination empty. Neither successful case left a temporary sibling.

Save As uses the shared bounded range inventory for Windows sources and rechecks the observed ranges before publishing. The fragmented NTFS case exceeded the 4,096-record limit and was refused before creating any output. The application warns about possible allocation growth in the sparse EFS Save As review and reports actual expansion after a successful save. The native UI test also confirmed that cancellation leaves no output and explicit approval to an NTFS destination preserves the sparse flag.

The Windows VM passed 51 platform cases and 4 application cases. Two platform cases skipped because they need separate fresh NTFS and large-file fixtures. Ubuntu passed 108 portable Hex application cases with 4 platform or fixture skips. The FAT32 VHDX detached after testing. Build-host evidence is in `.tmp/filecat-sparse-saveas-6f805f63-r3-FileCat.Platform.Windows.Tests.xml`, `.tmp/filecat-sparse-saveas-6f805f63-r3-FileCat.App.Tests.xml` and `.tmp/filecat-sparse-saveas-6f805f63-r3-controller.log`. The portable TRX is under `~/FileCatValidation/filecat-sparse-saveas-6f805f63-r2` on the Ubuntu VM.
