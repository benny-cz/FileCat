# Reviewed Save As for EFS-derived hex edits

Save As and patch export use the same review owner for frozen ranges, observed input protection and an exact EFS output folder. Save As displays the selected destination and the exact temporary sibling. Cancel is the default. Known EFS input requires explicit approval before stage creation. Unknown input protection refuses output. The existing new-name requirement applies through publication, including a competing creation after the review opens.

The writer samples the held source before each Windows read and before writing that chunk. It revalidates the source before publication. For sparse EFS-derived input it uses the bounded held range inventory. It copies the download mark through a named stream that is verified against the held temporary file, then publishes the same file by relative no-replace rename. The approved scope covers an output that may be stored without EFS. If Windows cannot keep the temporary artifact safe during cleanup, the error includes its path.

The Windows 11 x64 VM passed 55 native tests covering hex output and sparse transforms and 24 application tests. Native results include an approved clear copy of an EFS source with and without a download mark. A sparse fixture kept the observed allocation ranges and produced the expected digest after editing, including zero reads through the holes. The dialog fixture used Enter to cancel and confirmed zero files at the displayed output paths, then deliberately approved a new review and verified the edited bytes. Ubuntu and macOS each passed 19 hex and storage review regressions. See `.tmp/filecat-efs-saveas-sparse-tests.xml` and `.tmp/filecat-efs-saveas-ui.xml` on the build host and `saveas-results.xml` in each guest's `.tmp/efs-review-controls` directory.

This covers both E-OUT3 export actions on the tested local NTFS route. Additional destination filesystems and Windows architectures remain subject to their wider native qualification.
