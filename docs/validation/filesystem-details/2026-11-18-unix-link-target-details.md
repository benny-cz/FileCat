# Stored targets and explicit Unix link navigation

Linux reads the link text from the held `O_PATH` descriptor. macOS reads it with `readlink` between two no-follow samples of link type, device, file ID, creation time and change time. The macOS report identifies those samples as the source of the observation. The pathname samples provide no lifetime pin. Both routes preserve the link’s metadata when the stored target cannot be represented as UTF-8. [Apple `readlink(2)`](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/readlink.2.html). [Darwin `getattrlist(2)`](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/man/man2/getattrlist.2).

On explicit navigation, FileCat refreshes the source observation. It then resolves the target’s parent using the native Unix pathname rules before inspecting the destination’s final entry without following it. This handles `..` after a directory alias and preserves a trailing slash as a directory requirement. The report leaves target existence unchecked until the user asks to navigate.

On APFS on Apple silicon and ext4 on Ubuntu x64, the native fixtures returned the stored target after it became dangling. They also resolved a link through a redirected parent, resolved an intermediate target alias before applying `..`, and preserved a second link as the final entry. The Linux fixture also verified that invalid UTF-8 link bytes leave type and identity available while disabling target navigation.
