# Read-only fscrypt policy on ext4

File-system details now includes an fscrypt section in **Read full record** for regular files and directories on identified ext4 mounts on Linux x64. The summary shows the separately observed inode flag. For the full report, FileCat reopens the live `O_PATH` pin through procfs, checks the object's type and identity, and issues `FS_IOC_GET_ENCRYPTION_POLICY_EX`. FIEMAP shares that descriptor on regular files. The ioctl receives a 32-byte buffer, and the returned version and size must agree. FileCat retains the policy version, content and filename mode numbers, and flags. `ENODATA` means the inspected object has no fscrypt policy. A missing descriptor, unsupported result, or disagreement with the earlier `statx` flag has its own status. Volume protection is a separate observation. [Linux fscrypt query semantics](https://docs.kernel.org/filesystems/fscrypt.html#fs-ioc-get-encryption-policy-ex) · [Linux ioctl and policy layouts](https://github.com/torvalds/linux/blob/master/include/uapi/linux/fscrypt.h)

On the Ubuntu 24.04 x64 VM with kernel `7.0.0-43-generic` and glibc 2.39, a fresh 128 MiB ext4 image used the `encrypt` feature. A normal user prepared a legacy v1 directory with no added key and a v2 directory with a disposable key. The v2 directory contained an inheriting regular file. The kernel returned version byte 0 and 12 policy bytes for the v1 directory, and version byte 2 and 24 policy bytes for the v2 directory and file. FileCat displayed the expected version, AES-256-XTS content mode, AES-256-CTS filename mode and distinct directory or file scope. A separate plain directory returned an explicit absence of policy.

Path-filtered syscall tracing observed four policy ioctls and zero payload reads across the summary and full reports for the four prepared paths. An independent one-byte read of the same inheriting file produced one traced read. The full report retained its metadata-only classification. The Ubuntu record and FIEMAP selection passed 22 tests with no skips. The Mac passed 18 of the shared tests with four Linux-only skips. The Ubuntu TRX is `FileCatValidation/ci-fix-3877f7ef/tests/FileCat.Core.Tests/TestResults/linux-ext4-fscrypt.trx`, and the native traces are in `FileCatValidation/fscrypt-ext4.oha8aT`. Wider Linux filesystems and architectures require their own qualification.

## Filesystem keyring status for version 2 policies

The full report uses the version 2 policy identifier with `FS_IOC_GET_ENCRYPTION_KEY_STATUS` on the same verified descriptor. It reports present, absent or incompletely removed in the filesystem keyring. The identifier stays in the native request, and the report contains only the status and its source. The observation depends on a readable metadata descriptor. File access also depends on permissions and active handles. Version 1 status remains uninspected because its keys can use process keyrings. [Linux key-status semantics](https://docs.kernel.org/filesystems/fscrypt.html#fs-ioc-get-encryption-key-status) · [Linux v7.0 ioctl ABI](https://github.com/torvalds/linux/blob/v7.0/include/uapi/linux/fscrypt.h)

On Ubuntu 24.04 x64 with kernel `7.0.0-43-generic`, a normal user prepared three independent version 2 keys on a disposable 128 MiB ext4 image. The kernel reported the active key present, the removed key absent, and the third key incompletely removed while a covered file remained open. FileCat matched each result through the normal details reader. The loaded key was observed on both a directory and its inheriting file. The legacy and clear directory controls did not issue a key-status query. Path-filtered tracing saw six policy calls, four key-status calls and zero payload reads. An independent one-byte read produced one traced read.

The focused Core run passed 67 cases with 11 unrelated platform or fixture skips. Both traced fscrypt cases passed separately. The source was `423311b9` plus the collector and test changes. The test assembly SHA-256 was `17e4a53c735e95e698ba0c39bb776c7a7586287b8a7ec563d5ce1da077e98b37`, and the volume was unmounted at teardown. The TRX and traces are under `~/FileCatValidation/filecat-ext4-key-status-423311b9-r1`.
