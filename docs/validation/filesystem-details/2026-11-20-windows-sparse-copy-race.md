# Windows managed sparse-copy range-change checkpoint — 20 November 2026

`WindowsSparseCopy` formerly checked EOF after copying but did not verify that the allocated-range map still matched the queried ranges. A writer could allocate a skipped hole without changing EOF, and the copy could report success while omitting that data. The copy now hashes its clipped allocated ranges as it processes them and makes a second bounded `FSCTL_QUERY_ALLOCATED_RANGES` pass before publishing the destination. A changed map, EOF, or sparse attribute fails the copy; the caller removes its partial output. The pass holds at most one 256-entry range buffer and a digest.

Native qualification used the disposable Windows 11 x64 VM, build 26340, with a 4 KiB NTFS system volume and a medium-integrity token (RID 8192). The test assembly SHA-256 was `4616A6321539AAC0A69B29AA6CD148105B788BE707A576A3BD3A04550BB9CF69`. The focused `SparseCopyTests` run passed seven Windows cases, failed none and skipped four Unix-only cases. [The xUnit XML receipt](receipts/2026-11-20-windows-sparse-copy-race-x64.xml) has SHA-256 `F51E936EC6CF753E0B7A040776CA36C41320F7030DC9B0D608FA217F5E5E5C1B`.

The follow-up matrix added source EOF shrink/growth after the first copied extent, cancellation after a data extent and cancellation of an all-hole source. Each operation discarded its destination; the changed source kept its new EOF. The implementation also checks cancellation after range verification and before final destination sizing. The updated test assembly SHA-256 was `CF2696302F920D7ED28C9B300E4791E9F391BAF28D693EE41C019C6C9105196C`. The [second xUnit XML receipt](receipts/2026-11-20-windows-sparse-copy-race-x64-r2.xml) has SHA-256 `89D46669F5AC95A8064A76E8DBDD73A95ABD6068F719A4B9255509F00B572C01`: eleven Windows passes, zero failures and four Unix-only skips.

The new race fixture starts with two 4 KiB extents in an 8 MiB sparse source. Its progress callback writes and flushes a new 4 KiB extent into a hole after the first queried extent has been copied. The operation throws the allocated-range-change error and leaves no destination. A second fixture copies 300 separated extents, crossing the 256-record query buffer boundary, and verifies the full hash, sparse attribute and low allocation. Existing all-hole, two-extent and unaligned-EOF cases also passed.

This detects allocation-map changes observed by the second pass. It does not make a snapshot of source bytes or guarantee detection of a change followed by reversal or a writer racing after the final check. Device-loss and native-owner cancellation fixtures remain open.

## Same-range writer detected by a held source change token

The Windows sparse copy now records a change token on the held source handle before range queries and compares it after copying and the second range pass. A missing token refuses sparse copy. The native fixture rewrote and flushed the first 4 KiB allocated extent after FileCat had copied it, without changing EOF or the allocated-range map. FileCat detected the source revision and removed the partial destination. The source digest changed as expected.

On the disposable Windows 11 x64 VM (build 26340, 4 KiB NTFS, medium integrity RID 8192), the focused `SparseCopyTests` class passed twelve Windows cases with zero failures and five fixture/Unix skips. The test assembly SHA-256 was `F59AADC2E48B5D891A1A5BAE732A57E81EE7A684A1A76726C65668F550255E6F`. The [xUnit XML receipt](receipts/2026-11-20-windows-sparse-copy-revision-x64.xml) has SHA-256 `C0FEB4EC2684EE264C666A0CD895DE6593FB5C4DC3D59C14D6FEA22DBD48E8CB`. This qualifies the observed same-range write on that NTFS fixture. It does not claim an atomic snapshot or detection of every post-check write.

## Disk-full partial-output cleanup on an owned NTFS VHDX

The [native controller](../../../eng/validation/Invoke-SparseCopyDiskFull.ps1) created a disposable 256 MiB VHDX, verified its newly formatted 4 KiB NTFS `FCSPARSEFULL` volume, and filled it with noncompressible bytes until 6,012,928 bytes remained. The Core fixture copied a 16 MiB sparse source with two 4 MiB data extents into that volume without preallocation. It observed the sparse destination and reached logical progress 13,631,488 / 16,777,216 before the second data extent hit `HRESULT 0x80070070` (`ERROR_DISK_FULL`). `CopyFile` threw, removed its partial destination and preserved the source SHA-256 `A6EBAFBFD2B718209FF80CCE3F3EE9E20665D6BF9B604150F3EE9B337BC14D85`. The volume reported the same 6,012,928 free bytes after cleanup.

The final medium-integrity Windows 11 x64 build 26340 run passed one case without skips. Its test assembly SHA-256 was `B8F98CB69D36EC6AA1F239525C5BBD1DA1BACF82BDE83ABB56FC91609D49D9ED`. The [xUnit XML receipt](receipts/2026-11-20-windows-sparse-copy-disk-full-x64.xml) has SHA-256 `73DDEF94BE33EC42F51BE2AF9962A3E0DCA54D1705C5C84F0DCD7DE40ED46E50`; the [controller status](receipts/2026-11-20-windows-sparse-copy-disk-full-x64.json) has SHA-256 `F66951E8899A4B4CDA0666776DFD8B900D2B27BFCAA2E613D1AFEF0724F67308`. After the test, an independent guest check found neither the VHDX file nor an attached `FCSPARSEFULL` volume. This qualifies the managed sparse-copy disk-full path on this x64 NTFS fixture, not every storage action or device-loss outcome.

## Device loss after a partial sparse copy on native ARM64

The [owned VHDX controller](../../../eng/validation/Invoke-SparseCopyDeviceLoss.ps1) created a fresh 256 MiB, 4 KiB NTFS `FCSPARSELOSS` volume on a Windows 11 ARM64 hosted runner. A medium-integrity Core fixture copied a 16 MiB sparse source with two 4 MiB allocated extents into that volume. After the first 4 MiB write, the controller detached the VHDX while the copy was paused, verified that the volume disappeared, and let the copy continue. The copy reported `IOException` with `HRESULT 0x80070015` (`ERROR_NOT_READY`); it did not report success. The controller remounted the original partition and volume identity. The source still hashed to `10D150E84DDFC019424CFD6122BB85387C12951F22C9BB5371FF4205B63B36A8`.

The [native ARM64 run](https://github.com/benny-cz/FileCat/actions/runs/44831447647) on commit `09050956efcb90fd2ed973942e820296a21a53f8` passed exactly one case, with zero failures or skips. The [xUnit XML](receipts/2026-11-20-windows-sparse-copy-device-loss-arm64.xml) has SHA-256 `C354A8DAE62716214ACF665740D7446F462BEDE8877ED5A770405AE16840333E`; the [controller status](receipts/2026-11-20-windows-sparse-copy-device-loss-arm64.json) has SHA-256 `F247DF4C7D006C2ADC8277C8C29ABC369F8C9C6DBE07F418B3212A8C82A746BD`. The test assembly SHA-256 was `0FAD8FDF627AF10ADFCEF5A33ED5C066778DEE161DEB034317FB5F6138BFB632`. The remounted volume still held a 4 MiB partial destination. Detachment can prevent immediate deletion of a partial output; the fixture records it and retires the owned image after collecting evidence. This qualifies the managed sparse-copy device-loss path at this native ARM64 shape. Native-owner cancellation, writes after the final source check, other devices and other output routes remain separate work.
