# FileCat exploratory UX and hardening plan

**Prepared and rechecked:** 30–31 October 2026. **Status:** owner resumed bounded exploratory cycles after the first tranche; this plan does not itself accept product behavior. The product source inspected when preparing it was `37e6fc0e` on `main`. Refresh the source and CI identity before executing a shot.

## Purpose and boundary

Use the wait for SignPath's response to find consequential problems in real FileCat work: understandable actions, recoverable errors, correct files and destinations, responsive controls, truthful results, and a comfortable visual hierarchy. Prefer short, surprising user journeys over another systematic platform × provider × theme matrix. A journey may cross several tools, but its value must come from a boundary that the existing evidence does not already settle. Evaluate how easily someone notices the next action, reads the outcome, and returns to their file work; functional correctness alone does not settle the UX question.

This is exploratory work, not final 1.0.0 candidate qualification. The [release dashboard](../release/1.0.0/FILECAT_1_0_RELEASE_EXECUTION_REPORT.md) remains **NO-GO**: signing/provider acceptance, a frozen installed candidate, and its other required gates remain separate. Preview.3 predates the recent product fixes. Do not treat an unsigned source build, a VM observation, or a passing exploratory shot as signed installed-candidate acceptance.

## Options considered

| Approach | Value and cost | Decision |
|---|---|---|
| Replay the 76-case UX audit or the recent I566–I572 fixtures | Strong historical coverage already exists; replay would consume native and CI time without a new question. | Exclude unless a concrete change, invalid receipt, regression, or uncovered mandatory boundary is recorded first. |
| Exhaustive combinations of platforms, themes, scales, providers and file types | Broad but expensive, hard to interpret, and likely to rediscover known cases. | Exclude. Select the one environment and presentation needed by the observed consequence. |
| Unstructured clicking or unbounded fuzzing | Can reveal surprises, but a result without source identity, owned files and a repeatable action sequence cannot drive a safe fix. | Keep the surprise; bound each shot and capture enough to reproduce it. |
| Short user task with one realistic disruption | Tests the seams between features, keeps user consequences visible, and can be stopped when evidence is sufficient. | **Primary method.** Choose tasks opportunistically from the deck below; redraw when the exact boundary is already accepted. |
| Targeted parser/resource stress | Useful after a concrete anomaly or a distinct untested trust boundary; otherwise duplicates extensive security work. | Use as a follow-up to an observed issue, with a fixed input/time/resource budget and a positive control. |
| Final installed-candidate checks | Required for 1.0.0, but their exact artifact and signing prerequisites are absent. | Preserve in the release ledger; run when the candidate exists. |

## A small deck of possible shots

These are **prompts to sample**, not claims of untested defects or a mandatory sequence. Shuffle the remaining prompts, draw one, then veto or reshape it after the evidence search; a spontaneous real-user observation can replace a draw. Across the first tranche, include both everyday file work and at least one expert inspection task; do not force every operating system into every shot.

For a repeatable draw, number the eligible prompt rows in their displayed order and use a recorded random integer to choose among them. Remove a vetoed row before drawing again. The number chooses a *starting idea*, not a prescribed test script; a live user observation can preempt it. Record every veto and its accepted-case link in the [execution log](FILECAT_EXPLORATORY_UX_HARDENING_RESULTS.md) so discarded work remains visible.

### Owner observation: Speed history presentation

The owner supplied completed and paused-operation screenshots in which **Speed history** first appeared as an oversized disclosure and then as a narrow graph surrounded by unused report space. The graph's sampling already has accepted functional coverage; the distinct questions are its visual weight, placement, expanded footprint, truthful paused state, and useful width. Compare a completed operation with a meaningful multi-sample transfer and a paused transfer. Inspect collapsed and expanded states at normal, tight and wide viewports, with keyboard focus and accessible name. Keep short metrics readable at the left; let the chart use more of the details pane without stretching it across a very wide display. A paused transfer should add zero-rate samples over elapsed time, rather than freezing at its last working rate; retain the earlier activity so the drop is interpretable. Keep the graph optional and its caption honest. The [execution log](FILECAT_EXPLORATORY_UX_HARDENING_RESULTS.md) records the scoped result and native/CI limits. Do not add a release blocker from these screenshots alone.

### One stress dial per shot

Pair the ordinary task with **one** bounded pressure: a larger realistic list or file, a second process changing an owned item, a delayed or disconnected provider, a permission/conflict change, repeated rapid input, or a tight but usable viewport. Choose the pressure because it could change that task's user outcome; do not stack them for a dramatic but uninterpretable failure. Record the chosen size, duration and stop guard before execution. A simple positive control should still work, and no negative result counts as proof of safety unless source and destination bytes or identities were checked where relevant. Resource anomalies go to a focused measurement against the existing I06 limits; exploratory screenshots or one slow run do not certify performance.

## Execution for one shot

1. **Select and bound.** Write the user goal, one perturbation, expected user-visible outcome and exact existing-evidence veto. Use a test-owned source/target and record their initial hashes or manifests when mutation is possible. Set a 45-minute exploration limit and a fixed input size. Give a deliberately held control an explicit guard appropriate to the task (30 seconds by default for UI feedback, not for a legitimate large transfer). A guard expiry is a diagnostic observation, not automatically a product failure or a performance-contract violation.
2. **Observe once.** Use a current Git-built app in the ready Win11 or Ubuntu VM, or on the Mac, as the task requires. Record commit/package identity, OS/backend, input steps, visible focus/status/target, final bytes and a screenshot or accessibility receipt where visual or spoken behavior matters. When presentation is the question, record discoverability, visual hierarchy, space used, keyboard focus, and whether expanded content remains visible and scrollable. Keep the physical Windows workstation usable; perform no foreground desktop automation or exclusive loads there. Use only owned fixtures for destructive or permission-changing cases, and do not change real recovery media or stored credentials for exploration.
3. **Triage the consequence.** Check the exact behavior against source, tests, the UX ledger, release issues and security evidence. If it is accepted behavior, explain it and stop. If it is ambiguous, run one narrower positive/negative control. If it is a real new failure, reproduce on an owned fixture before changing code. Do not claim a security defect from a confusing label alone, or a UX pass from a component test alone.
4. **Fix only proved problems.** Prioritize wrong-item/data-loss/security or blocked core work, then repeated substantial friction, then polish. Add a regression for the user-visible invariant when it protects the fix; avoid tests that mirror implementation order. Run affected tests and the required latest-source CI after a product change. Reopen an accepted case only for its documented consequential reason and stopping condition. Keep an exact installed-candidate follow-up in the release ledger where applicable.
5. **Record and stop.** One short record per shot: source/environment, goal, prior-case check, fixture/perturbation, observations, hashes or resource/timing evidence, disposition, fix/tests if any, and precise remaining limit. File only a distinct issue; link a related existing ID for a true regression. Remove temporary fixtures and preserve only useful receipts.

Write those records in the [execution log](FILECAT_EXPLORATORY_UX_HARDENING_RESULTS.md), with a link to any larger evidence artifact. Start each native session by confirming the app's exact build/source identity and a small positive fixture. A CI run may proceed in parallel; investigate an actionable required-lane failure before blaming it on a shot or making another product change. Do not wait idle for a queued run.

## Triage and finite stopping rules

- **P0/P1:** An observed wrong destination/object, data loss, unsafe authority, silent partial success, or blocked core task enters the release issue register and is fixed before 1.0.0 qualification. Stop that shot at a minimal reproduction and positive control; expand only to the affected boundary.
- **P2:** Fix a reproducible, consequential UX problem when the remedy is contained and can be verified on the current source. Repetition raises priority but is not required when one real user journey shows substantial friction. A one-off awkward interaction with no demonstrated user cost can be recorded without product churn.
- **P3/idea:** Keep as an optional note. Do not add a release gate or broadly redesign a control from one exploratory observation.
- **No finding:** Record the tested scope and stop. “No additional high-ROI improvement found” is a valid result; do not manufacture work to fill the tranche.
- **Cycle limit:** At most **eight distinct 45-minute shots** before a fresh prioritization decision. An evidence-vetoed duplicate is redrawn and does not count; at most two diagnostic repeats are allowed for one ambiguous result. The owner explicitly resumed the loop after the first tranche: start another bounded cycle only after checking release priorities and remaining distinct seams. Stop a cycle earlier if executable candidate qualification is prioritized, a P0/P1 needs focused resolution, or the next three proposed shots collapse into accepted coverage. A SignPath reply alone does not end exploration. Sample GitHub CI between shots, fix a consequential required-lane failure, and continue other independent work while CI runs.

The tranche is complete when every executed shot has a scoped record, all proved P0/P1 findings are either corrected with their release gate or explicitly blocking, P2 decisions are recorded, temporary fixtures are cleaned up, and the latest product source has no unexplained required CI failure caused by the tranche. This does not assert stable-release readiness or replace the owner’s final GO decision.
