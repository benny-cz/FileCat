## Purpose and boundary

Keep looking for consequential problems in real FileCat work while 1.0.0 qualification and later product development continue: understandable actions, recoverable errors, correct files and destinations, responsive controls, truthful results, and a comfortable visual hierarchy. Prefer short, surprising user journeys over another systematic platform × provider × theme matrix. A journey may cross several tools, but its value must come from a boundary that the existing evidence does not already settle. Evaluate how easily someone notices the next action, reads the outcome, and returns to their file work; functional correctness alone does not settle the UX question.

This is exploratory work, not final 1.0.0 candidate qualification. The [release dashboard](../release/1.0.0/FILECAT_1_0_RELEASE_EXECUTION_REPORT.md) remains **NO-GO**: signing/provider acceptance, a frozen installed candidate, and its other required gates remain separate. Public preview.5 contains I566–I582 but is unsigned. Do not treat an unsigned preview, source build, VM observation, or passing exploratory shot as signed installed-candidate acceptance.

## A small deck of possible shots

These are **prompts to sample**, not claims of untested defects or a mandatory sequence. Shuffle eligible prompts, draw one, then veto or reshape it after the evidence search; a spontaneous real-user observation can replace a draw. Across each rolling eight-shot cycle, include everyday file work and at least one expert inspection task when distinct seams exist; do not force every operating system into every shot.

For a repeatable draw, number the eligible prompt rows in their displayed order and use a recorded random integer to choose among them. Remove a vetoed row from the **current cycle** before drawing again; reconsider it in a later cycle only after a changed source, new user observation or distinct uncovered boundary supplies a reason. ### One stress dial per shot

Pair the ordinary task with **one** bounded pressure: a larger realistic list or file, a second process changing an owned item, a delayed or disconnected provider, a permission/conflict change, repeated rapid input, or a tight but usable viewport. Choose the pressure because it could change that task's user outcome; do not stack them for a dramatic but uninterpretable failure. Record the chosen size, duration and stop guard before execution. A simple positive control should still work, and no negative result counts as proof of safety unless source and destination bytes or identities were checked where relevant. Resource anomalies go to a focused measurement against the existing I06 limits; exploratory screenshots or one slow run do not certify performance.

## Execution for one shot

1. **Select and bound.** Write the user goal, one perturbation, expected user-visible outcome and exact existing-evidence veto. Use a test-owned source/target and record their initial hashes or manifests when mutation is possible. Set a 45-minute exploration limit and a fixed input size. Give a deliberately held control an explicit guard appropriate to the task (30 seconds by default for UI feedback, not for a legitimate large transfer). A guard expiry is a diagnostic observation, not automatically a product failure or a performance-contract violation.
2. **Observe once.** Use a current Git-built app in the ready Win11 or Ubuntu VM, or on the Mac, as the task requires. Record commit/package identity, OS/backend, input steps, visible focus/status/target, final bytes and a screenshot or accessibility receipt where visual or spoken behavior matters. When presentation is the question, record discoverability, visual hierarchy, space used, keyboard focus, and whether expanded content remains visible and scrollable. Keep the physical Windows workstation usable; perform no foreground desktop automation or exclusive loads there. Use only owned fixtures for destructive or permission-changing cases, and do not change real recovery media or stored credentials for exploration.
3. **Triage the consequence.** Check the exact behavior against source, tests, the UX ledger, release issues and security evidence. If it is accepted behavior, explain it and stop. If it is ambiguous, run one narrower positive/negative control. If it is a real new failure, reproduce on an owned fixture before changing code. Do not claim a security defect from a confusing label alone, or a UX pass from a component test alone.
4. **Fix only proved problems.** Prioritize wrong-item/data-loss/security or blocked core work, then repeated substantial friction, then polish. Add a regression for the user-visible invariant when it protects the fix; avoid tests that mirror implementation order. Run affected tests and the required latest-source CI after a product change. Reopen an accepted case only for its documented consequential reason and stopping condition. Keep an exact installed-candidate follow-up in the release ledger where applicable.
5. **Record and close the shot.** One short record per shot: source/environment, goal, prior-case check, fixture/perturbation, observations, hashes or resource/timing evidence, disposition, fix/tests if any, and precise remaining limit. File only a distinct issue; link a related existing ID for a true regression. Remove temporary fixtures and preserve only useful receipts. Then return to the loop's reconciliation step.

Write those records in the [execution log](FILECAT_EXPLORATORY_UX_HARDENING_RESULTS.md), with a link to any larger evidence artifact. Start each native session by confirming the app's exact build/source identity and a small positive fixture. A CI run may proceed in parallel; investigate an actionable required-lane failure before blaming it on a shot or making another product change. Do not wait idle for a queued run. At every handoff, record the cycle number, last completed shot, current source, pending CI, vetoed prompts, open issue and next eligible action so the next active session resumes rather than restarting.

## Open-ended (infinite) loop with bounded work

Repeat **reconcile → select → observe → triage/fix → record → sample CI → reconcile** with **no terminal cycle count**. The owner has authorized the next cycle as well as this one; finishing a tranche, finding no defect, or vetoing three duplicate ideas does **not** finish bughunting. At a cycle boundary, update the release-priority check and resume with a fresh user goal or neglected seam. A user-reported surprise preempts the draw. A later preview or stable release changes the source baseline, not this recurrence rule.

- **P0/P1:** An observed wrong destination/object, data loss, unsafe authority, silent partial success, or blocked core task enters the release issue register and is fixed before 1.0.0 qualification. Close the exploratory shot at a minimal reproduction and positive control. Suspend new draws while the consequential fix and its affected CI gate are resolved; then resume the loop.
- **P2:** Fix a reproducible, consequential UX problem when the remedy is contained and can be verified on the current source. Repetition raises priority but is not required when one real user journey shows substantial friction. A one-off awkward interaction with no demonstrated user cost can be recorded without product churn.
- **P3/idea:** Keep as an optional note. Do not add a release gate or broadly redesign a control from one exploratory observation.
- **No finding:** Record the tested scope, close that shot and draw again. “No additional high-ROI improvement found **in this cycle**” is a valid result; do not manufacture work to fill the cycle.

Close each cycle only after every executed shot has a scoped record, proved P0/P1 findings are corrected or explicitly blocking, P2 dispositions are recorded, owned fixtures are cleaned up, and any consequential latest-source CI failure is diagnosed.
