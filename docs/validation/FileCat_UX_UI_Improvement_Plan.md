# FileCat UX/UI improvement plan

**Review date:** 28 October 2026. **Disposition:** one recommended correction, S2; no S0, S1, or S3 recommendations. The correction is to make Operations' live speed control truthful: preserve the exact transfer cap when reopened or confirmed, and offer the action only for work it can affect. No other high-ROI implementation change was established in the reviewed scope. This plan is analysis only; every recommendation below remains proposed.

### FCUX-NEXT-001 — Make the live speed control truthful

**Classification:** new, narrowly source-confirmed boundary of the live Operations control; S2, high source confidence, medium effort because availability spans several executors. The expected benefit is trustworthy control of a running or queued transfer, especially on a constrained connection, and removal of a misleading action from unrelated jobs. How often users use sub-MB caps is unknown; no frequency or throughput measurement is asserted. The moderate consequence is lost pacing intent and a false control affordance, with a practical workaround for noticed rounding. The correction remains high ROI because the live prompt and its reach can be bounded without changing the transfer engine.

**Affected journey and current behavior.** A user sets a Copy limit of `0.0625 MB/s` in the transfer form, corresponding to `65,536 bytes/s`; the existing component test asserts this exact stored value. While that Copy is unfinished, the user selects its row in Operations and opens **Limit speed…**. `OperationsView.axaml:211` exposes the action. `OperationsView.axaml.cs:390-398` converts `Job.RateLimit` from bytes/s to MB/s with `ToString("0.#")`; therefore the prompt starts at `0.1` in a dot-decimal locale (`0,1` in Czech), and pressing OK writes `104,857 bytes/s` back as a different cap. A positive cap below `0.05 MB/s` is displayed as `0`; confirming it removes the cap. This is an unexecuted, deterministic source-derived scenario, not an observed native interaction. `Job.RateLimit` is live state (`Job.cs:116-120`), and `Job.Throttle` reads it during copy waits (`Job.cs:529-543`), so this is a behavior change rather than cosmetic rounding. Its practical workaround is to re-enter the desired fractional value manually, if the user notices the change.

**Validation gap in the same control.** The initial transfer form parses current-locale or invariant decimal text and rejects nonfinite, negative, overflowing and positive sub-byte limits while retaining the form (`src/FileCat.App/Views/OperationDialogs.cs:315-333`). The live prompt accepts any `double.TryParse` result at or above zero and casts the scaled value to `long` (`src/FileCat.App/Views/OperationsView.axaml.cs:395-398`); it has no equivalent finite/range check. `OverlayDialogService.PromptAsync` already provides a retained prompt, inline assertive error and field help text when its `Validate` delegate returns a reason (`src/FileCat.App/Views/OverlayDialogService.cs:326-380`), so a bounded correction can reuse that behavior. The exact outcome of a nonfinite or overflowing cast across all runtimes is not asserted here; allowing such values to pass validation and replace the user's existing cap is the established gap.

**Action availability in the same control.** The button is bound only to `!IsFinished` (`OperationsView.axaml:211`), so an unfinished Delete, Recycle, Rename, Verify, Archive Test/Update or Undo also offers it. The product's `Job.Throttle` calls are in byte-copy paths (`Executors.cs:999,1159`, `StreamTransferExecutor.cs:488`, `SftpJobs.cs:689`); `JobExecutors.CreateFor` dispatches the other kinds to distinct executors (`Executors.cs:40-77`). For those nontransfer jobs, the prompt changes a stored `RateLimit` number without changing their execution. This is source-confirmed misleading control availability, not a claim that every Copy or Move phase uses throttling: a same-volume Move can use a rename path, and a same-server SFTP Move has a separate unpaced executor (`SftpJobs.cs:26,1212`).

**Prior-work reconciliation.** The [old audit](FileCat_UX_UI_Audit.md#fcux-041) and the accepted ledger's [transfer-form scope](UX_UI_ACCEPTANCE_LEDGER.md#ac-s2-041) address preserving initial Copy options and correcting invalid form input. The [implementation history](UX_UI_IMPLEMENTATION_STATUS.md#evidence-transfer-options-historical) and `TransferDestinationValidationTests.cs:260,539` specifically show the exact `65,536 bytes/s` initial cap. The ledger does not contain a live **Limit speed…** round-trip case, and searches for that control in the old audit, ledger and App tests found none. This proposal does not reopen `FCUX-041` or its accepted siblings; it covers a different control on an already-created job.

**Smallest correction and behavior.** Show the stored limit with meaningful fractional precision and preserve the original integer byte/s cap on untouched confirmation, including values that a `double` conversion cannot represent exactly; retain the explicit `0` = unlimited contract. Validate edited input by the same finite, nonnegative, nonoverflowing and at-least-one-byte/s rules as the transfer form, using the current locale and the supported invariant decimal route. Keep the prompt open with a specific inline reason on invalid input and leave the current cap unchanged. The user-facing prompt can continue to say **“Maximum speed in MB/s (0 removes the limit):”**. Avoid an imprecise one-decimal display even if a separate status summary remains rounded. Show **Limit transfer speed…** only for a selected unfinished job with a byte-copy/upload phase the executor can pace. Same-volume and same-server rename-only Move paths have no bytes to limit; do not imply their rename is paced. A shared parse/format helper and a job capability flag are implementation options, not required abstractions. Likely anchors are `OperationsView.OnLimit`, `JobViewModel` availability, `OperationDialogs.ShowTransferAsync` and their tests; `Job.RateLimit` and `Job.Throttle` should retain their current live-cancellation and bounded-wait behavior. No persisted-state migration is needed because the stored unit remains bytes/s.

**Finite acceptance criteria (future implementation, not passed now).**

1. **Given** an unfinished Copy with an exact `65,536 bytes/s` cap from `0.0625 MB/s`, **when** the user opens **Limit speed…** and confirms the untouched value, **then** the displayed value communicates that fraction and the cap remains exactly `65,536 bytes/s`. The same untouched-confirmation invariant holds for a non-round integer cap that cannot be represented exactly by a `double` MB/s conversion.
2. **Given** an unfinished Copy with a positive cap below `0.05 MB/s`, **when** the prompt opens and its untouched value is confirmed, **then** the cap remains positive and unchanged. **Given** an explicit `0`, confirmation removes the limit.
3. **Given** nonfinite, negative, overflowing, or positive sub-byte text, **when** the user attempts to confirm, **then** the same prompt retains focus/context, exposes a specific inline error to sighted and assistive-technology users, and the old cap remains unchanged. Correction to a valid locale-appropriate or invariant decimal can then succeed in that prompt.
4. **Given** any current cap, **when** Cancel is chosen, **then** the cap does not change. A valid edited cap must affect the selected transfer rather than another job or the global default.
5. **Given** an unfinished byte-copying transfer, **when** its Operations detail is selected, **then** the live speed action is available and changing a valid cap updates that transfer. **Given** an unfinished Delete, Verify or Archive Test job, **when** its detail is selected, **then** no speed action is offered by pointer, keyboard or accessibility action list. A same-volume or same-server rename-only Move does not claim its rename phase is rate-limited.

**Completion check and risks.** Add a targeted App component test around the live prompt's initial text, arbitrary-integer untouched confirmation, invalid correction, selected-job ownership and action availability; reuse existing `TransferDestinationValidationTests` patterns. A small Core test of `RateLimit`/`Throttle` is useful only if the parsing change also touches live engine behavior; existing `JobRateLimitTests` already cover live release and cancellation. During implementation, review before/after prompt presentation and field accessibility on one isolated native desktop if the prompt UI changes. Verify the resulting byte/s state, not merely the label. Do not rerun the accepted provider/theme matrix without a concrete regression signal. The main risks are rounding a legitimate arbitrary byte/s cap, changing decimal-separator behavior, or hiding the control for an executor that does honor throttling; test representative fractional values and derive availability from the actual supported execution paths.
