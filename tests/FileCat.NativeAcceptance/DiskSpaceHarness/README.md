# Native disk-space window harness

This standalone development executable opens the real DiskSpaceWindow with production styles, AppServices, a live ordinary metadata backend and an isolated generated fixture/profile. It does not register a product command or change any capability gate. Build this project explicitly, as with the neighboring native desktop harnesses.

Stage its output into a task-owned bundle and name its **apphost** `FileCat.exe` on Windows or `FileCat` on Unix so other testers can detect the instance. Keep `DiskSpaceHarness.dll` under its own assembly name: the production app dependency is already `FileCat.dll`. Check for apphost and dotnet-hosted FileCat instances immediately before launch; postpone if busy. The harness also refuses another FileCat process and a nonordinary token at entry.

With no arguments, each launch creates a fresh `native-validation/dsa-UUID` beneath its bundle. The selected fixture includes a large file, zero-length file, package-shaped directory, 500 small files, Unicode and hidden names, and hard-link/link fixtures where available. Start remains an explicit window action. `report.json` records the last displayed observation, dimensions, hashes, fixture limitations and source-hash preservation at close. It contains only this generated fixture/profile. Existing data/settings are not used.

The optional `--large-text` switch sets this generated window's text size to 20 DIP for native layout/input checks. `--compact` requests an initial 380x430 client size, avoiding desktop auto-maximization of the larger default window. Both modes are recorded; verify actual native dimensions rather than treating a request as acceptance. Other arguments are refused. Create extra tabs with the window's New analysis action; the ordinary eight-session cap still applies.

`--windows-input` opts into the real Windows input-queue subset in `WindowsInput.cs`. It is restricted to the disposable `DESKTOP-A60F1NE` VM and ordinary `filecatdsa_r2` account, and refuses before creating the desktop application on other machines. It checks the active console session, interactive window station, unlocked Default input desktop, competing FileCat/dotnet processes, foreground ownership, held modifiers and point ownership before gestures. Its desktop-only activation helper does not take focus from Start/Search or another application. A blocked foreground needs user interaction or a postponed run; do not count its timeout as acceptance.

That subset clicks Start and a row, uses native Return/Space, chooses both name directions and follows a breadcrumb and Back while checking stable focus/marks. Owned window captures and `windows-input.json` record the observed steps and exact binaries. Success closes the app; failure also requests its own close. Inspect the final `report.json`, source hashes and process exit separately. This opt-in test does not establish the complete Windows input, screen-reader, theme or DPI matrix, and must never be run as a live host test.

Exercise setup, scanning, metric/chart/table changes, navigation, filters, keyboard focus/marks, review cancellation, tabs and preserving close behavior with native UI input. Check layout and actual accessibility separately; an in-process report or headless rendering is not visual/assistive-technology qualification. Always close the owned instance. If desktop control fails, creating `close.request` inside that exact owned run directory closes only this harness. An eight-minute safety deadline also closes it if the controller stops, and marks that outcome in its report; a deadline close is not a successful manual acceptance result.
