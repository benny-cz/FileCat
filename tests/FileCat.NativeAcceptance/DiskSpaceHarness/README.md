# Native disk-space window harness

This standalone development executable opens the real DiskSpaceWindow with production styles, AppServices, a live ordinary metadata backend and an isolated generated fixture/profile. It does not register a product command or change any capability gate. Build this project explicitly, as with the neighboring native desktop harnesses.

Stage its output into a task-owned bundle and name its **apphost** `FileCat.exe` on Windows or `FileCat` on Unix so other testers can detect the instance. Keep `DiskSpaceHarness.dll` under its own assembly name: the production app dependency is already `FileCat.dll`. Check for apphost and dotnet-hosted FileCat instances immediately before launch; postpone if busy. The harness also refuses another FileCat process and a nonordinary token at entry.

With no arguments, each launch creates a fresh `native-validation/dsa-UUID` beneath its bundle. The selected fixture includes a large file, zero-length file, package-shaped directory, 500 small files, Unicode and hidden names, and hard-link/link fixtures where available. Start remains an explicit window action. `report.json` records the last displayed observation, dimensions, hashes, fixture limitations and source-hash preservation at close. It contains only this generated fixture/profile. Existing data/settings are not used.

The optional `--large-text` switch sets this generated window's text size to 20 DIP for native layout/input checks. `--compact` requests an initial 380x430 client size, avoiding desktop auto-maximization of the larger default window. Both modes are recorded; verify actual native dimensions rather than treating a request as acceptance. Unknown arguments are refused. Create extra tabs with the window's New analysis action; the ordinary eight-session cap still applies.

`--windows-input` opts into the real Windows input-queue subset in `WindowsInput.cs`. It is restricted to the disposable `DESKTOP-A60F1NE` VM and ordinary `filecatdsa_r2` account, and refuses before creating the desktop application on other machines. It checks the active console session, interactive window station, unlocked Default input desktop, competing FileCat/dotnet processes, foreground ownership, held modifiers and point ownership before gestures. Its desktop-only activation helper does not take focus from Start/Search or another application. A blocked foreground needs user interaction or a postponed run; do not count its timeout as acceptance.

That subset clicks Start and a row, uses native Return/Space, chooses both name directions and follows a breadcrumb and Back while checking stable focus/marks. Owned window captures and `windows-input.json` record the observed steps and exact binaries. Success closes the app; failure also requests its own close. Inspect the final `report.json`, source hashes and process exit separately. This opt-in test does not establish the complete Windows input, screen-reader, theme or DPI matrix, and must never be run as a live host test.

Exercise setup, scanning, metric/chart/table changes, navigation, filters, keyboard focus/marks, review cancellation, tabs and preserving close behavior with native UI input. Check layout and actual accessibility separately; an in-process report or headless rendering is not visual/assistive-technology qualification. Always close the owned instance. If desktop control fails, creating `close.request` inside that exact owned run directory closes only this harness. An eight-minute safety deadline also closes it if the controller stops, and marks that outcome in its report; a deadline close is not a successful manual acceptance result.

The Windows input subset also visits the generated navigation link using native arrow keys and checks its visible omitted-target explanation while retaining the independent mark. Reports include formatted table measures and states so a real zero-length regular file can be distinguished from a non-file boundary in the exact tested build.

`--shared-profile` puts this generated stage's profile in `native-validation-shared-profile` beside the harness, allowing serial process-restart checks. `--profile-probe` starts the generated metadata scan and reports its completed revision, host/profile correlation and continuity explanation. It leaves the window open for native capture until the controller writes the exact run's `close.request` or the deadline expires. It refuses combination with `--windows-input`; Windows profile probes also require the disposable VM/account. This self-driving metadata/persistence check is not native pointer, keyboard or accessibility qualification. Corrupt-state probes may modify only this generated stage's private-state file while its app is closed, and must verify preserved bytes, unchanged fixture sources and owned process exit.

`--saved-ordering-probe` uses the same VM/account and close guards. In a fresh generated profile it saves ascending/descending Name views; later processes reopen those exact inventories without resaving. It verifies actual row order, captured scope, empty marks/basket, inert imported origin and filename-only defaults, then shows the descending offline tab for native capture. Controllers also compare all five inventory/catalog payload hashes across processes. Use `--shared-profile` and a fresh task-owned stage for a two-process persistence run. This remains a self-driving functional/native rendering check rather than physical-input qualification.

`--indexed-probe` exercises the internal trusted native profile/quota/acquisition path and full indexed reader. It refuses combination with profile or Windows input probes and uses the same Windows VM/account guards. It closes the acquisition owner before exploring the retained dataset, drills the generated root, selects Name ascending and Table, then inspects a native navigation link when available. The report records exact path/object/file totals, displayed IDs/order, trusted state hash, owner/source closure and explicit namespace evidence. Windows captures only its guarded foreground window, using the existing desktop-only activation helper; Start/Search or another foreground app remains a refusal. Close requests cancel preparation and wait for the actual probe, window and acquisition cleanup before source-hash reporting and process shutdown. This self-driving metadata/rendering subset is not physical-input, full resource, package, accessibility or public-spill qualification.

`--memory-fallback-probe` uses the same ordinary VM/account and owned-process close guards. It refuses combination with other probes. In its fresh generated profile only, it plants an unsupported private-state record and removes the empty analysis scratch directory, then verifies preserving memory preparation. One source overlaps the held ancestor of the unavailable boundary and remains unread; the independent generated fixture is scanned. The completed result enters the memory window, retains its store after acquisition-owner closure, filters one generated filename, clears the query and opens the fixture folder through the normal folder-open route. The report includes stage diagnostics, source/private-neighbor hashes, unavailable scope, continuity notice and retained revision. Breadcrumb navigation is ancestor-only and must not be used to enter that child folder.

This probe renders only FileCat's own visual tree from its actual native window to `native-memory-window-render.png`; it calls no system screen-capture API and collects no desktop, system-frame or unrelated-window pixels. It requires no capture/privacy permission changes. This allows native-process layout review while keeping compositor, native input, accessibility and complete platform/theme/DPI qualification explicitly separate. Controllers verify unchanged source/private-state/neighbor bytes after actual owned process exit and that the unavailable scratch directory was not recreated.
